OAuth 2.0

Casdoor es un servidor de autorización OAuth 2.0. Esta página describe cómo obtener un token de acceso con cada tipo de concesión, cómo verificar un token y cómo usarlo. Si prefieres no llamar a los endpoints tú mismo, usa un SDK de Casdoor o un cliente OIDC estándar.

Endpoints​

EndpointURL
Authorizationhttps://<casdoor-host>/login/oauth/authorize
Tokenhttps://<casdoor-host>/api/login/oauth/access_token
Refresh tokenhttps://<casdoor-host>/api/login/oauth/refresh_token
Token introspectionhttps://<casdoor-host>/api/login/oauth/introspect
UserInfohttps://<casdoor-host>/api/userinfo

En los ejemplos, ClientId y ClientSecret son el Client ID y el Client secret de la aplicación de Casdoor.

Tipos de concesión compatibles​

Grant TypeRFCUse Case
Authorization CodeRFC 6749 §4.1Default; web/mobile apps with a backend. Enabled by default.
ImplicitRFC 6749 §4.2Frontend-only apps without a backend.
Resource Owner PasswordRFC 6749 §4.3Apps with no frontend redirect; user credentials sent directly.
Client CredentialsRFC 6749 §4.4Service-to-service calls with no user involved.
Refresh TokenRFC 6749 §6Renew an access token without re-authenticating.
Device AuthorizationRFC 8628Devices with limited input or no browser.
Token ExchangeRFC 8693Swap an existing token for one with different scope or audience.
JWT BearerRFC 7523Service auth using a signed JWT assertion instead of a client secret.
Verification CodeCasdoor extensionNative apps that sign users in (and up) with a code sent by SMS or email.

El flujo de authorization code está habilitado por defecto. Active los otros tipos de flujo en Grant types en la página de edición de la aplicación.

Flujo de authorization code​

Use este flujo para aplicaciones que inician sesión de usuarios a través del navegador. Es el flujo recomendado.

  1. Redirija al usuario al endpoint de autorización:

    https://<CASDOOR_HOST>/login/oauth/authorize?
    client_id=CLIENT_ID&
    redirect_uri=REDIRECT_URI&
    response_type=code&
    scope=openid&
    state=STATE

  2. El usuario inicia sesión. Casdoor redirige el navegador a su URL de redirección con un código de autorización:

    https://REDIRECT_URI?code=CODE&state=STATE&iss=ISSUER

    iss es la URL del emisor de Casdoor, según lo definido por RFC 9207. Compárela con el issuer del documento de descubrimiento para asegurarse de que la respuesta proviene del servidor de Casdoor al que envió al usuario. Casdoor añade iss a cada respuesta de autorización y a cada error que envía de vuelta a la URL de redirección, y el documento de descubrimiento anuncia esto con "authorization_response_iss_parameter_supported": true.

  3. Intercambie el código por tokens. Envíe una solicitud POST al endpoint de tokens:

    https://<CASDOOR_HOST>/api/login/oauth/access_token

    Con el cuerpo:

    {
        "grant_type": "authorization_code",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "code": Code,
    }

  4. Lea los tokens de la respuesta:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Un código de autorización es válido durante 5 minutos y funciona una sola vez. Un segundo intercambio del mismo código falla con invalid_grant y la descripción authorization code has been used for token: [...].

Las respuestas del endpoint de tokens y del endpoint de refresh token llevan las cabeceras Cache-Control: no-store y Pragma: no-cache, para que ninguna caché guarde los tokens.

Permisos​

Solicite scopes con el parámetro scope de la URL de autorización. Estos determinan qué campos de usuario devuelven los tokens y el endpoint UserInfo.

AlcanceDescripción
openid (default)sub, iss, aud
profilename, displayName, avatar
emailemail - Tooltip
addressaddress (OIDC object in JWT-Standard; see OIDC address claim)
phonenúmero de teléfono

Separe varios scopes con %20:

https://<CASDOOR_HOST>/login/oauth/authorize?
client_id=...&
scope=openid%20email

Para ver las claims detrás de cada scope, consulte la especificación de OpenID Connect.

PKCE​

Casdoor admite Proof Key for Code Exchange (PKCE), que protege el código de autorización de clientes públicos como aplicaciones móviles y de una sola página (SPA).

  1. Genere un code verifier aleatorio de entre 43 y 128 caracteres.

  2. Calcule el code challenge: el hash SHA-256 del verifier codificado en Base64-URL.

  3. Añada dos parámetros a la URL de autorización:

    &code_challenge_method=S256&code_challenge=YOUR_CHALLENGE

  4. Añada el parámetro code_verifier, con el verifier original, a la solicitud de tokens.

Con PKCE, client_secret es opcional en la solicitud de tokens. Si lo envía, debe ser correcto.

nota

Cuando Casdoor inicia sesión de usuarios en un proveedor OAuth externo que requiere PKCE, como Twitter o un proveedor personalizado con PKCE activado, Casdoor genera el code verifier para cada flujo. Usted no implementa PKCE para esa parte.

Vincular un token a un servicio​

Si su aplicación llama a varios servicios de backend, puede vincular un token a uno de ellos, de modo que un token emitido para un servicio no pueda usarse en otro. Casdoor admite Resource Indicators (RFC 8707) para esto.

  1. Añade el parámetro resource, con un URI absoluto que identifique el servicio, a la URL de autorización:

    https://<CASDOOR_HOST>/login/oauth/authorize?
    client_id=CLIENT_ID&
    redirect_uri=REDIRECT_URI&
    response_type=code&
    scope=openid&
    state=STATE&
    resource=https://api.example.com

  2. Envía el mismo resource en la solicitud de token:

    {
        "grant_type": "authorization_code",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "code": Code,
        "resource": "https://api.example.com"
    }

La afirmación aud (audiencia) del token de acceso es entonces el URI del recurso y no el ID del cliente. El servicio verifica que se emitió un token para él comprobando aud. El valor de resource debe ser exactamente el mismo en ambas solicitudes.

Casdoor mantiene el parámetro resource durante el inicio de sesión interactivo. Si el usuario debe introducir una contraseña, completar la autenticación multifactor (MFA), usar WebAuthn o aprobar la página de consentimiento, el parámetro sobrevive a las redirecciones. También se conserva cuando Casdoor inicia sesión automáticamente al usuario con una sesión existente.

Cuando actualizas el token, el nuevo token de acceso mantiene el aud de la concesión original. Puedes repetir resource en la solicitud de actualización, como parámetro de consulta o campo del cuerpo. Si lo haces, debe tener el mismo valor que en la concesión original. De lo contrario, Casdoor devuelve invalid_grant con la descripción resource parameter does not match the original grant.

Omitir la página de inicio de sesión con una pista de proveedor​

Para enviar al usuario directamente a un proveedor OAuth, sin mostrar la página de inicio de sesión de Casdoor, añade provider_hint=<provider-name> a la URL de autorización:

https://<CASDOOR_HOST>/login/oauth/authorize?
client_id=CLIENT_ID&
redirect_uri=REDIRECT_URI&
response_type=code&
scope=openid&
state=STATE&
provider_hint=github

Casdoor sirve entonces una pequeña página de redirección, sin cargar el frontend completo, y envía al usuario al proveedor. Esto acorta el tiempo hasta la redirección en dispositivos y conexiones lentas.

Registro en el flujo de autorización​

Un usuario que crea una cuenta durante el flujo de autorización es redirigido a tu URL de redirección con un código de autorización tan pronto como finaliza el registro, exactamente igual que después de un inicio de sesión. Casdoor mantiene los parámetros de autorización, como client_id, response_type y redirect_uri, durante el registro. Tu aplicación no necesita cambios para esto.

Controlar la indicación de inicio de sesión​

Por defecto, un usuario que ya tiene una sesión de Casdoor puede iniciar sesión sin volver a introducir credenciales. Añade los parámetros OpenID Connect prompt y max_age a la URL de autorización para cambiar esto:

ParameterEffect
prompt=loginThe user must enter credentials again, even with an existing session
max_age=<seconds>El usuario debe volver a introducir credenciales si las introdujo por última vez hace más de <seconds> segundos, o si Casdoor no sabe cuándo lo hizo
prompt=noneCasdoor shows no page. It signs the user in with the existing session, or sends an error back to the redirect URL

prompt acepta una lista de valores separados por espacios. Cuando la sesión existente no satisface prompt=login o max_age, un inicio de sesión con esa sesión falla con login_required y el mensaje Please sign in again. La hora en la que el usuario introdujo las credenciales está en la afirmación auth_time del token de ID.

Usa prompt=none para comprobar, por ejemplo desde un iframe oculto, si el usuario sigue teniendo sesión iniciada. Casdoor omite entonces la redirección automática a un único proveedor, y responde de la misma manera que iría una respuesta exitosa, con state e iss, y con uno de estos errores:

ErrorReason
login_requiredNo Casdoor session, the user of the session isn't in the organization of the application, or the session doesn't satisfy max_age
consent_requiredThe user must approve the consent page first
interaction_requiredThe user must update the password, set up or complete MFA, select a plan, or fill in the prompt page first
access_deniedThe sign-in failed for another reason. error_description says why
server_errorThe request to Casdoor failed

Concesión implícita​

Usa esta concesión solo para aplicaciones sin backend. Prefiere la concesión de código de autorización con PKCE.

  1. En Grant types de la aplicación, activa Token para devolver un token de acceso, ID Token para devolver un token de ID, o ambos.

  2. Redirige al usuario a:

    https://<CASDOOR_HOST>/login/oauth/authorize?client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&response_type=token&scope=openid&state=STATE

  3. Después de que el usuario inicie sesión, Casdoor redirige el navegador a:

    https://REDIRECT_URI#access_token=ACCESS_TOKEN&token_type=Bearer&state=STATE&iss=ISSUER

response_type puede ser token, id_token, o id_token token. El endpoint de autorización nunca devuelve un token de actualización. Si el tipo de concesión que necesita un tipo de respuesta no está activado, Casdoor muestra Grant_type: token is not supported in this application (o id_token).

Cuando scope contiene openid y la respuesta contiene un token de ID, envía un parámetro nonce. Casdoor lo copia en el token de ID, y rechaza la solicitud sin él: The nonce parameter is required for this response type.

precaución

La concesión implícita en el endpoint de tokens (grant_type=token con un nombre de usuario y una contraseña) requiere un usuario con una contraseña local. Los usuarios creados solo a través de un proveedor externo y que no tienen contraseña local no pueden usarla y reciben invalid_grant. Se aplican las mismas reglas que para la concesión de contraseña. Usa la concesión de código de autorización para estos usuarios.

Flujo híbrido​

En el flujo híbrido de OpenID Connect, el endpoint de autorización devuelve un código de autorización junto con tokens. Tu frontend puede usar los tokens inmediatamente, y tu backend intercambia el código como en la concesión de código de autorización.

response_type es una combinación de code, token e id_token separados por espacios. Los valores híbridos son:

response_typeThe authorization endpoint returns
code id_tokencode and id_token
code tokencode and access_token
code token id_tokencode, access_token e id_token

  1. En Grant types de la aplicación, activa Token para un tipo de respuesta que contenga token, y ID Token para uno que contenga id_token.

  2. Redirija al usuario al endpoint de autorización con el tipo de respuesta y un nonce:

    https://<CASDOOR_HOST>/login/oauth/authorize?client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&response_type=code%20id_token&scope=openid&state=STATE&nonce=NONCE

    El nonce es obligatorio cuando el scope contiene openid y el tipo de respuesta contiene id_token, o es code token.

  3. Después de que el usuario inicie sesión, Casdoor redirige el navegador a su URL de redirección. Los valores están en el fragmento, a menos que solicite otro modo de respuesta.

  4. Intercambie el código en el endpoint de tokens. Solo este intercambio devuelve un token de actualización.

El token de ID lleva estas reclamaciones de la especificación OpenID Connect:

ClaimWhen it's present
auth_timeWhen Casdoor knows the time at which the user last entered credentials
at_hashWhen the ID token comes with an access token, and in the ID token of the authorization code grant
c_hashWhen the ID token comes with an authorization code

at_hash y c_hash usan SHA-256, o SHA-384 o SHA-512 si el método de firma de Token signing method de la aplicación termina en 384 o 512. Verifíquelos como describe la especificación OpenID Connect.

Modos de respuesta​

response_mode decide cómo envía Casdoor la respuesta de autorización, o el error, a la URL de redirección:

response_modeDeliveryDefault for
queryIn the query stringresponse_type=code
fragmentIn the fragment, after #Every response type that returns a token
form_postIn a form that the browser submits to the redirect URL with POSTNone

Casdoor nunca coloca tokens en la cadena de consulta. Una respuesta que contenga un token va en el fragmento, incluso con response_mode=query. La respuesta contiene state e iss, y token_type=Bearer cuando contiene un token de acceso. Con form_post, son campos del formulario. La página de inicio de sesión y la página de consentimiento admiten los tres modos.

Con Auto signin activado, Casdoor inicia sesión a un usuario que tiene una sesión sin cargar la página de inicio de sesión solo para response_type=code con response_mode vacío o query. Otras solicitudes cargan la página de inicio de sesión, que luego completa el inicio de sesión.

Flujo de dispositivo​

Use este flujo para dispositivos con entrada limitada o sin navegador, como televisores inteligentes y herramientas CLI.

  1. Active el flujo de dispositivo en Grant types de la aplicación.
  2. Envíe una solicitud al device_authorization_endpoint desde el documento de descubrimiento.
  3. Muestre al usuario el verification_uri de la respuesta, como texto o como código QR.
  4. El usuario abre la URL en otro dispositivo, introduce el código de usuario e inicia sesión. Casdoor proporciona la página detrás de verification_uri, por lo que no necesita crear una interfaz de usuario para ella.
  5. Mientras tanto, el dispositivo consulta el endpoint de tokens con su device_code hasta que el usuario haya iniciado sesión. Consulte RFC 8628, sección 3.4.

También puede ofrecer el inicio de sesión por dispositivo como un método de inicio de sesión en la tabla Signin methods de la aplicación.

Permita a los usuarios iniciar sesión en su sitio web escaneando un código QR​

El mismo flujo permite a los usuarios que han iniciado sesión en su aplicación nativa iniciar sesión en su sitio web escaneando un código QR con la aplicación.

  1. En la consola de administración de Casdoor, añada Device login a los Signin methods de la aplicación, con la regla Login page.
  2. Active Device Code en Grant types.

La página de inicio de sesión ahora muestra un código QR junto al formulario y completa el inicio de sesión por sí sola una vez que se aprueba el código QR.

El código QR contiene el verification_uri, por ejemplo https://<casdoor-host>/login/oauth/device/ra91hy?cancelToken=.... Un usuario que lo escanea con la cámara de un teléfono abre la URL en el navegador, inicia sesión y aprueba allí. Su aplicación puede aprobarlo directamente en su lugar, con el token de acceso que ya posee:

  1. Obtenga el código de usuario de la ruta de la URL. En el ejemplo, es ra91hy.

  2. Muestre al usuario aquello en lo que está a punto de iniciar sesión.

  3. Envíe una solicitud POST a https://<casdoor-host>/api/login con el encabezado Authorization: Bearer <access-token> y el cuerpo:

    {
        "application": ApplicationName,
        "organization": OrganizationName,
        "type": "device",
        "userCode": "ra91hy"
    }

Para rechazar el inicio de sesión, envíe userCode y el cancelToken de la misma URL como parámetros de consulta a https://<casdoor-host>/api/cancel-device-auth.

Flujo de dispositivo con varias réplicas​

De forma predeterminada, Casdoor mantiene las solicitudes de autorización de dispositivo pendientes, que asignan códigos de dispositivo a códigos de usuario, en memoria. Con varias réplicas de Casdoor, la solicitud de consulta del dispositivo y la confirmación en el navegador pueden alcanzar diferentes réplicas, y el flujo falla entonces intermitentemente.

Para compartir las solicitudes entre réplicas, configure redisEndpoint en conf/app.conf. Casdoor las almacena entonces en Redis. Esta es la misma opción que comparte sesiones, en el formato host:port[,poolSize[,password[,db]]], por ejemplo localhost:6379,100,mypassword,2, y no se necesita ninguna otra opción. Varias direcciones en el primer campo, separadas por ;, usan Redis Cluster. Si Casdoor no puede conectar con Redis al iniciarse, registra una advertencia y usa el almacén en memoria. Consulte la Referencia de configuración.

Flujo de credenciales de propietario de recursos​

Use este grant solo cuando su aplicación no puede redirigir al usuario a Casdoor y recopila el nombre de usuario y la contraseña por sí misma.

  1. Active el password grant en Grant types de la aplicación.

  2. Envíe una solicitud POST al endpoint de token:

    https://<CASDOOR_HOST>/api/login/oauth/access_token

    Con el cuerpo:

    {
        "grant_type": "password",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "username": Username,
        "password": Password,
    }

  3. Lea los tokens de la respuesta:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Cuando Casdoor rechaza el password grant​

Una contraseña sola omitiría las comprobaciones de la página de inicio de sesión. Por lo tanto, Casdoor rechaza el password grant, y el implicit grant en el endpoint de token, con invalid_grant en estos casos:

Caseerror_description
The user has MFA enabledthe user has MFA enabled and cannot sign in with a password grant, please use the authorization code flow
The organization has turned off sign-inThe organization: <organization> has disabled users to signin
The user must change the password, or must set up MFA that the organization requiresthe user: <organization>/<user> must update the password or set up MFA on the login page first
The user has no local password, for example a user created through an external providerOAuth users cannot use password grant type, please use authorization code flow

Las otras restricciones de inicio de sesión de la aplicación y la organización, como las restricciones de IP, también se aplican. Un usuario que deba cambiar la contraseña o configurar MFA lo hace primero en la página de inicio de sesión, después de lo cual el password grant vuelve a funcionar.

Verification code grant​

Utilice este grant en aplicaciones nativas que inician sesión a los usuarios con un número de teléfono o una dirección de correo electrónico y un código de un solo uso, sin abrir un navegador. Es un grant de extensión de Casdoor, según lo permitido por la sección 4.5 del RFC 6749. Si la aplicación lo permite, una dirección que aún no tiene una cuenta se registra en el mismo paso.

  1. Active Verification Code en Grant types de la aplicación, y agregue un proveedor de SMS, un proveedor de correo electrónico, o ambos a la aplicación.

  2. Envíe el código. Envíe una solicitud POST con datos de formulario a https://<casdoor-host>/api/send-verification-code:

    FieldValue
    applicationIdadmin/<APPLICATION_NAME>
    typephone or email
    destThe phone number or email
    countryCodeThe region of a phone number, e.g. CN or US. Not needed for an E.164 number like +8613800000000
    methodlogin
    captchaTypenone, or the captcha type and captchaToken when the application's captcha provider asks for one

  3. Intercambie el código por tokens. Envíe una solicitud POST a https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "urn:casdoor:params:oauth:grant-type:verification-code",
        "client_id": ClientId,
        "username": "+8613800000000",
        "code": "123456",
        "scope": "openid profile"
    }

    username es el número de teléfono o la dirección de correo electrónico a la que se envió el código. Para un número de teléfono en formato nacional, envíe también country_code.

El grant no necesita un secreto de cliente, por lo que funciona desde un cliente público. La respuesta es la misma que para los otros grants y contiene un refresh_token que mantiene al usuario conectado.

Los códigos incorrectos cuentan hacia el límite de Failed signin limit de la aplicación. Casdoor rechaza a los usuarios que tienen MFA habilitado. Utilice el authorization code grant para ellos.

Registrar nuevos usuarios con un código de verificación​

Cuando ningún usuario tiene el número de teléfono o la dirección de correo electrónico, el grant crea el usuario, como lo haría la página de registro, si se cumplen todas las siguientes condiciones:

  • Enable signup está activado para la aplicación, y Disable self signup está desactivado.
  • Los Signup items de la aplicación no requieren nada más allá de lo que demuestra el código. Solo ID, Username, Display name, Password, Confirm password, Agreement, Signup button y Providers pueden ser requeridos, además de Email cuando el usuario se registra con una dirección de correo electrónico, o Phone cuando el usuario se registra con un número de teléfono. Los elementos de registro predeterminados requieren tanto Email como Phone, así que haga que el otro sea opcional.
  • Para un número de teléfono, su región está en Supported country codes de la organización.

De lo contrario, /api/send-verification-code responde que el usuario no existe, y solo los usuarios existentes pueden iniciar sesión.

Client credentials grant​

Utilice este grant para llamadas máquina a máquina, donde no hay ningún usuario presente.

  1. Active el client credentials grant en Grant types de la aplicación.

  2. Envíe una solicitud POST a https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "client_credentials",
        "client_id": ClientId,
        "client_secret": ClientSecret,
    }

  3. Lea el token de la respuesta:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

A diferencia de los tokens de los grants anteriores, este access token pertenece a la aplicación y no a un usuario.

Concesión de token de actualización​

Utilice el token de actualización de una respuesta anterior para obtener un nuevo token de acceso.

  1. Establezca la vida útil de los tokens de actualización en Refresh token expire de la aplicación. El valor predeterminado es 0 horas.

  2. Envíe una solicitud POST a https://<casdoor-host>/api/login/oauth/refresh_token:

    {
        "grant_type": "refresh_token",
        "refresh_token": REFRESH_TOKEN,
        "scope": SCOPE,
        "client_id": ClientId,
        "client_secret": ClientSecret,
    }

  3. Lea los tokens de la respuesta:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Casdoor comprueba la solicitud de actualización de la siguiente manera:

  • Si el token fue emitido por un intercambio de código de autorización que envió un client_secret, o por un intercambio de token, la solicitud de actualización debe contener el client_secret correcto. De lo contrario, Casdoor devuelve invalid_client. Un cliente público que utilizó PKCE sin secreto se actualiza sin uno.
  • El token de actualización debe pertenecer a la aplicación solicitante. De lo contrario, Casdoor devuelve invalid_grant con the token is for wrong application (client_id).
  • Un scope en la solicitud debe ser un subconjunto del scope original. Si lo omite, el nuevo token tiene el scope original.
  • Un token de actualización desconocido o revocado falla con invalid_grant y refresh token is invalid or revoked. Un token de actualización que Casdoor haya invalidado, por ejemplo al cerrar sesión, falla con invalid_grant y refresh token is expired.

Cambiar el nombre de un usuario no invalida los tokens de actualización del usuario. Para ver los eventos que sí revocan los tokens, consulte Cuándo Casdoor revoca tokens.

Rotación de tokens de actualización​

Por defecto, cada actualización devuelve un nuevo token de actualización y revoca el que se utilizó, como recomienda RFC 9700 para clientes públicos. Guarde el nuevo token de actualización después de cada actualización. Un token de actualización que ya se ha utilizado falla con invalid_grant.

La rotación rompe los clientes en los que varios procesos comparten un único token de actualización, por ejemplo, una CLI que ejecuta trabajos paralelos con un token de una variable de entorno: la primera actualización revoca el token para todos los demás. Para tales clientes, active Disable refresh token rotation en la configuración OIDC/OAuth de la aplicación. Entonces:

  • Una actualización devuelve el mismo token de actualización, que mantiene su caducidad original.
  • Los tokens de acceso de las actualizaciones anteriores siguen siendo válidos hasta que caduquen.
  • Cerrar sesión sigue revocando el token de actualización para todos los procesos.
precaución

Sin rotación, un token de actualización filtrado funciona hasta que caduca. Mantenga Refresh token expire corto y prefiera DPoP para clientes públicos.

Concesión de intercambio de token​

Token Exchange (RFC 8693) intercambia un token por un nuevo token con diferentes propiedades. Utilícelo cuando un servicio llama a otro en nombre de un usuario, o para reducir el alcance de un token antes de pasarlo a un servicio posterior. Por ejemplo, una puerta de enlace API intercambia un token con un alcance amplio por un token con un alcance estrecho antes de reenviar una solicitud a un microservicio, para que cada servicio obtenga solo los permisos que necesita.

Envíe una solicitud POST a https://<casdoor-host>/api/login/oauth/access_token:

{
    "grant_type": "urn:ietf:params:oauth:grant-type:token-exchange",
    "client_id": ClientId,
    "client_secret": ClientSecret,
    "subject_token": SubjectToken,
    "subject_token_type": "urn:ietf:params:oauth:token-type:access_token",
    "scope": "openid email"
}
ParameterDescripción
subject_tokenThe token to exchange, typically an access token or a JSON Web Token (JWT) that you already hold
subject_token_typeurn:ietf:params:oauth:token-type:access_token (default), urn:ietf:params:oauth:token-type:jwt, or urn:ietf:params:oauth:token-type:id_token
scopeOptional. A subset of the scope of the subject token. If you omit it, the new token has the scope of the subject token
audienceOptional. The application that the new access token is for, by its client ID or by its application name. The aud claim of the new access token is then the client ID of that application, and the aud of the new ID token stays the requesting client

La respuesta contiene un nuevo token para el mismo usuario que el token de sujeto:

{
    "access_token": "eyJhb...",
    "id_token": "eyJhb...",
    "refresh_token": "eyJhb...",
    "token_type": "Bearer",
    "expires_in": 10080,
    "scope": "openid email"
}

Casdoor valida el token de sujeto con el certificado de la aplicación que lo emitió, identificado por la reclamación azp, y no con el certificado del cliente solicitante. Si el cliente solicitante no es el emisor, la reclamación aud del token de sujeto debe incluir el ID de cliente del cliente solicitante. De lo contrario, Casdoor rechaza el intercambio con invalid_grant. Esto evita que una aplicación intercambie los tokens de otra aplicación sin ser nombrada como audiencia (RFC 8693, sección 2.1). La regla se aplica a todos los formatos de Token format, incluyendo JWT-Standard.

Casdoor también rechaza el intercambio en estos casos:

CaseError
El token de sujeto no es un token activo de Casdoor, por ejemplo porque fue revocado o ha expirado. Con subject_token_type establecido en urn:ietf:params:oauth:token-type:id_token, Casdoor busca el token como un token de identificación, de lo contrario como un token de accesoinvalid_grant, subject_token is revoked or unknown
The subject token has no user, for example a token of the client credentials grantinvalid_grant, subject_token has no user
The user is forbidden to sign ininvalid_grant
The user isn't in the organization of the requesting application, and the application isn't sharedinvalid_grant
audience isn't a known applicationinvalid_target
The audience application isn't in the organization of the user, and isn't sharedinvalid_target

Un token de un emisor externo también puede ser el token de sujeto, sin secreto de cliente. Consulte Credenciales federadas.

Concesión de portador JWT​

Con la concesión de portador JWT (RFC 7523), un cliente obtiene un token de acceso presentando una afirmación JWT firmada en lugar de un secreto de cliente. Úselo para llamadas de servicio a servicio en las que el cliente posee una clave privada y no desea compartir un secreto de larga duración.

  1. Active JWT Bearer en Grant types de la aplicación.

  2. Suba el certificado del cliente en Client cert en la pestaña Security de la aplicación. Casdoor verifica las aserciones con la clave pública de dicho certificado.

  3. Cree la aserción: un JWT firmado con la clave privada del cliente que contiene las siguientes reclamaciones (claims):

    ClaimDescription
    issIssuer — the client_id of the application
    subSujeto — el client_id de la aplicación
    audAudience — the Casdoor token endpoint URL
    expExpiry time (Unix timestamp)

  4. Envíe una solicitud POST a https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "urn:ietf:params:oauth:grant-type:jwt-bearer",
        "client_assertion_type": "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
        "client_assertion": "<signed-JWT>",
        "client_id": "CLIENT_ID"
    }

  5. Lea el token de la respuesta:

    {
        "access_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Casdoor verifica la firma y las reclamaciones JWT estándar. El token de acceso pertenece a la aplicación, igual que con la concesión de credenciales de cliente.

La assertion de la concesión JWT bearer también puede ser un token de un emisor externo en el que confía la aplicación. Consulte Credenciales federadas.

Credenciales federadas (identidad de carga de trabajo)​

Con las credenciales federadas, una aplicación confía en los tokens de un emisor OpenID Connect externo, como GitHub Actions, Kubernetes, una identidad de carga de trabajo en la nube u otro IdP, como sus credenciales. Una carga de trabajo que ya posee dicho token obtiene un token de Casdoor sin necesidad de un secreto de cliente o un certificado de cliente.

  1. En la consola de administración de Casdoor, abra la aplicación y vaya a la pestaña OIDC/OAuth.

  2. En Federated credentials, agregue una fila para cada emisor y sujeto en los que confíe:

    ColumnDescription
    IssuerThe issuer of the external tokens. It must equal the iss claim exactly, for example https://token.actions.githubusercontent.com
    JWKS URLThe URL of the signing keys of the issuer. If you leave it empty, Casdoor reads jwks_uri from <issuer>/.well-known/openid-configuration, whose issuer must match
    SubjectRequired. The sub claim to accept. * matches any text, for example repo:my-org/my-repo:*
    AudienceEl valor aud a aceptar. Si lo deja vacío, Casdoor acepta su propio origen, su endpoint de tokens https://<casdoor-host>/api/login/oauth/access_token, o el ID de cliente de la aplicación
    UserThe user that the token stands for: a username, or {claim} to take the username from a claim, for example {email}. If you leave it empty, the token stands for the application itself

  3. En Grant types, active la concesión que utiliza la carga de trabajo.

  4. Haga clic en Save.

La carga de trabajo presenta entonces su token externo de una de las tres formas siguientes:

  • Como client_assertion en el endpoint de tokens, con client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer, para autenticar al cliente en cualquier concesión. Envíe también client_id en la solicitud, porque el sub de un token externo no es un ID de cliente.
  • Como la assertion de la concesión JWT bearer.
  • Como el subject_token de la concesión de intercambio de tokens. No se necesita un secreto de cliente.

Por ejemplo, un trabajo de GitHub Actions intercambia su token OIDC por un token de Casdoor:

curl -X POST https://<casdoor-host>/api/login/oauth/access_token \
  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d client_id=<client-id> \
  -d subject_token=<github-oidc-token> \
  -d subject_token_type=urn:ietf:params:oauth:token-type:jwt

Casdoor verifica un token externo de la siguiente manera:

  • La firma se verifica con las claves del emisor. Casdoor almacena en caché las claves durante una hora y las vuelve a obtener, como máximo una vez por minuto, cuando un token tiene un kid desconocido.
  • El algoritmo de firma es uno de RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384, ES512 o EdDSA.
  • El token debe tener una reclamación exp. Casdoor permite un desfase de reloj de un minuto.
  • Un token de un emisor de confianza cuyo sujeto no coincide con ninguna fila falla, por ejemplo con the subject: <sub> of issuer: <issuer> is not trusted by application: [<application>].

Con User vacío, el nuevo token es un token de aplicación, igual que con la concesión de credenciales de cliente, sin un token de actualización ni un token de ID. En caso contrario, es un token del usuario mapeado en la organización de la aplicación. Si ese usuario no existe, o al token le falta la reclamación, Casdoor devuelve invalid_grant.

El documento de descubrimiento lista private_key_jwt en token_endpoint_auth_methods_supported.

DPoP (tokens restringidos al remitente)​

Casdoor admite Demonstrating Proof of Possession (DPoP, RFC 9449). DPoP vincula un token de acceso a una clave que posee el cliente, de modo que un token filtrado es inútil sin la clave privada.

Para obtener un token vinculado a DPoP, envíe un encabezado DPoP con un JWT de prueba DPoP en la solicitud de token:

POST /api/login/oauth/access_token
DPoP: <DPoP proof JWT>

Casdoor vincula el token a la clave pública de la prueba, mediante su huella digital JWK (jkt), y devuelve el token_type DPoP en lugar de Bearer:

{
    "access_token": "eyJhb...",
    "token_type": "DPoP",
    "expires_in": 10080,
    "scope": "openid"
}

La solicitud de token de actualización acepta el mismo encabezado DPoP. Casdoor rechaza una prueba inválida con el error invalid_dpop_proof. Un token de actualización emitido con DPoP también está vinculado a la clave: actualizarlo requiere una prueba DPoP firmada con la misma clave. Sin una prueba, o con una prueba de otra clave, la actualización falla con invalid_dpop_proof. Casdoor verifica la reclamación htu de una prueba de actualización contra el endpoint de tokens, https://<casdoor-host>/api/login/oauth/access_token.

El documento de descubrimiento enumera los algoritmos de firma que Casdoor acepta para las pruebas en dpop_signing_alg_values_supported:

{
    "dpop_signing_alg_values_supported": ["RS256", "RS512", "ES256", "ES384", "ES512", "PS256", "PS384", "PS512"]
}

La respuesta de introspección del token muestra la vinculación de clave en la reclamación cnf.jkt (RFC 9449, sección 8).

Verificar un token de acceso​

Casdoor admite introspección de tokens (RFC 7662). Autentique la solicitud con autenticación básica HTTP, usando el ID del cliente como nombre de usuario y el secreto del cliente como contraseña:

POST /api/login/oauth/introspect HTTP/1.1
Host: CASDOOR_HOST
Accept: application/json
Content-Type: application/x-www-form-urlencoded
Authorization: Basic Y2xpZW50X2lkOmNsaWVudF9zZWNyZXQ=

token=ACCESS_TOKEN&token_type_hint=access_token

Ejemplo de respuesta:

{
    "active": true,
    "client_id": "c58c...",
    "username": "admin",
    "token_type": "Bearer",
    "exp": 1647138242,
    "iat": 1646533442,
    "nbf": 1646533442,
    "sub": "7a6b4a8a-b731-48da-bc44-36ae27338817",
    "aud": [
        "c58c..."
    ],
    "iss": "http://localhost:8000"
}

Alternativamente, verifique usted mismo la firma del token con la clave pública del certificado de la aplicación, o con las claves del endpoint JWKS. Los SDKs hacen esto en ParseJwtToken().

Usar un token de acceso​

Envíe el token de acceso para llamar a la API de Casdoor. Por ejemplo, llame a /api/userinfo, con GET o POST, de una de estas dos maneras:

  • Con el encabezado Authorization: Authorization: Bearer <access-token>
  • Con un parámetro de consulta: https://<casdoor-host>/api/userinfo?accessToken=<access-token>

Casdoor devuelve los campos del usuario que el alcance del token permite:

{
    "sub": "7a6b4a8a-b731-48da-bc44-36ae27338817",
    "iss": "http://localhost:8000",
    "aud": "c58c..."
}

Para obtener más campos, solicite más alcances en la solicitud de autorización.

UserInfo y get-account​

EndpointReturns
/api/userinfoThe standard OpenID Connect (OIDC) claims of the user, limited by the scopes of the token
/api/get-accountEl objeto completo de usuario de la cuenta iniciada. Este endpoint es específico de Casdoor. Incluye el token de acceso del proveedor OAuth externo, si lo hay

Obtener el token de acceso de un proveedor externo​

Cuando un usuario inicia sesión a través de un proveedor OAuth externo, como GitHub o Google, Casdoor almacena el token de acceso de ese proveedor en el campo originalToken del usuario. Su aplicación puede usarlo para llamar a la API del proveedor, como la API de GitHub o la API de Google Drive, en nombre del usuario, sin otro flujo de OAuth.

Lea el token desde /api/get-account:

{
  "status": "ok",
  "data": {
    "name": "user123",
    "originalToken": "ya29.a0AfH6SMBx...",
    ...
  }
}

Casdoor devuelve originalToken solo al usuario y a los administradores. Para todos los demás solicitantes, oculta el campo.
