OAuth 2.0

O Casdoor é um servidor de autorização OAuth 2.0. Esta página descreve como obter um token de acesso com cada tipo de concessão, como verificar um token e como usá-lo. Se você preferir não chamar os endpoints manualmente, use um SDK do Casdoor ou um cliente OIDC padrão.

Endpoints​

EndpointURL
Authorizationhttps://<casdoor-host>/login/oauth/authorize
Tokenhttps://<casdoor-host>/api/login/oauth/access_token
Refresh tokenhttps://<casdoor-host>/api/login/oauth/refresh_token
Token introspectionhttps://<casdoor-host>/api/login/oauth/introspect
UserInfohttps://<casdoor-host>/api/userinfo

Nos exemplos, ClientId e ClientSecret são o Client ID e o Client secret da aplicação do Casdoor.

Tipos de concessão suportados​

Grant TypeRFCUse Case
Authorization CodeRFC 6749 §4.1Default; web/mobile apps with a backend. Enabled by default.
ImplicitRFC 6749 §4.2Frontend-only apps without a backend.
Resource Owner PasswordRFC 6749 §4.3Apps with no frontend redirect; user credentials sent directly.
Client CredentialsRFC 6749 §4.4Service-to-service calls with no user involved.
Refresh TokenRFC 6749 §6Renew an access token without re-authenticating.
Device AuthorizationRFC 8628Devices with limited input or no browser.
Token ExchangeRFC 8693Swap an existing token for one with different scope or audience.
JWT BearerRFC 7523Service auth using a signed JWT assertion instead of a client secret.
Verification CodeCasdoor extensionNative apps that sign users in (and up) with a code sent by SMS or email.
Mobile One-ClickExtensão do CasdoorAplicações nativas que fazem login (e cadastro) de usuários com o número de telefone do dispositivo, através do Alibaba Cloud PNVS.

A concessão de código de autorização está ativada por padrão. Ative os outros tipos de concessão em Grant types na página de edição da aplicação.

Concessão de código de autorização​

Use esta concessão para aplicações que fazem login de usuários através do navegador. É a concessão recomendada.

  1. Redirecione o usuário para o endpoint de autorização:

    https://<CASDOOR_HOST>/login/oauth/authorize?
    client_id=CLIENT_ID&
    redirect_uri=REDIRECT_URI&
    response_type=code&
    scope=openid&
    state=STATE

  2. O usuário faz login. O Casdoor redireciona o navegador para sua URL de redirecionamento com um código de autorização:

    https://REDIRECT_URI?code=CODE&state=STATE&iss=ISSUER

    iss é a URL do emissor (issuer) do Casdoor, conforme definido pela RFC 9207. Compare-a com o issuer do documento de descoberta para garantir que a resposta vem do servidor Casdoor para o qual você enviou o usuário. O Casdoor adiciona iss a cada resposta de autorização e a cada erro que envia de volta à URL de redirecionamento, e o documento de descoberta anuncia isso com "authorization_response_iss_parameter_supported": true.

  3. Troque o código por tokens. Envie uma requisição POST ao endpoint de token:

    https://<CASDOOR_HOST>/api/login/oauth/access_token

    Com o corpo:

    {
        "grant_type": "authorization_code",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "code": Code,
    }

  4. Leia os tokens da resposta:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Um código de autorização é válido por 5 minutos e funciona apenas uma vez. Uma segunda troca do mesmo código falha com invalid_grant e a descrição authorization code has been used for token: [...].

As respostas dos endpoints de token e de refresh token carregam os cabeçalhos Cache-Control: no-store e Pragma: no-cache, para que nenhum cache retenha os tokens.

Escopos​

Solicite escopos com o parâmetro scope da URL de autorização. Eles determinam quais campos do usuário são retornados pelos tokens e pelo endpoint UserInfo.

EscopoDescrição
openid (default)sub, iss, aud
profilename, displayName, avatar
emailemail address
addressaddress (OIDC object in JWT-Standard; see OIDC address claim)
phonenúmero de telefone

Separe vários escopos com %20:

https://<CASDOOR_HOST>/login/oauth/authorize?
client_id=...&
scope=openid%20email

Para as claims por trás de cada escopo, consulte a especificação OpenID Connect.

PKCE​

O Casdoor suporta Proof Key for Code Exchange (PKCE), que protege o código de autorização de clientes públicos, como aplicativos móveis e single-page applications.

  1. Gere um verificador de código aleatório de 43 a 128 caracteres.

  2. Calcule o desafio de código (code challenge): o hash SHA-256 do verificador codificado em Base64-URL.

  3. Adicione dois parâmetros à URL de autorização:

    &code_challenge_method=S256&code_challenge=YOUR_CHALLENGE

  4. Adicione o parâmetro code_verifier, com o verificador original, à requisição de token.

Com PKCE, client_secret é opcional na requisição de token. Se você enviá-lo, ele deve estar correto.

nota

Quando o próprio Casdoor autentica usuários em um provedor OAuth externo que requer PKCE, como Twitter ou um provedor personalizado com PKCE ativado, o Casdoor gera o verificador de código para cada fluxo. Você não precisa implementar o PKCE para essa parte.

Vincular um token a um serviço​

Se sua aplicação chama vários serviços de backend, você pode vincular um token a um deles, para que um token emitido para um serviço não possa ser usado em outro. O Casdoor suporta Resource Indicators (RFC 8707) para isso.

  1. Adicione o parâmetro resource, com uma URI absoluta que identifica o serviço, à URL de autorização:

    https://<CASDOOR_HOST>/login/oauth/authorize?
    client_id=CLIENT_ID&
    redirect_uri=REDIRECT_URI&
    response_type=code&
    scope=openid&
    state=STATE&
    resource=https://api.example.com

  2. Envie o mesmo resource na requisição de token:

    {
        "grant_type": "authorization_code",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "code": Code,
        "resource": "https://api.example.com"
    }

A claim aud (audience) do token de acesso passa a ser a URI do recurso e não o ID do cliente. O serviço verifica se um token foi emitido para ele checando aud. O valor de resource deve ser exatamente o mesmo em ambas as requisições.

O Casdoor mantém o parâmetro resource durante o login interativo. Se o usuário precisar inserir uma senha, concluir a autenticação multifator (MFA), usar WebAuthn ou aprovar a página de consentimento, o parâmetro sobrevive aos redirecionamentos. Ele também é mantido quando o Casdoor autentica o usuário automaticamente com uma sessão existente.

Ao atualizar o token, o novo token de acesso mantém o aud da concessão original. Você pode repetir resource na requisição de atualização, como parâmetro de consulta ou campo do corpo. Se fizer isso, deve ser o mesmo valor da concessão original. Caso contrário, o Casdoor retorna invalid_grant com a descrição resource parameter does not match the original grant.

Pular a página de login com uma dica de provedor​

Para enviar o usuário diretamente a um provedor OAuth, sem mostrar a página de login do Casdoor, adicione provider_hint=<provider-name> à URL de autorização:

https://<CASDOOR_HOST>/login/oauth/authorize?
client_id=CLIENT_ID&
redirect_uri=REDIRECT_URI&
response_type=code&
scope=openid&
state=STATE&
provider_hint=github

O Casdoor então serve uma pequena página de redirecionamento, sem carregar o frontend completo, e envia o usuário ao provedor. Isso reduz o tempo até o redirecionamento em dispositivos e conexões lentas.

Cadastro no fluxo de autorização​

Um usuário que cria uma conta durante o fluxo de autorização é redirecionado à sua URL de redirecionamento com um código de autorização assim que o cadastro é concluído, exatamente como após um login. O Casdoor mantém os parâmetros de autorização, como client_id, response_type e redirect_uri, durante o cadastro. Sua aplicação não precisa de alterações para isso.

Controlar o prompt de login​

Por padrão, um usuário que já tem uma sessão no Casdoor pode ser autenticado sem inserir credenciais novamente. Adicione os parâmetros OpenID Connect prompt e max_age à URL de autorização para alterar isso:

ParameterEffect
prompt=loginThe user must enter credentials again, even with an existing session
max_age=<seconds>O usuário deve inserir credenciais novamente se elas foram inseridas há mais de <seconds> segundos, ou se o Casdoor não souber quando isso ocorreu
prompt=noneCasdoor shows no page. It signs the user in with the existing session, or sends an error back to the redirect URL

prompt aceita uma lista separada por espaços de valores. Quando a sessão existente não satisfaz prompt=login ou max_age, um login com essa sessão falha com login_required e a mensagem Please sign in again. O horário em que o usuário inseriu as credenciais está na claim auth_time do ID token.

Use prompt=none para verificar, por exemplo, de um iframe oculto, se o usuário ainda está autenticado. O Casdoor então pula o redirecionamento automático para um único provedor e responde da mesma forma que uma resposta bem-sucedida seria enviada, com state e iss, e com um destes erros:

ErrorReason
login_requiredNo Casdoor session, the user of the session isn't in the organization of the application, or the session doesn't satisfy max_age
consent_requiredThe user must approve the consent page first
interaction_requiredThe user must update the password, set up or complete MFA, select a plan, or fill in the prompt page first
access_deniedThe sign-in failed for another reason. error_description says why
server_errorThe request to Casdoor failed

Implicit grant​

Use este grant apenas para aplicações sem backend. Prefira o authorization code grant com PKCE.

  1. Em Grant types da aplicação, ative Token para retornar um token de acesso, ID Token para retornar um ID token, ou ambos.

  2. Redirecione o usuário para:

    https://<CASDOOR_HOST>/login/oauth/authorize?client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&response_type=token&scope=openid&state=STATE

  3. Após o usuário fazer login, o Casdoor redireciona o navegador para:

    https://REDIRECT_URI#access_token=ACCESS_TOKEN&token_type=Bearer&state=STATE&iss=ISSUER

response_type pode ser token, id_token ou id_token token. O endpoint de autorização nunca retorna um refresh token. Se o tipo de grant necessário por um tipo de resposta não estiver ativado, o Casdoor mostra Grant_type: token is not supported in this application (ou id_token).

Quando scope contém openid e a resposta contém um token de ID, envie um parâmetro nonce. O Casdoor o copia para o token de ID e recusa a solicitação sem ele: The nonce parameter is required for this response type.

cuidado

A concessão implícita no endpoint de token (grant_type=token com um nome de usuário e uma senha) requer um usuário com senha local. Usuários criados apenas por meio de um provedor externo e que não possuem senha local não podem usá-la e recebem invalid_grant. As mesmas regras da concessão de senha se aplicam. Use a concessão de código de autorização para esses usuários.

Fluxo híbrido​

No fluxo híbrido do OpenID Connect, o endpoint de autorização retorna um código de autorização junto com os tokens. Seu frontend pode usar os tokens imediatamente, e seu backend troca o código como na concessão de código de autorização.

response_type é uma combinação separada por espaços de code, token e id_token. Os valores híbridos são:

response_typeThe authorization endpoint returns
code id_tokencode and id_token
code tokencode and access_token
code token id_tokencode, access_token e id_token

  1. Em Grant types da aplicação, ative Token para um tipo de resposta que contenha token, e ID Token para um que contenha id_token.

  2. Redirecione o usuário para o endpoint de autorização com o tipo de resposta e um nonce:

    https://<CASDOOR_HOST>/login/oauth/authorize?client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&response_type=code%20id_token&scope=openid&state=STATE&nonce=NONCE

    nonce é obrigatório quando scope contém openid e o tipo de resposta contém id_token, ou é code token.

  3. Após o usuário fazer login, o Casdoor redireciona o navegador para sua URL de redirecionamento. Os valores estão no fragmento, a menos que você solicite outro modo de resposta.

  4. Troque o código no endpoint de token. Somente esta troca retorna um token de atualização.

O token de ID carrega as seguintes declarações da especificação OpenID Connect:

ClaimWhen it's present
auth_timeWhen Casdoor knows the time at which the user last entered credentials
at_hashWhen the ID token comes with an access token, and in the ID token of the authorization code grant
c_hashWhen the ID token comes with an authorization code

at_hash e c_hash usam SHA-256, ou SHA-384 ou SHA-512 quando o Token signing method da aplicação termina em 384 ou 512. Verifique-os conforme descrito pela especificação OpenID Connect.

Modos de resposta​

response_mode decide como o Casdoor envia a resposta de autorização, ou o erro, para a URL de redirecionamento:

response_modeDeliveryDefault for
queryIn the query stringresponse_type=code
fragmentIn the fragment, after #Every response type that returns a token
form_postIn a form that the browser submits to the redirect URL with POSTNone

O Casdoor nunca coloca tokens na string de consulta. Uma resposta que contém um token vai para o fragmento, mesmo com response_mode=query. A resposta contém state e iss, e token_type=Bearer quando contém um token de acesso. Com form_post, eles são campos do formulário. A página de login e a página de consentimento suportam todos os três modos.

Com Auto signin ativado, o Casdoor autentica um usuário que possui uma sessão sem carregar a página de login apenas para response_type=code com response_mode vazio ou query. Outras solicitações carregam a página de login, que então conclui o login.

Concessão de dispositivo​

Use esta concessão para dispositivos com entrada limitada ou sem navegador, como TVs inteligentes e ferramentas CLI.

  1. Ative a concessão de dispositivo em Grant types da aplicação.
  2. Envie uma solicitação para o device_authorization_endpoint do documento de descoberta.
  3. Mostre ao usuário o verification_uri da resposta, como texto ou como código QR.
  4. O usuário abre a URL em outro dispositivo, insere o código do usuário e faz login. O Casdoor fornece a página atrás de verification_uri, então você não precisa construir uma interface para ela.
  5. Enquanto isso, o dispositivo consulta o endpoint de token com seu device_code até que o usuário faça login. Veja RFC 8628, seção 3.4.

Você também pode oferecer o login por dispositivo como um método de login na tabela Signin methods da aplicação.

Permita que usuários façam login em seu site escaneando um código QR​

O mesmo fluxo permite que usuários autenticados em seu aplicativo nativo façam login em seu site escaneando um código QR com o aplicativo.

  1. No console de administração do Casdoor, adicione Device login aos Signin methods da aplicação, com a regra Login page.
  2. Ative Device Code em Grant types.

A página de login agora mostra um código QR ao lado do formulário e completa o login automaticamente assim que o código QR é aprovado.

O código QR contém o verification_uri, por exemplo https://<casdoor-host>/login/oauth/device/ra91hy?cancelToken=.... Um usuário que o escaneia com a câmera de um telefone abre a URL no navegador, faz login e aprova lá. Seu app pode aprová-lo diretamente, usando o token de acesso que já possui:

  1. Obtenha o código do usuário do caminho da URL. No exemplo, é ra91hy.

  2. Mostre ao usuário em que ele está prestes a fazer login.

  3. Envie uma solicitação POST para https://<casdoor-host>/api/login com o cabeçalho Authorization: Bearer <access-token> e o corpo:

    {
        "application": ApplicationName,
        "organization": OrganizationName,
        "type": "device",
        "userCode": "ra91hy"
    }

Para rejeitar o login, envie userCode e o cancelToken da mesma URL como parâmetros de consulta para https://<casdoor-host>/api/cancel-device-auth.

Concessão de dispositivo com várias réplicas​

Por padrão, o Casdoor mantém solicitações pendentes de autorização de dispositivo, que mapeiam códigos de dispositivo para códigos de usuário, na memória. Com várias réplicas do Casdoor, a solicitação de consulta do dispositivo e a confirmação no navegador podem atingir réplicas diferentes, e o fluxo falha intermitentemente.

Para compartilhar as solicitações entre réplicas, defina redisEndpoint em conf/app.conf. O Casdoor então as armazena no Redis. Esta é a mesma opção que compartilha sessões, no formato host:port[,poolSize[,password[,db]]], por exemplo localhost:6379,100,mypassword,2, e nenhuma outra opção é necessária. Vários endereços no primeiro campo, separados por ;, usam o Redis Cluster. Se o Casdoor não conseguir acessar o Redis na inicialização, ele registra um aviso e usa o armazenamento em memória. Veja a Referência de configuração.

Concessão de credenciais de proprietário de recurso (password)​

Use esta concessão somente quando sua aplicação não pode redirecionar o usuário para o Casdoor e coleta o nome de usuário e a senha por conta própria.

  1. Ative o fluxo de concessão por senha em Grant types da aplicação.

  2. Envie uma requisição POST para o endpoint de token:

    https://<CASDOOR_HOST>/api/login/oauth/access_token

    Com o corpo:

    {
        "grant_type": "password",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "username": Username,
        "password": Password,
    }

  3. Leia os tokens da resposta:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Quando o Casdoor recusa a concessão por senha​

Uma senha sozinha ignoraria as verificações da página de login. Portanto, o Casdoor recusa a concessão por senha e a concessão implícita no endpoint de token com invalid_grant nestes casos:

Caseerror_description
The user has MFA enabledthe user has MFA enabled and cannot sign in with a password grant, please use the authorization code flow
The organization has turned off sign-inThe organization: <organization> has disabled users to signin
The user must change the password, or must set up MFA that the organization requiresthe user: <organization>/<user> must update the password or set up MFA on the login page first
The user has no local password, for example a user created through an external providerOAuth users cannot use password grant type, please use authorization code flow

As outras restrições de login da aplicação e da organização, como restrições de IP, também se aplicam. Um usuário que precisa alterar a senha ou configurar MFA faz isso primeiro na página de login, após o qual a concessão por senha funciona novamente.

Concessão por código de verificação​

Use esta concessão em aplicativos nativos que autenticam usuários com um número de telefone ou endereço de e-mail e um código de uso único, sem abrir um navegador. É uma extensão de concessão do Casdoor, conforme permitido pela seção 4.5 do RFC 6749. Se a aplicação permitir, um endereço que ainda não possui conta é cadastrado na mesma etapa.

  1. Ative Verification Code em Grant types da aplicação e adicione um provedor SMS, um provedor de e-mail, ou ambos à aplicação.

  2. Envie o código. Envie uma requisição POST com dados de formulário para https://<casdoor-host>/api/send-verification-code:

    FieldValue
    applicationIdadmin/<APPLICATION_NAME>
    typephone or email
    destThe phone number or email
    countryCodeThe region of a phone number, e.g. CN or US. Not needed for an E.164 number like +8613800000000
    methodlogin
    captchaTypenone, or the captcha type and captchaToken when the application's captcha provider asks for one

  3. Troque o código por tokens. Envie uma requisição POST para https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "urn:casdoor:params:oauth:grant-type:verification-code",
        "client_id": ClientId,
        "username": "+8613800000000",
        "code": "123456",
        "scope": "openid profile"
    }

    username é o número de telefone ou o endereço de e-mail para o qual o código foi enviado. Para um número de telefone no formato nacional, envie também country_code.

A concessão não requer segredo de cliente, portanto funciona de um cliente público. A resposta é a mesma das outras concessões e contém um refresh_token que mantém o usuário conectado.

Códigos incorretos contam para o Failed signin limit da aplicação. O Casdoor recusa usuários que têm MFA habilitado. Use a concessão de código de autorização para eles.

Cadastre novos usuários com um código de verificação​

Quando nenhum usuário possui o número de telefone ou o endereço de e-mail, a concessão cria o usuário, assim como a página de cadastro faria, se todas as seguintes condições forem atendidas:

  • Enable signup está ativado para a aplicação e Disable self signup está desativado.
  • Os campos de Signup items da aplicação não exigem nada além do que o código prova. Apenas ID, Username, Display name, Password, Confirm password, Agreement, Signup button e Providers podem ser obrigatórios, mais Email quando o usuário se cadastra com um endereço de e-mail, ou Phone quando o usuário se cadastra com um número de telefone. Os itens de cadastro padrão exigem tanto Email quanto Phone, então torne o outro opcional.
  • Para um número de telefone, sua região deve estar em Supported country codes da organização.

Caso contrário, /api/send-verification-code responde que o usuário não existe e apenas usuários existentes podem fazer login.

Concessão de um clique móvel​

Aplicativos nativos na China continental também podem autenticar usuários com o número de telefone do dispositivo, sem um código SMS: o SDK de login de um clique do Alibaba Cloud PNVS retorna um token, e o aplicativo troca esse token usando o tipo de concessão urn:casdoor:params:oauth:grant-type:mobile-one-click. Veja Login de um clique móvel.

Concessão de credenciais de cliente​

Use esta concessão para chamadas máquina-a-máquina, onde não há presença de usuário.

  1. Ative a concessão de credenciais de cliente em Grant types da aplicação.

  2. Envie uma requisição POST para https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "client_credentials",
        "client_id": ClientId,
        "client_secret": ClientSecret,
    }

  3. Leia o token da resposta:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Diferentemente dos tokens das concessões acima, este token de acesso pertence à aplicação e não a um usuário.

Concessão de token de atualização​

Use o token de atualização de uma resposta anterior para obter um novo token de acesso.

  1. Defina a validade dos tokens de atualização em Refresh token expire da aplicação. O padrão é 0 horas.

  2. Envie uma requisição POST para https://<casdoor-host>/api/login/oauth/refresh_token:

    {
        "grant_type": "refresh_token",
        "refresh_token": REFRESH_TOKEN,
        "scope": SCOPE,
        "client_id": ClientId,
        "client_secret": ClientSecret,
    }

  3. Leia os tokens da resposta:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

O Casdoor verifica a solicitação de atualização da seguinte forma:

  • Se o token foi emitido por uma troca de código de autorização que enviou um client_secret, ou por uma troca de token, a solicitação de atualização deve conter o client_secret correto. Caso contrário, o Casdoor retorna invalid_client. Um cliente público que usou PKCE sem segredo atualiza sem um.
  • O token de atualização deve pertencer à aplicação solicitante. Caso contrário, o Casdoor retorna invalid_grant com the token is for wrong application (client_id).
  • Um scope na solicitação deve ser um subconjunto do escopo original. Se você omiti-lo, o novo token terá o escopo original.
  • Um token de atualização desconhecido ou revogado falha com invalid_grant e refresh token is invalid or revoked. Um token de atualização invalidado pelo Casdoor, por exemplo ao sair, falha com invalid_grant e refresh token is expired.

Renomear um usuário não invalida os tokens de atualização do usuário. Para os eventos que revogam tokens, veja Quando o Casdoor revoga tokens.

Rotação de token de atualização​

Por padrão, cada atualização retorna um novo token de atualização e revoga o que foi utilizado, conforme recomendado pela RFC 9700 para clientes públicos. Armazene o novo token de atualização após cada atualização. Um token de atualização que já foi utilizado falha com invalid_grant.

A rotação quebra clientes nos quais vários processos compartilham um único token de atualização, por exemplo, uma CLI que executa trabalhos paralelos com um token de uma variável de ambiente: a primeira atualização revoga o token para todas as outras. Para esses clientes, ative Disable refresh token rotation nas configurações OIDC/OAuth da aplicação. Então:

  • Uma atualização retorna o mesmo token de atualização, que mantém seu prazo de validade original.
  • Os tokens de acesso de atualizações anteriores permanecem válidos até expirarem.
  • O logout ainda revoga o token de atualização para todos os processos.
cuidado

Sem rotação, um token de atualização vazado funciona até expirar. Mantenha Refresh token expire curto e prefira DPoP para clientes públicos.

Concessão de troca de token​

Token Exchange (RFC 8693) troca um token por um novo token com propriedades diferentes. Use-o quando um serviço chama outro em nome de um usuário, ou para restringir o escopo de um token antes de passá-lo a um serviço downstream. Por exemplo, um gateway de API troca um token com escopo amplo por um token com escopo restrito antes de encaminhar uma solicitação a um microsserviço, para que cada serviço receba apenas as permissões de que precisa.

Envie uma solicitação POST para https://<casdoor-host>/api/login/oauth/access_token:

{
    "grant_type": "urn:ietf:params:oauth:grant-type:token-exchange",
    "client_id": ClientId,
    "client_secret": ClientSecret,
    "subject_token": SubjectToken,
    "subject_token_type": "urn:ietf:params:oauth:token-type:access_token",
    "scope": "openid email"
}
ParameterDescrição
subject_tokenThe token to exchange, typically an access token or a JSON Web Token (JWT) that you already hold
subject_token_typeurn:ietf:params:oauth:token-type:access_token (default), urn:ietf:params:oauth:token-type:jwt, or urn:ietf:params:oauth:token-type:id_token
scopeOptional. A subset of the scope of the subject token. If you omit it, the new token has the scope of the subject token
audienceOptional. The application that the new access token is for, by its client ID or by its application name. The aud claim of the new access token is then the client ID of that application, and the aud of the new ID token stays the requesting client

A resposta contém um novo token para o mesmo usuário do token de assunto:

{
    "access_token": "eyJhb...",
    "id_token": "eyJhb...",
    "refresh_token": "eyJhb...",
    "token_type": "Bearer",
    "expires_in": 10080,
    "scope": "openid email"
}

O Casdoor valida o token de assunto com o certificado da aplicação que o emitiu, identificado pela claim azp, e não com o certificado do cliente solicitante. Se o cliente solicitante não for o emissor, a claim aud do token de assunto deve incluir o ID do cliente do cliente solicitante. Caso contrário, o Casdoor rejeita a troca com invalid_grant. Isso impede que uma aplicação troque os tokens de outra aplicação sem ser designada como audiência (RFC 8693, seção 2.1). A regra se aplica a todos os formatos de token, incluindo JWT-Standard.

O Casdoor também recusa a troca nestes casos:

CaseError
O token de assunto não é um token ativo do Casdoor, por exemplo, porque foi revogado ou expirou. Com subject_token_type definido como urn:ietf:params:oauth:token-type:id_token, o Casdoor procura o token como um token de ID, caso contrário, como um token de acessoinvalid_grant, subject_token is revoked or unknown
The subject token has no user, for example a token of the client credentials grantinvalid_grant, subject_token has no user
The user is forbidden to sign ininvalid_grant
The user isn't in the organization of the requesting application, and the application isn't sharedinvalid_grant
audience isn't a known applicationinvalid_target
The audience application isn't in the organization of the user, and isn't sharedinvalid_target

Um token de um emissor externo também pode ser o token de assunto, sem segredo do cliente. Veja Credenciais federadas.

Concessão de portador JWT​

Com a concessão de portador JWT (RFC 7523), um cliente obtém um token de acesso apresentando uma asserção JWT assinada em vez de um segredo do cliente. Use-a para chamadas serviço a serviço nas quais o cliente possui uma chave privada e você não deseja compartilhar um segredo de longa duração.

  1. Ative JWT Bearer em Grant types da aplicação.

  2. Carregue o certificado do cliente em Client cert na aba Security da aplicação. O Casdoor verifica as asserções com a chave pública desse certificado.

  3. Crie a asserção: um JWT assinado com a chave privada do cliente e contendo as seguintes claims:

    ClaimDescription
    issIssuer — the client_id of the application
    subAssunto — o client_id da aplicação
    audAudience — the Casdoor token endpoint URL
    expExpiry time (Unix timestamp)

  4. Envie uma solicitação POST para https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "urn:ietf:params:oauth:grant-type:jwt-bearer",
        "client_assertion_type": "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
        "client_assertion": "<signed-JWT>",
        "client_id": "CLIENT_ID"
    }

  5. Leia o token da resposta:

    {
        "access_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

O Casdoor verifica a assinatura e as claims padrão do JWT. O token de acesso pertence à aplicação, assim como na concessão de credenciais do cliente.

A assertion da concessão de portador JWT também pode ser um token de um emissor externo no qual a aplicação confia. Veja Credenciais federadas.

Credenciais federadas (identidade de carga de trabalho)​

Com credenciais federadas, uma aplicação confia nos tokens de um emissor OpenID Connect externo, como GitHub Actions, Kubernetes, uma identidade de carga de trabalho em nuvem ou outro IdP, como sua credencial. Uma carga de trabalho que já possui tal token obtém um token do Casdoor sem segredo do cliente ou certificado do cliente.

  1. No console administrativo do Casdoor, abra a aplicação e vá para a aba OIDC/OAuth.

  2. Em Federated credentials, adicione uma linha para cada emissor e assunto nos quais você confia:

    ColumnDescription
    IssuerThe issuer of the external tokens. It must equal the iss claim exactly, for example https://token.actions.githubusercontent.com
    JWKS URLThe URL of the signing keys of the issuer. If you leave it empty, Casdoor reads jwks_uri from <issuer>/.well-known/openid-configuration, whose issuer must match
    SubjectRequired. The sub claim to accept. * matches any text, for example repo:my-org/my-repo:*
    AudienceO valor aud a aceitar. Se você deixá-lo vazio, o Casdoor aceita sua própria origem, seu endpoint de token https://<casdoor-host>/api/login/oauth/access_token ou o ID do cliente da aplicação
    UserThe user that the token stands for: a username, or {claim} to take the username from a claim, for example {email}. If you leave it empty, the token stands for the application itself

  3. Em Grant types, ative a concessão usada pela carga de trabalho.

  4. Clique em Save.

A carga de trabalho então apresenta seu token externo de uma das três maneiras:

  • Como client_assertion no endpoint de token, com client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer, para autenticar o cliente em qualquer concessão. Envie client_id na solicitação também, porque o sub de um token externo não é um ID de cliente.
  • Como a assertion da concessão de portador JWT.
  • Como o subject_token da concessão de troca de token. Nenhum segredo do cliente é necessário.

Por exemplo, um job do GitHub Actions troca seu token OIDC por um token do Casdoor:

curl -X POST https://<casdoor-host>/api/login/oauth/access_token \
  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d client_id=<client-id> \
  -d subject_token=<github-oidc-token> \
  -d subject_token_type=urn:ietf:params:oauth:token-type:jwt

O Casdoor verifica um token externo da seguinte forma:

  • A assinatura é verificada com as chaves do emissor. O Casdoor armazena em cache as chaves por uma hora e as busca novamente, no máximo uma vez por minuto, quando um token tem um kid desconhecido.
  • O algoritmo de assinatura é um dos RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384, ES512 ou EdDSA.
  • O token deve ter uma reivindicação exp. O Casdoor permite um desvio de relógio de um minuto.
  • Um token de um emissor confiável cujo assunto não corresponde a nenhuma linha falha, por exemplo, com the subject: <sub> of issuer: <issuer> is not trusted by application: [<application>].

Com User vazio, o novo token é um token de aplicação, como na concessão de credenciais do cliente, sem um token de atualização ou um token de ID. Caso contrário, é um token do usuário mapeado na organização da aplicação. Se esse usuário não existir, ou se o token não tiver a reivindicação, o Casdoor retorna invalid_grant.

O documento de descoberta lista private_key_jwt em token_endpoint_auth_methods_supported.

DPoP (tokens com restrição de remetente)​

O Casdoor suporta Demonstrating Proof of Possession (DPoP, RFC 9449). O DPoP vincula um token de acesso a uma chave que o cliente possui, para que um token vazado seja inútil sem a chave privada.

Para obter um token vinculado ao DPoP, envie um cabeçalho DPoP com um JWT de prova DPoP na solicitação de token:

POST /api/login/oauth/access_token
DPoP: <DPoP proof JWT>

O Casdoor vincula o token à chave pública da prova, pela impressão digital JWK (jkt), e retorna o token_type DPoP em vez de Bearer:

{
    "access_token": "eyJhb...",
    "token_type": "DPoP",
    "expires_in": 10080,
    "scope": "openid"
}

A solicitação de token de atualização aceita o mesmo cabeçalho DPoP. O Casdoor rejeita uma prova inválida com o erro invalid_dpop_proof. Um token de atualização emitido com DPoP também está vinculado à chave: atualizá-lo requer uma prova DPoP assinada com a mesma chave. Sem uma prova, ou com uma prova de outra chave, a atualização falha com invalid_dpop_proof. O Casdoor verifica a reivindicação htu de uma prova de atualização contra o endpoint de token, https://<casdoor-host>/api/login/oauth/access_token.

O documento de descoberta lista os algoritmos de assinatura que o Casdoor aceita para provas em dpop_signing_alg_values_supported:

{
    "dpop_signing_alg_values_supported": ["RS256", "RS512", "ES256", "ES384", "ES512", "PS256", "PS384", "PS512"]
}

A resposta da introspecção do token mostra a vinculação da chave na reivindicação cnf.jkt (RFC 9449, seção 8).

Verificar um token de acesso​

O Casdoor suporta introspecção de token (RFC 7662). Autentique a solicitação com autenticação básica HTTP, usando o ID do cliente como nome de usuário e o segredo do cliente como senha:

POST /api/login/oauth/introspect HTTP/1.1
Host: CASDOOR_HOST
Accept: application/json
Content-Type: application/x-www-form-urlencoded
Authorization: Basic Y2xpZW50X2lkOmNsaWVudF9zZWNyZXQ=

token=ACCESS_TOKEN&token_type_hint=access_token

Exemplo de resposta:

{
    "active": true,
    "client_id": "c58c...",
    "username": "admin",
    "token_type": "Bearer",
    "exp": 1647138242,
    "iat": 1646533442,
    "nbf": 1646533442,
    "sub": "7a6b4a8a-b731-48da-bc44-36ae27338817",
    "aud": [
        "c58c..."
    ],
    "iss": "http://localhost:8000"
}

Alternativamente, verifique a assinatura do token você mesmo com a chave pública do certificado da aplicação, ou com as chaves do endpoint JWKS. Os SDKs fazem isso em ParseJwtToken().

Usar um token de acesso​

Envie o token de acesso para chamar a API do Casdoor. Por exemplo, chame /api/userinfo, com GET ou POST, de uma das duas maneiras:

  • Com o cabeçalho Authorization: Authorization: Bearer <access-token>
  • Com um parâmetro de consulta: https://<casdoor-host>/api/userinfo?accessToken=<access-token>

O Casdoor retorna os campos do usuário que o escopo do token permite:

{
    "sub": "7a6b4a8a-b731-48da-bc44-36ae27338817",
    "iss": "http://localhost:8000",
    "aud": "c58c..."
}

Para obter mais campos, solicite mais escopos na solicitação de autorização.

UserInfo e get-account​

EndpointReturns
/api/userinfoThe standard OpenID Connect (OIDC) claims of the user, limited by the scopes of the token
/api/get-accountO objeto completo do usuário da conta conectada. Este endpoint é específico do Casdoor. Ele inclui o token de acesso do provedor OAuth externo, se houver

Obter o token de acesso de um provedor externo​

Quando um usuário faz login através de um provedor OAuth externo, como GitHub ou Google, o Casdoor armazena o token de acesso desse provedor no campo originalToken do usuário. Sua aplicação pode usá-lo para chamar a API do provedor, como a API do GitHub ou a API do Google Drive, em nome do usuário, sem outro fluxo OAuth.

Leia o token de /api/get-account:

{
  "status": "ok",
  "data": {
    "name": "user123",
    "originalToken": "ya29.a0AfH6SMBx...",
    ...
  }
}

O Casdoor retorna originalToken apenas para o usuário e para administradores. Para todos os outros solicitantes, ele oculta o campo.
