概要

ユーザープロパティ​

Casdoor はユーザーアカウントを管理します。各ユーザーには以下のプロパティがあります：

  • Owner: ユーザーを所有する組織
  • Name: ユーザーの一意なユーザー名（組織内で一意である必要があります）
  • CreatedTime: ユーザーアカウントが作成された時のタイムスタンプ
  • UpdatedTime: ユーザーアカウントが最後に更新された時のタイムスタンプ
  • Id: 各ユーザーの一意な識別子 (UUID)
  • Type: ユーザーアカウントの種類（例：normal-user, guest-user）
  • Password: ユーザーの暗号化されたパスワード
  • PasswordSalt: パスワードハッシュに使用されるソルト値
  • PasswordOptions: パスワードの複雑さに関するオプション
  • DisplayName: ユーザーインターフェースに表示されるユーザーの表示名
  • FirstName: ユーザーの名前（given name）
  • LastName: ユーザーの苗字（family name）
  • Avatar: ユーザーの現在のアバター画像への URL またはリンク
  • PermanentAvatar: ユーザーの永続的に保存されたアバターへの URL（プロバイダーの変更に影響されません）
  • Email: ユーザーのメールアドレス（自動的に小文字に正規化されます）
  • Phone: ユーザーの電話番号。国内番号として数字のみで保存されます。電話番号 を参照してください
  • CountryCode: 電話番号の地域、例えば PL や US など
  • Location: ユーザーの地理的な位置
  • Address: ユーザーの住所情報を含む文字列の配列（例：番地、都市、州、郵便番号）
  • Affiliation: ユーザーの所属組織または機関
  • Title: ユーザーの職業上の肩書きまたは職位
  • IdCardType: 本人確認に使用される ID カードの種類（例：パスポート、運転免許証）
  • IdCard: ID カード番号（検証後は読み取り専用になります）
  • RealName: ユーザーの検証済みの実名（本人確認後は読み取り専用になります）
  • IsVerified: ユーザーが ID Verification プロバイダーを通じて本人確認を完了したかどうかを示します
  • Homepage: ユーザーの個人ホームページまたはウェブサイトへの URL
  • Bio: ユーザーの短い経歴または説明
  • Tag: ユーザーを分類するためのタグ（カンマ区切りで複数指定可能）
  • Region: ユーザーの地理的な地域またはエリア
  • Language: インターフェースにおけるユーザーの優先言語
  • Gender: ユーザーの性別
  • Birthday: ユーザーの生年月日
  • Education: ユーザーの学歴または教育背景
  • Balance: ユーザーのアカウント残高（決済機能を備えたアプリケーション用）
  • Score: ユーザーに関連付けられた数値スコア（アプリケーション定義）
  • Karma: ユーザーのカルマまたは評判ポイント
  • Ranking: ユーザーのランキング順位（アプリケーション定義）
  • IsDefaultAvatar: ユーザーがデフォルトのアバターを使用しているかどうかを示します
  • IsOnline: ユーザーが現在オンラインであるかどうかを示します
  • IsAdmin: ユーザーが所属組織の管理者であるかどうかを示します
  • IsGlobalAdmin: ユーザーに Casdoor の管理権限があるかどうかを示します
  • IsForbidden: ユーザーアカウントが禁止または制限されているかどうかを示します。これを有効にすると、ユーザーのアクセスは直ちに終了します。ユーザーの禁止または削除を参照してください
  • IsDeleted: ユーザーがソフト削除された場合（IsDeleted = true）、OAuth プロバイダーを含むすべての認証方法でのサインインができなくなります。これにより、削除されたユーザーがサードパーティログイン経由で再登録することを防ぎます。
  • SignupApplication: ユーザーがサインアップしたアプリケーション
  • Hash: 内部認証メカニズムで使用されるハッシュ値
  • PreHash: 以前のハッシュ値（パスワード移行中に使用）
  • CreatedIp: ユーザーアカウントが作成された IP アドレス
  • LastSigninTime: ユーザーの最後の成功したサインインのタイムスタンプ（Last signin time）。最終サインイン時刻と IP アドレスを参照してください
  • LastSigninIp: ユーザーの最後の成功したサインインの IP アドレス（Last signin IP）
  • Roles: ユーザーのロールの配列（拡張フィールド、User API 経由では読み取り専用）
  • Permissions: ユーザーの権限の配列（拡張フィールド、User API 経由では読み取り専用）
  • OriginalRefreshToken: 最新のソーシャルログインからのリフレッシュトークン（レガシーな単一プロバイダーフィールド、後方互換性のために保持）。API レスポンスでは *** とマスクされます。
  • Properties["oauth_<ProviderType>_accessToken"] / Properties["oauth_<ProviderType>_refreshToken"]: Properties マップに格納されるプロバイダーごとの OAuth トークン。ユーザーが複数の OAuth プロバイダー経由でサインインする場合、各プロバイダーのトークンは独自キーの下に個別に保存されます（例: oauth_GitHub_accessToken）。両方のフィールドは API レスポンスでは *** とマスクされます。
  • Addresses: 構造化された住所エントリのリスト。各住所には Tag（Home, Work, Other）、Line 1、Line 2、City、State、Zip code、Region が含まれます。ユーザーはアカウントプロフィールページから住所を管理できます。

ソーシャルプラットフォームログイン用の一意の ID:

  • Github: GitHub OAuth ログインからのユーザーの一意の識別子
  • Google: Google OAuth ログインからのユーザーの一意の識別子
  • QQ: QQ OAuth ログインからのユーザーの一意の識別子
  • WeChat: WeChat OAuth ログインからのユーザーの一意の識別子
  • Facebook: Facebook OAuth ログインからのユーザーの一意の識別子
  • DingTalk: DingTalk OAuth ログインからのユーザーの一意の識別子
  • Weibo: Weibo OAuth ログインからのユーザーの一意の識別子
  • Gitee: Gitee OAuth ログインからのユーザーの一意の識別子
  • LinkedIn: LinkedIn OAuth ログインからのユーザーの一意の識別子
  • Wecom: WeCom (WeChat Work) OAuth ログインからのユーザーの一意の識別子
  • Lark: Lark (Feishu) OAuth ログインからのユーザーの一意の識別子
  • Gitlab: GitLab OAuth ログインからのユーザーの一意の識別子
  • Adfs: ADFS 認証からのユーザーの一意の識別子
  • Baidu: Baidu OAuth ログインによるユーザーの一意な識別子
  • Casdoor: 他の Casdoor インスタンスの OAuth ログインによるユーザーの一意な識別子
  • Infoflow: Infoflow OAuth ログインによるユーザーの一意な識別子
  • Apple: Apple OAuth ログインによるユーザーの一意な識別子

  • Azure AD B2C: Azure AD B2C OAuth ログインによるユーザーの一意な識別子
  • Slack: Slack OAuth ログインによるユーザーの一意な識別子
  • Steam: Steam OAuth ログインによるユーザーの一意な識別子
  • Ldap: LDAP 認証によるユーザーの一意な識別子
  • Telegram: Telegram OAuth ログインによるユーザーの一意な識別子

Organization 管理者権限​

Users with IsAdmin enabled are administrators of their organization:

  • 組織内のユーザー、アプリケーション、リソースを管理するための完全なアクセス権
  • 組織内のユーザーに送信された確認コードの記録へのアクセス権
  • 組織レベルの設定およびポリシーを構成する機能

組織管理者には昇格された権限がありますが、適用範囲はその組織内に限定されます。グローバル管理者（built-in 組織のユーザー）は、Casdoor インスタンス内のすべての組織に対する完全なアクセス権を持ちます。

User tags​

Tag フィールドはユーザーを分類します。単一のタグまたはカンマ区切りの複数のタグ（例: "developer,qa,reviewer"）を使用できます。アプリケーションアクセスチェックでは、各タグが個別に評価されます。

予約済みタグ値:

  • normal-user: 完全な認証機能を持つ標準ユーザー
  • guest-user: Temporary users created through guest authentication without initial credentials
    • 適切なユーザー名またはパスワードを設定すると、自動的に normal-user にアップグレードされます
    • アカウントをアップグレードするまで直接サインインできません

カスタムタグはアプリケーションアクセスを制限できます。Application Tags を参照してください。

本人確認​

Casdoor は ID Verification プロバイダーを通じて本人確認をサポートしています。ユーザーは身分証明書情報と実名を提出することで本人確認を行うことができ、Jumio などのサードパーティサービスによって検証されます。

ユーザーが本人確認を完了したとき:

  • IsVerified フィールドが true に設定されます
  • RealName、IdCardType、IdCard および関連する本人確認フィールドが読み取り専用になります
  • 確認済みステータスは JWT トークンおよび OIDC userinfo レスポンスに含まれます
  • ユーザーのプロフィールに確認バッジが表示されます

この機能は、KYC（顧客身元確認）コンプライアンスが必要なアプリケーションや、ユーザーの本人性の真正性を確保する必要があるアプリケーションに役立ちます。本人確認の構成に関する詳細については、ID Verification Providers を参照してください。

Email normalization​

Casdoor は重複アカウントを避け、一意性を保つために、すべてのメールアドレスを小文字に正規化します。つまり、user@example.com、User@Example.com、USER@EXAMPLE.COM は同じメールアドレスとして扱われ、RFC 5321 標準に準拠します。

この正規化は以下の場合に自動的に実行されます:

  • ユーザー登録およびアカウント作成時
  • ユーザーログインおよび認証時
  • メール重複チェック時

Phone numbers​

Casdoor は、ユーザー登録時、Casdoor 管理コンソールまたは POST /api/update-user 経由でユーザーが更新される際、および確認コードを使ってユーザーが電話番号を変更する際に、国番号とともに電話番号を解析・検証します。無効な番号は Phone number is invalid または電話番号変更時に Phone number is invalid in your region <country-code> というエラーで拒否されます。

Casdoor は電話番号を phone に数字のみで保存し、地域コードを countryCode に保存します。例えば、+48 666 666 666 は 666666666 と PL として保存されます。Casdoor が番号から地域コードを取得するのは、番号が + で始まる場合、または国コードが指定されていない場合のみです。複数の国で共有されている市外局番（例：+1）は、ユーザーが選択した国を上書きしません。

The check for Phone already exists compares the normalized values. At sign-in, Casdoor also looks up a national number in each of the Supported country codes of the organization.

最終サインイン時刻と IP アドレス​

Casdoor は /api/login を通じたすべての成功したサインイン後に lastSigninTime と lastSigninIp を更新します。これにはサインインページおよびソーシャルプロバイダーによるサインインが含まれます。

OAuth 2.0 パスワードグラント (grant_type=password) は lastSigninTime のみを更新し、lastSigninIp は変更しません。Casdoor はトークン生成後にこのサインインを記録するため、そのトークンの lastSigninTime および lastSigninIp クレームには以前のサインイン情報が保持されます。現在のサインイン時刻はトークンの iat クレームです。

ユーザーの禁止または削除​

更新操作により isForbidden または isDeleted（ソフト削除を伴う）が有効になると、Casdoor は直ちにユーザーのアクセスを終了します：

  1. ユーザーのトークンに対して OpenID Connect (OIDC) バックチャネルログアウトと SAML ログアウトを送信します。
  2. すべてのアプリケーションにおけるユーザーのすべてのトークンを有効期限切れにします。
  3. すべてのアプリケーションにおけるユーザーのすべてのセッションを削除します。
  4. SSO ログアウト通知を送信します。これらはベストエフォートです：通知送信時点でアクセスはすでに失効しています。

ユーザーの削除も同様の処理を行います。

その後、Casdoor は禁止、削除、または除去されたユーザーのすべてのトークンを非アクティブとして扱います：

  • /api/login/oauth/introspect は active: false を返します。
  • そのようなアクセストークンを用いた API 呼び出しは The user is forbidden to sign in, please contact the administrator エラーで失敗します。
  • Casdoor の MCP エンドポイントはトークンを拒否します。

client_credentials グラントのトークンはユーザーに紐付いておらず、アクティブなままです。

columns パラメータによる部分更新​

/api/update-user はオプションの columns クエリパラメータを受け付け、部分更新を実行します：列挙されたフィールドのみが書き込まれ、ユーザー上の他のすべてのフィールドは変更されません。これを省略する場合（または空のままにする場合）、ユーザーオブジェクト全体が更新されます。

columns 内のフィールド名は camelCase または snake_case のいずれかで記述できます。どちらも受け付けられ、同じ基盤カラムにマッピングされます。例えば、columns=displayName,avatar と columns=display_name,avatar は同等です。

update-user 経由でのパスワード設定​

管理者は POST /api/update-user を使用して、空でも *** でもない新しい password を送信することでユーザーのパスワードを設定できます。Casdoor は組織の Password type を用いてそれをハッシュ化します。パスワードを保存する前に、Casdoor は以下を確認します：

  • パスワードにスペースが含まれていないこと。
  • パスワードが組織の パスワード複雑性 要件を満たしていること。
  • パスワードが再利用されていないこと。詳細は パスワード履歴 を参照してください。

その後、Casdoor は旧パスワードをパスワード履歴に記録し、lastChangePasswordTime を設定します。また、columns にリストされていなくても、password、password_salt、password_type、および last_change_password_time カラムを書き込みます。

これは管理者のみ、および自分のアカウントに対する guest-user タグを持つユーザーのみが可能です。その他のユーザーからの要求、および LDAP ユーザーに対するすべての要求は Please use the set-password API to change the password エラーで失敗します。

すでにハッシュ化されたパスワードをインポートするには、columns に password と password_type を含め、password にハッシュを、passwordType にアルゴリズムを送信します。Casdoor はその後、ハッシュ化や検証を行わず、与えられた状態でパスワードを保存します。

ロールと権限（拡張フィールド）​

User オブジェクトの Roles および Permissions フィールドは拡張されています。これらはユーザーデータの取得時に充填され、User テーブルには保存されません。これらは Roles および Permissions リソースから ExtendUserWithRolesAndPermissions() を介して構築されます。

重要： /api/update-user（columns パラメータ経由を含む）を使用してロールや権限を変更することはできません。割り当てや管理には Roles および Permissions API とそれらの管理ページ（例えばサイドバーの Roles や Permissions）を使用してください。

Properties フィールドの使用​

Properties フィールドは、組み込みスキーマに含まれないカスタムユーザー属性のためのキーバリューマップ（map[string]string）です。これを使用して：

  • 組織固有のユーザー属性を保存します
  • 標準フィールドに収まらないカスタムメタデータを追加します
  • コアスキーマを変更せずにユーザープロファイルを拡張します

XLSX からのユーザーインポート​

XLSX ファイルをアップロードしてユーザーを追加または更新します。

はじめる​

管理コンソールの Users ページでは以下が表示されます：

  • Download template: すべての利用可能なユーザーフィールドとそのローカライズされたカラムヘッダーを含む XLSX テンプレートを生成します
  • Upload (.xlsx): XLSX ファイルからユーザーをインポートするためのアップロードダイアログを開きます

テンプレートファイルには、Display Name#field_name 形式（例：Organization#owner）のヘッダーが含まれます。ここで、表示名は言語に合わせてローカライズされ、# の後のフィールド名はインポート時のマッピングに使用されます。コメントプレフィックス（# より前の部分）は、インポート時に自動的に削除されます。

アップロードプロセス​

XLSX ファイルを選択すると、Casdoor はデータのプレビューを表示します。確認してインポートを開始してください。参照用に、5 人のテストユーザーを含む サンプルファイル (xlsx/user_test.xlsx) が利用可能です。

アップロード権限​

誰がアップロードできるかは、あなたのロールによって異なります：

  • Global admins（built-in 組織で IsGlobalAdmin が true に設定されているユーザー）は、任意の組織にユーザーをアップロードできます。対象組織は、XLSX ファイル内の Owner フィールドによって決定されます。
  • Organization admins（IsAdmin が true に設定されているユーザー）は、自分の組織にのみユーザーをアップロードできます。システムは、重複チェックとユーザー作成が正しい組織にスコープされることを保証します。

インポート時のパスワード暗号化のバイパス​

別のシステムからユーザーを移行する際、組織のデフォルトのパスワードタイプで再ハッシュするのではなく、既存のパスワードハッシュを保持する必要がある場合があります。ユーザーインポート中に passwordType フィールドを使用して、保存されているパスワードのフォーマットを Casdoor に通知します。

例：bcrypt パスワード

/api/add-user の POST ボディの例：

{
  "owner": "organization",
    "signupApplication": "first-app",
    "email":"dev@dev.com",
    "name": "dev",
    "displayName": "developper",
    "password": "$2a$10$.o/iVyDE9Xk8ioywHDnQRu72RviOi6FPa1ujhusbSCZeg7VOa6MY6",
    "passwordType":"bcrypt",
}

パスワードはすでに bcrypt でハッシュ化されているため、passwordType を "bcrypt" に設定し、Casdoor が再度ハッシュ化しないようにします。
