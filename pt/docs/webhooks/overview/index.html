Pontos de webhook

O Casdoor pode notificar sua aplicação quando eventos ocorrerem, enviando requisições HTTP POST com um payload JSON para uma URL que você configura. Use webhooks para reagir a cadastros, logins, logout, atualizações de perfil e muitos outros eventos.

Como os webhooks funcionam​

Quando um evento ocorre no Casdoor:

  1. O Casdoor envia uma requisição POST para a URL do webhook especificada.
  2. A requisição contém um payload JSON com detalhes do evento.
  3. Sua aplicação processa o payload e executa ações relevantes baseadas no tipo de evento.

Eventos suportados​

Os webhooks podem se inscrever em um amplo conjunto de eventos, agrupados por área:

Eventos de Autenticação & Sessão​

  • signup, login, logout - Fluxos de autenticação de usuário
  • sso-logout, unlink - Single sign-on e desvinculação de conta
  • new-user - Evento personalizado para criação de novo usuário
  • new-user-ldap - Evento personalizado disparado quando um novo usuário é criado através de uma sincronização LDAP
  • new-user-syncer - Evento personalizado disparado quando um novo usuário é criado através de um syncer de banco de dados

logout e sso-logout são disparados também para requisições GET, por exemplo, quando uma relying party OpenID Connect (OIDC) envia o navegador para GET /api/logout para logout iniciado pela RP. O Casdoor registra essas duas ações mesmo quando logPostOnly no arquivo de configuração é true, que normalmente ignora todas as requisições GET. Sem um cookie de sessão, o registro obtém seu usuário e organização do assunto de id_token_hint.

Eventos de Gerenciamento de Recursos​

Operações CRUD padrão (add-*, update-*, delete-*) estão disponíveis para todos os recursos principais, incluindo organizações, grupos, usuários, aplicações, provedores e certificados. Recursos adicionais como roles, permissions, models, adapters, enforcers, sessions, tokens, products, payments e pricing também suportam essas operações. Webhooks podem rastrear alterações em syncers, forms, invitations, configurações de LDAP, orders, tickets e transactions também.

Operações Especializadas​

User Management: add-user-keys, remove-user-from-group, upload-users, check-user-password, set-password, reset-email-or-phone, verify-identification

Bulk Operations: upload-groups, upload-roles, upload-permissions, upload-resource

Order Processing: place-order, cancel-order, pay-order

Payment Handling: invoice-payment, notify-payment

Invitations: send-invitation, verify-invitation

Support Systems: add-ticket-message

Synchronization: run-syncer, test-syncer-db, sync-ldap-users

Access Control: enforce, batch-enforce, add-policy, update-policy, remove-policy, add-record

Multi-Factor Authentication: delete-mfa, set-preferred-mfa, mfa/setup/initiate, mfa/setup/verify, mfa/setup/enable

WebAuthn: webauthn/signup/begin, webauthn/signup/finish, webauthn/signin/begin, webauthn/signin/finish

OAuth & Token Management: login/oauth/access_token, login/oauth/refresh_token, login/oauth/introspect

Verification & Communication: send-verification-code, verify-code, verify-captcha, send-email, send-sms, send-notification

SAML: acs, saml/metadata

System Operations: health, metrics, callback, device-auth, faceid-signin-begin, user, userinfo

Cada evento inclui informações contextuais no payload do webhook, permitindo implementar lógica personalizada baseada na ação específica que disparou o webhook.

Configurando um webhook​

  1. No console de administração do Casdoor, vá para Admin > Webhooks.
  2. Clique em Add.
  3. Selecione a Organization que possui o webhook.
  4. Em URL, insira o endereço que recebe os eventos.
  5. Em Events, selecione um ou mais eventos.
  6. Opcional: em Headers, adicione cabeçalhos personalizados, por exemplo, para autenticação.
  7. Defina Single org only, veja Eventos de outras organizações.
  8. Ative Is enabled e salve. A partir de então, o Casdoor enviará os eventos para a URL.

Um administrador de uma organização pode adicionar webhooks apenas à sua própria organização. Para qualquer outra organização, POST /api/add-webhook retorna "Unauthorized operation".

Eventos de outras organizações​

Single org only (singleOrgOnly) decide quais registros disparam o webhook:

  • On: Apenas os registros da organização que possui o webhook o disparam.
  • Off: Os registros de todas as organizações o disparam.

Apenas um administrador global, isto é, um usuário da organização built-in, pode desativar Single org only. Quando qualquer outra pessoa adiciona ou atualiza um webhook, o Casdoor salva-o com Single org only ativado.

Endereços aos quais um webhook pode acessar​

Os webhooks de todas as organizações, exceto built-in, só podem enviar requisições para endereços da Internet. O Casdoor recusa conexões com endereços privados, de loopback, link-local e não especificados, bem como com o espaço de endereçamento compartilhado 100.64.0.0/10. A faixa link-local inclui o endereço de metadados da nuvem 169.254.169.254. O Casdoor verifica o endereço IP resolvido de cada conexão, portanto, nomes de host que resolvem para endereços de intranet, DNS rebinding e redirecionamentos para endereços de intranet também são recusados. Esses webhooks não usam o proxy configurado para o Casdoor.

O erro de uma entrega recusada contém the address: <address> is not allowed, only Internet addresses can be requested.

Somente os webhooks da organização built-in, gerenciados apenas por administradores globais, podem acessar hosts na intranet. Para enviar os eventos de outra organização para um serviço em sua própria rede, um administrador global cria o webhook na organização built-in e desativa Single org only.

Filtrando payloads de webhook​

Ao trabalhar com webhooks, nem sempre você precisa dos dados completos do registro. O Casdoor permite filtrar o payload configurando ObjectFields para cada webhook. Esse recurso é particularmente valioso quando há preocupações com privacidade, restrições de largura de banda ou quando seu endpoint processa apenas campos específicos.

A configuração ObjectFields aceita "All" para receber o registro completo, ou uma lista de nomes de campos específicos que você deseja incluir. Quando você especifica nomes de campos, o Casdoor enviará apenas esses campos no payload do webhook, reduzindo o tamanho do payload e expondo apenas os dados necessários para sua aplicação.

Se você configurar vários webhooks com diferentes configurações de ObjectFields, cada webhook opera independentemente. Por exemplo, um webhook pode receber apenas IDs de usuário e timestamps, enquanto outro recebe perfis completos de usuários. O Casdoor garante que a filtragem aplicada a um webhook não afete os dados enviados aos outros, mesmo quando são acionados pelo mesmo evento.

Exemplo de payload​

Exemplo de JSON enviado ao seu webhook durante o login:

{
  "event": "login",
  "timestamp": 1709452800,
  "user": {
    "id": "12345",
    "username": "johndoe",
    "email": "johndoe@example.com"
  }
}

Sua aplicação deve analisar esse payload e executar as ações necessárias, como registrar o evento ou notificar outro serviço.

Classificação de falhas de login​

Cada tentativa de login é armazenada como um registro (visível em Records no console de administração e entregue com o payload do webhook). Quando um login falha, o Casdoor preenche o campo detail do registro com um motivo estável e legível por máquina, permitindo que você classifique falhas sem analisar mensagens de erro localizadas.

Os motivos possíveis são:

detalhesMeaning
user-not-foundNo matching user for the supplied identifier.
account-disabledThe user account is disabled (forbidden).
account-frozenThe user account is frozen/locked.
wrong-passwordThe password did not match.
password-expiredThe password has expired and must be reset.
mfa-failedMulti-factor authentication verification failed.

Logins bem-sucedidos deixam detail vazio. Use esses valores para criar dashboards de auditoria, alertas (por exemplo, picos em wrong-password) ou lógica de bloqueio baseada em um motivo específico de falha.

Testando webhooks​

Antes da produção, teste com:

  • Beeceptor – Permite criar uma URL de webhook personalizada e inspecionar solicitações recebidas.
  • Webhook.site – Fornece um endpoint de webhook instantâneo para testes.

Exemplo com Beeceptor​

  1. Crie um endpoint no Beeceptor.
  2. Copie a URL e defina-a como a URL do webhook no Casdoor.
  3. Acione um evento (por exemplo, faça login no Casdoor).
  4. Inspecione a solicitação no dashboard do Beeceptor.

Tratamento de webhooks na sua aplicação​

Seu servidor deve ser capaz de processar solicitações de webhook recebidas. Abaixo está um exemplo simples em Node.js:

const express = require('express');
const app = express();

app.use(express.json());

app.post('/webhook', (req, res) => {
  console.log('Received webhook:', req.body);
  res.status(200).send('Webhook received');
});

app.listen(3000, () => console.log('Server running on port 3000'));

Valide as solicitações de webhook recebidas (por exemplo, assinaturas ou segredos compartilhados) e teste com Beeceptor ou Webhook.site antes de usar webhooks em produção.

Rastreamento de entrega e nova tentativa​

O Casdoor persiste cada tentativa de entrega de webhook como um registro Webhook Event. Navegue até Webhook Events na barra lateral para ver o histórico de entregas de todos os webhooks da sua organização.

Cada registro de evento inclui:

CampoDescrição
Estadopending, success, failed, or retrying
Contagem de tentativasHow many delivery attempts have been made
Last status codeHTTP response code from the most recent attempt
Last response / errorResponse body or error message from the most recent attempt
Próxima hora de nova tentativaWhen the next automatic retry will occur (if applicable)

Nova tentativa automática​

Entregas com falha são tentadas novamente automaticamente por um worker em segundo plano que executa a cada 30 segundos. O número máximo padrão de novas tentativas por evento é 3. Depois que todas as tentativas são esgotadas, o status do evento é definido como failed e nenhuma outra tentativa é feita automaticamente.

Repetição manual​

Para reenviar um evento, abra-o na lista Webhook Events e clique em Replay. Isso cria uma nova tentativa de entrega, independentemente da contagem atual de novas tentativas ou do status. Use isso para recuperar-se de indisponibilidades temporárias do endpoint ou para reprocessar um evento após corrigir um bug no seu handler.
