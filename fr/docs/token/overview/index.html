Aperçu

Casdoor est basé sur OAuth et utilise des jetons pour l'authentification et l'autorisation des utilisateurs.

Jeton d'accès et jeton d'identifiant​

Une connexion retourne deux JSON Web Tokens (JWT) différents :

  • Le jeton d'accès sert à appeler les API. Sa claim tokenType est access-token.
  • Le jeton d'identifiant indique à votre application qui s'est connecté. Sa claim tokenType est id-token.

Les deux jetons portent les mêmes claims utilisateurs, dans le même Token format, et sont signés avec la même clé. Ils diffèrent par ces claims :

ClaimAccess tokenID token
tokenTypeaccess-tokenid-token
jtiIts own IDIts own ID
audThe client ID, or the resource of RFC 8707, or the audience of a token exchangeAlways the client ID
at_hash, c_hashNot presentPresent in the cases that OpenID Connect defines

Pour une application partagée, l'aud des deux jetons est <client-id>-org-<organization>, l'ID client de l'application pour l'organisation de l'utilisateur. Comme les deux jetons sont séparés, l'un ne peut pas remplacer l'autre, conformément à la section 3.12 de la RFC 8725. Envoyez le jeton d'accès aux API et utilisez le jeton d'identifiant uniquement pour lire l'identité de l'utilisateur.

Le point de terminaison /api/login retourne le jeton d'identifiant dans le champ data3 de sa réponse.

Champs du jeton​

Casdoor stocke chaque jeton émis sous forme d'enregistrement avec ces champs :

ChampDescription
owner, nameThe ID of the token record
createdTimeWhen Casdoor issued the token
applicationThe application that the token was issued to
organization, userThe user of the token
codeThe authorization code that the token was issued for
accessToken, refreshToken, idTokenLes trois jetons. Casdoor stocke également un hash de chacun d'eux, dans accessTokenHash, refreshTokenHash et idTokenHash
expiresInThe lifetime of the access token, in seconds. 0 means that Casdoor has revoked the token
scopeThe granted scope
tokenTypeBearer, or DPoP for a token bound with DPoP
grantTypeThe grant that issued the token, when it matters for refreshing
resourceThe resource or the token exchange audience that the token is bound to
sessionIdThe Casdoor browser session in which the user signed in, if any

Cycle de vie des jetons et invalidation​

Lorsqu'un utilisateur se connecte, Casdoor émet un jeton d'accès et un jeton de rafraîchissement. Le jeton d'accès est utilisé pour l'authentification API ; le jeton de rafraîchissement est utilisé pour obtenir de nouveaux jetons d'accès sans ré-authentification.

Pour révoquer un jeton, Casdoor définit son expiresIn à 0. Le point d'accès d'introspection du jeton renvoie alors "active": false, et le point d'accès de rafraîchissement rejette le jeton de rafraîchissement avec invalid_grant et refresh token is expired.

Quand Casdoor révoque des jetons​

EventTokens that Casdoor revokes
The user signs out with SSO logout and logoutAll=trueAll tokens of the user
The user signs out of one session, or an administrator ends a session on the Sessions pageThe tokens that were issued in that session
The user's password is changed through /api/set-password, by the user, by an administrator, or with the forgot-password flowAll tokens of the user, in all applications. Applications must sign the user in again
A new sign-in to an application with Enable exclusive signin on and Max sessions at most 1The earlier tokens of the user for that application. See Exclusive sign-in
The user is forbidden to sign in, or deletedAll tokens of the user
RP-initiated logout with id_token_hintThe token of the hint

Les jetons émis sans session navigateur, tels que les jetons du type d'autorisation client credentials, ne sont pas affectés par la fin d'une session. Une session Casdoor créée à partir d'un jeton d'accès prend fin lorsque ce jeton est révoqué ou expiré.

Nettoyage automatique des jetons expirés​

Casdoor supprime automatiquement les enregistrements de jetons expirés depuis un certain temps, afin que la table token ne croisse pas indéfiniment. Un jeton est supprimé une fois qu'il a été expiré pendant une durée supérieure à la période de rétention de son organisation, comptée à partir du temps d'expiration propre au jeton.

Définissez la période de rétention dans Token retention days sur l'onglet Advanced de l'organisation. Une valeur vide ou 0 signifie la valeur par défaut de 30 jours. Les jetons des organisations qui n'existent plus utilisent 30 jours.

Le processus de nettoyage s'exécute :

  • une fois au démarrage, en arrière-plan, afin de ne pas retarder le démarrage du serveur
  • quotidiennement à minuit, heure du serveur

Le nettoyage supprime jusqu'à 1 000 jetons par lot, et n'affecte que les jetons déjà expirés dépassant la période de rétention. Les jetons actifs ne sont jamais touchés.

Options de format de jeton​

Lors de l'émission de JWTs, choisissez parmi quatre formats :

  • JWT
  • JWT-Empty
  • JWT-Custom
  • JWT-Standard

Les options de format de jeton fonctionnent comme suit :

  • JWT : inclut tous les champs User dans la charge utile du jeton
  • JWT-Empty : inclut uniquement les champs User non vides
  • JWT-Custom : inclut les champs Token User personnalisés sélectionnés (choisissez les attributs dans Token fields)
  • JWT-Standard : inclut les claims OIDC standard (email, phone, gender, address) au format conforme à OIDC

Définissez le format dans Token format sur l'onglet OIDC/OAuth de l'application. Une valeur vide signifie JWT. Une nouvelle application reçoit le Default token format de son organisation, et les Default token fields de son organisation comme ses Token fields, depuis l'onglet Advanced de l'organisation. La modification de ces valeurs par défaut ne change pas les applications existantes. Les applications créées par les clients via l'enregistrement dynamique des clients reçoivent les mêmes valeurs par défaut.

info

Seul JWT-Standard produit un claim address conforme à OIDC. Dans les formats JWT, JWT-Empty et JWT-Custom, le champ address est inclus sous forme de tableau brut []string (la propriété Address de l'utilisateur), ce qui ne se conforme pas à la spécification OIDC. Si votre application analyse le claim address comme un objet, utilisez le format de jeton JWT-Standard.

Format de groupe​

Token group format sur l'onglet OIDC/OAuth de l'application décide comment le claim groups nomme les groupes de l'utilisateur, dans tous les formats de jeton et dans la réponse de /api/userinfo :

OptionValue in groups
ID (org/group)<organization>/<group>. This is the default
Path (org/parent/group)Le chemin complet du groupe depuis son groupe racine, tel que <organization>/<parent-group>/<group>
Name (group)<group>

Path (org/parent/group) remplace l'option useGroupPathInToken de conf/app.conf, qui n'existe plus.

Restriction des champs avec Token fields​

Le paramètre Token fields sur l'application (utilisé pour choisir les attributs utilisateurs personnalisés pour le format JWT-Custom) agit également comme une liste blanche pour le point d'accès /userinfo.

  • Lorsque Token fields est vide, aucune liste blanche n'est appliquée : la charge utile du jeton et la réponse /userinfo incluent leur ensemble complet de champs par défaut. C'est le comportement par défaut.
  • Lorsque Token fields liste un ou plusieurs champs, seuls ces champs sont renvoyés. Tout attribut utilisateur non présent dans la liste est omis de la fois la charge utile du jeton JWT-Custom et la réponse /userinfo.

La liste blanche est comparée aux noms des propriétés utilisateur sous-jacentes. Par exemple, pour exposer le nom d'affichage, l'email et l'avatar via /userinfo, ajoutez Name, Email et Avatar à Token fields. Les champs respectent toujours les scopes OAuth demandés — par exemple Email n'est renvoyé que si le scope email est accordé, Location (le claim address) uniquement avec le scope address, et Phone uniquement avec le scope phone. Les claims sub et aud sont toujours renvoyés indépendamment de la liste blanche.

prudence

La configuration de Token fields restreint /userinfo, pas seulement le jeton. Si vous dépendiez auparavant de /userinfo pour renvoyer tous les champs, l'ajout d'entrées ici commencera à filtrer cette réponse. Laissez Token fields vide pour conserver la réponse complète.

Claim Adresse OIDC​

La spécification OIDC définit le claim address comme un objet JSON comportant les champs suivants :

FieldDescription
formattedFull mailing address, formatted for display
street_addressComposante de l'adresse postale (peut inclure le numéro de maison, le nom de rue, la boîte postale, etc.)
localityCity or locality
régionState, province, prefecture, or region
postal_codeZip code or postal code
countryCountry name

Comment Casdoor mappe les données utilisateur vers le claim adresse​

Casdoor stocke les informations d'adresse dans deux champs utilisateur distincts :

  • Location (string) : Une chaîne de caractères indiquant une localisation générale (par exemple, "New York"). Ce champ est utilisé comme valeur address en chaîne simple renvoyée par le point d'accès /api/userinfo lorsque la portée address est demandée.
  • Address (tableau de chaînes) : Un tableau de chaînes représentant les lignes d'adresse (par exemple, ["123 Main St", "Anytown, NY 12345", "USA"]). Ce champ est la source de la réclamation address conforme à OIDC dans les jetons JWT-Standard.

Réclamation d'adresse JWT-Standard​

Lorsque la portée address est demandée et que le format JWT-Standard est utilisé, Casdoor renvoie l'objet suivant dans le jeton :

{
  "address": {
    "street_address": "123 Main St\nAnytown, NY 12345\nUSA",
    "formatted": "",
    "locality": "",
    "region": "",
    "postal_code": "",
    "country": ""
  }
}

Le champ street_address contient les entrées du tableau Address de l'utilisateur jointes par des sauts de ligne. Les autres sous-champs d'adresse conformes à OIDC (formatted, locality, region, postal_code, country) sont actuellement vides car Casdoor stocke l'adresse entière sous forme de lignes libres dans le tableau Address plutôt que dans des champs par composante.

Formats non standard (JWT, JWT-Empty, JWT-Custom)​

Dans les formats de jetons JWT, JWT-Empty et JWT-Custom, le champ address est la propriété brute Address de l'objet utilisateur — un tableau JSON de chaînes — et non un objet d'adresse OIDC :

{
  "address": ["123 Main St", "Anytown, NY 12345", "USA"]
}

Les clients OIDC qui s'attendent à ce que la réclamation address soit un objet JSON (selon la spécification OIDC) échoueront lors de l'analyse de cette structure. Passez au format JWT-Standard si vous avez besoin d'une réclamation address conforme à la spécification dans le jeton.

Réclamations OIDC standard​

Tous les formats de jetons JWT incluent ces réclamations OpenID Connect standard dans la charge utile :

  • sub - Identifiant du sujet (ID utilisateur unique)
  • email - Adresse e-mail de l'utilisateur
  • email_verified - Booléen indiquant si l'adresse e-mail est vérifiée : l'utilisateur l'a confirmée avec un code ou un lien magique de Casdoor, ou le fournisseur OAuth qui a créé l'utilisateur l'a attestée
  • name ou preferred_username - Nom d'affichage de l'utilisateur
  • picture ou avatar - URL de l'avatar de l'utilisateur

La réclamation email_verified permet aux applications externes utilisant Casdoor comme fournisseur d'identité de déterminer directement le statut de vérification de l'e-mail à partir du jeton, sans appels API supplémentaires.

Lorsqu'un utilisateur s'inscrit via un fournisseur OAuth, Casdoor récupère le statut de vérification de l'adresse e-mail auprès du fournisseur. Par exemple, Google l'indique dans sa réclamation email_verified, et un fournisseur OAuth personnalisé peut mapper un champ emailVerified. Des fournisseurs tels que GitHub, GitLab, Gitee, Facebook, LinkedIn, DingTalk, Lark et Twitter considèrent toutes les adresses e-mail qu'ils renvoient comme vérifiées.

Le format JWT contient également les champs lastSigninTime et lastSigninIp de l'utilisateur. Dans un jeton issu d'une autorisation par mot de passe, ils décrivent la connexion précédente, car Casdoor enregistre la connexion après avoir émis le jeton. L'heure de la connexion actuelle correspond à la réclamation iat.

Attributs de jeton personnalisés​

Avec le format JWT-Custom, définissez des attributs personnalisés et leurs types de données. Chaque attribut possède un champ Type qui contrôle la manière dont les valeurs sont incluses dans le JWT :

  • Array : La valeur de l'attribut sera toujours renvoyée sous forme de tableau, même si elle ne contient qu'un seul élément. Cela garantit la compatibilité avec les clients OIDC qui attendent des types tableaux pour des champs tels que les rôles, les groupes ou les permissions.
  • String : La valeur de l'attribut sera renvoyée sous forme de chaîne unique (le premier élément si plusieurs valeurs existent).

Les attributs vides sont automatiquement omis du jeton pour garder la charge utile propre. Lors de la configuration d'attributs pour les rôles, les groupes ou les permissions, il est recommandé d'utiliser le type Array pour une meilleure conformité OIDC et une compatibilité accrue avec des systèmes tels que Rancher et Keycloak.
