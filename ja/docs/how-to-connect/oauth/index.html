OAuth 2.0

Casdoor は OAuth 2.0 認可サーバーです。このページでは、各グラントタイプでアクセストークンを取得する方法、トークンを検証する方法、およびそれを使用する方法について説明します。エンドポイントを直接呼び出したくない場合は、Casdoor SDK または 標準 OIDC クライアント を使用してください。

エンドポイント​

EndpointURL
Authorizationhttps://<casdoor-host>/login/oauth/authorize
Tokenhttps://<casdoor-host>/api/login/oauth/access_token
Refresh tokenhttps://<casdoor-host>/api/login/oauth/refresh_token
Token introspectionhttps://<casdoor-host>/api/login/oauth/introspect
UserInfohttps://<casdoor-host>/api/userinfo

例では、ClientId と ClientSecret は、Casdoor アプリケーション の Client ID と Client secret です。

サポートされているグラントタイプ​

Grant TypeRFCUse Case
Authorization CodeRFC 6749 §4.1Default; web/mobile apps with a backend. Enabled by default.
ImplicitRFC 6749 §4.2Frontend-only apps without a backend.
Resource Owner PasswordRFC 6749 §4.3Apps with no frontend redirect; user credentials sent directly.
Client CredentialsRFC 6749 §4.4Service-to-service calls with no user involved.
リフレッシュトークンRFC 6749 §6Renew an access token without re-authenticating.
Device AuthorizationRFC 8628Devices with limited input or no browser.
Token ExchangeRFC 8693Swap an existing token for one with different scope or audience.
JWT BearerRFC 7523Service auth using a signed JWT assertion instead of a client secret.
Verification CodeCasdoor extensionNative apps that sign users in (and up) with a code sent by SMS or email.
モバイルワンクリックログインCasdoor 拡張機能Alibaba Cloud PNVS を通じて、デバイスの電話番号でユーザーをサインイン（およびサインアップ）するネイティブアプリ。

認可コードグラントはデフォルトで有効になっています。他のグラントタイプは、アプリケーションの編集ページの Grant types で有効にしてください。

認可コードグラント​

ブラウザを通じてユーザーをサインインするアプリケーションには、このグラントを使用します。推奨されるグラントです。

  1. ユーザーを認可エンドポイントにリダイレクトします:

    https://<CASDOOR_HOST>/login/oauth/authorize?
    client_id=CLIENT_ID&
    redirect_uri=REDIRECT_URI&
    response_type=code&
    scope=openid&
    state=STATE

  2. ユーザーがサインインします。Casdoor はブラウザを、認可コード付きでリダイレクト URL にリダイレクトします:

    https://REDIRECT_URI?code=CODE&state=STATE&iss=ISSUER

    iss is the issuer URL of Casdoor, as defined by RFC 9207. Compare it with the issuer of the discovery document to make sure that the response comes from the Casdoor server that you sent the user to. Casdoor adds iss to every authorization response and to every error that it sends back to the redirect URL, and the discovery document announces this with "authorization_response_iss_parameter_supported": true.

  3. コードをトークンと交換します。トークンエンドポイントに POST リクエストを送信してください:

    https://<CASDOOR_HOST>/api/login/oauth/access_token

    ボディは次のとおりです:

    {
        "grant_type": "authorization_code",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "code": Code,
    }

  4. レスポンスからトークンを読み取ります:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

認可コードは有効期限が5分で、一度しか使用できません。同じコードを再度交換しようとすると、invalid_grant と説明 authorization code has been used for token: [...] で失敗します。

トークンエンドポイントおよびリフレッシュトークンエンドポイントのレスポンスにはヘッダー Cache-Control: no-store と Pragma: no-cache が含まれており、キャッシュにトークンが保持されないようにしています。

スコープ​

認可URLの scope パラメーターでスコープを要求します。これにより、トークンと UserInfo エンドポイント が返すユーザーフィールドが決まります。

スコープ説明
openid (default)sub, iss, aud
profilename, displayName, avatar
emailemail
addressaddress (OIDC object in JWT-Standard; see OIDC address claim)
phone電話番号

複数のスコープは %20 で区切ります:

https://<CASDOOR_HOST>/login/oauth/authorize?
client_id=...&
scope=openid%20email

各スコープに対応するクレームについては、OpenID Connect仕様 を参照してください。

PKCE​

Casdoorは、モバイルやシングルページアプリケーションなどの公開クライアントの認可コードを保護する Proof Key for Code Exchange (PKCE) をサポートしています。

  1. 43文字から128文字のランダムなコードベリファイアを生成します。

  2. コードチャレンジを計算します。これはベリファイアのBase64URLエンコードされたSHA-256ハッシュです。

  3. 認可URLに2つのパラメーターを追加します:

    &code_challenge_method=S256&code_challenge=YOUR_CHALLENGE

  4. 元のベリファイアを含む code_verifier パラメーターをトークンリクエストに追加します。

PKCEを使用する場合、トークンリクエストでの client_secret はオプションです。送信する場合は、正しい値である必要があります。

注

Casdoor自体が、TwitterやPKCEが有効なカスタムプロバイダーなど、PKCEを必要とする外部OAuthプロバイダーでユーザーをサインインさせる場合、Casdoorはフローごとにコードベリファイアを生成します。この部分についてPKCEを実装する必要はありません。

トークンを1つのサービスにバインドする​

アプリケーションが複数のバックエンドサービスを呼び出す場合、トークンをそのうちの1つにバインドして、あるサービス向けに発行されたトークンを別のサービスで使用できないようにすることができます。Casdoorはこれのために Resource Indicators (RFC 8707) をサポートしています。

  1. サービスを識別する絶対URIを含む resource パラメーターを認可URLに追加します:

    https://<CASDOOR_HOST>/login/oauth/authorize?
    client_id=CLIENT_ID&
    redirect_uri=REDIRECT_URI&
    response_type=code&
    scope=openid&
    state=STATE&
    resource=https://api.example.com

  2. 同じ resource をトークンリクエストにも送信します:

    {
        "grant_type": "authorization_code",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "code": Code,
        "resource": "https://api.example.com"
    }

アクセストークンの aud (audience) クレームは、クライアントIDではなくリソースURIになります。サービスは aud を確認することで、トークンが自分用に発行されたことを検証します。両方のリクエストにおける resource の値は完全に一致している必要があります。

Casdoorはインタラクティブなサインインを通じて resource パラメーターを引き継ぎます。ユーザーがパスワードを入力したり、多要素認証 (MFA) を完了したり、WebAuthnを使用したり、同意ページを承認したりする必要がある場合でも、リダイレクトを経由してパラメーターは維持されます。既存のセッションを使用してCasdoorが自動的にユーザーをサインインさせる場合も同様に保持されます。

トークンをリフレッシュすると、新しいアクセストークンは元のグラントの aud を維持します。リフレッシュリクエストでは、クエリパラメーターまたはボディのフィールドとして resource を繰り返すことができます。行う場合、元のグラントと同じ値である必要があります。それ以外の場合、Casdoorは説明 resource parameter does not match the original grant で invalid_grant を返します。

プロバイダーヒントでサインインページをスキップする​

Casdoorのサインインページを表示せずに、ユーザーを特定のOAuthプロバイダーへ直接送るには、認可URLに provider_hint=<provider-name> を追加します:

https://<CASDOOR_HOST>/login/oauth/authorize?
client_id=CLIENT_ID&
redirect_uri=REDIRECT_URI&
response_type=code&
scope=openid&
state=STATE&
provider_hint=github

その後、Casdoorは完全なフロントエンドを読み込まずに小さなリダイレクトページを提供し、ユーザーをプロバイダーへ送ります。これにより、低速なデバイスや接続環境でのリダイレクトまでの時間が短縮されます。

認可フロー中のサインアップ​

認可フロー中にアカウントを作成したユーザーは、サインアップ完了後、サインイン後と同様に、認可コード付きでリダイレクトURLへリダイレクトされます。Casdoorは client_id、response_type、redirect_uri などの認可パラメーターをサインアップ経由で引き継ぎます。アプリケーション側で変更を行う必要はありません。

サインインプロンプトの制御​

デフォルトでは、既にCasdoorセッションを持つユーザーは、資格情報を再入力せずにサインインできます。これを変更するには、OpenID Connectパラメーター prompt と max_age を認可URLに追加します:

ParameterEffect
prompt=loginThe user must enter credentials again, even with an existing session
max_age=<seconds>ユーザーが最後に資格情報を入力してから <seconds> 秒以上経過している場合、またはCasdoorが最終入力を認識していない場合、ユーザーは資格情報を再入力する必要があります
prompt=noneCasdoor shows no page. It signs the user in with the existing session, or sends an error back to the redirect URL

prompt はスペース区切りの値のリストを受け取ります。既存のセッションが prompt=login または max_age を満たさない場合、そのセッションでのサインインは login_required とメッセージ Please sign in again で失敗します。ユーザーが資格情報を入力した時刻は、IDトークンの auth_time クレームに含まれています。

例えば非表示のiframeから、ユーザーがまだサインインしているかを確認するために prompt=none を使用します。Casdoorは単一プロバイダーへの自動リダイレクトをスキップし、成功時の応答と同様の方法で、state と iss、そしてこれらのエラーのうちいずれかを返します:

ErrorReason
login_requiredNo Casdoor session, the user of the session isn't in the organization of the application, or the session doesn't satisfy max_age
consent_requiredThe user must approve the consent page first
interaction_requiredThe user must update the password, set up or complete MFA, select a plan, or fill in the prompt page first
access_deniedThe sign-in failed for another reason. error_description says why
server_errorThe request to Casdoor failed

Implicit Grant​

このグラントはバックエンドを持たないアプリケーションでのみ使用してください。PKCE付きの認可コードグラントを優先してください。

  1. アプリケーションの Grant types で、アクセストークンを返すために Token を、IDトークンを返すために ID Token を、または両方をオンにします。

  2. ユーザーを以下へリダイレクトします:

    https://<CASDOOR_HOST>/login/oauth/authorize?client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&response_type=token&scope=openid&state=STATE

  3. ユーザーがサインインした後、Casdoorはブラウザを以下へリダイレクトします:

    https://REDIRECT_URI#access_token=ACCESS_TOKEN&token_type=Bearer&state=STATE&iss=ISSUER

response_type は token、id_token、または id_token token にできます。認可エンドポイントは決してリフレッシュトークンを返しません。必要なレスポンスタイプに対応するグラントタイプがオンになっていない場合、Casdoorは Grant_type: token is not supported in this application (または id_token) を表示します。

scope に openid が含まれ、かつレスポンスに ID トークンが含まれる場合、nonce パラメータを送信してください。Casdoor はこれを ID トークンにコピーし、このパラメータがない場合はリクエストを拒否します: The nonce parameter is required for this response type.

注意

トークンエンドポイントでのインプリシットグラント（ユーザー名とパスワードを含む grant_type=token）には、ローカルパスワードを持つユーザーが必要です。外部プロバイダー経由でのみ作成され、ローカルパスワードを持たないユーザーはこれを使用できず、invalid_grant を受け取ります。パスワードグラントと同じルールが適用されます。これらのユーザーには認可コードグラントを使用してください。

ハイブリッドフロー​

OpenID Connect のハイブリッドフローでは、認可エンドポイントは認可コードとトークンを同時に返します。フロントエンドはすぐにトークンを使用でき、バックエンドは認可コードグラントと同様にコードを交換します。

response_type は、code、token、id_token のスペース区切りの組み合わせです。ハイブリッド値は次のとおりです:

response_typeThe authorization endpoint returns
code id_tokencode and id_token
code tokencode and access_token
code token id_tokencode, access_token, および id_token

  1. アプリケーションの Grant types で、token を含むレスポンスタイプに対して Token をオンにし、id_token を含むものに対して ID Token をオンにしてください。

  2. レスポンスタイプと nonce を指定して、ユーザーを認可エンドポイントにリダイレクトします:

    https://<CASDOOR_HOST>/login/oauth/authorize?client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&response_type=code%20id_token&scope=openid&state=STATE&nonce=NONCE

    scope に openid が含まれ、かつレスポンスタイプに id_token が含まれる場合、または code token の場合、nonce は必須です。

  3. ユーザーがサインインした後、Casdoor はブラウザをリダイレクト URL へリダイレクトします。別のレスポンモードを指定しない限り、値はフラグメントに含まれます。

  4. トークンエンドポイントでコードを交換します。この交換のみがリフレッシュトークンを返します。

ID トークンには、OpenID Connect 仕様の次のクレームが含まれます:

ClaimWhen it's present
auth_timeWhen Casdoor knows the time at which the user last entered credentials
at_hashWhen the ID token comes with an access token, and in the ID token of the authorization code grant
c_hashWhen the ID token comes with an authorization code

at_hash と c_hash は SHA-256 を使用するか、アプリケーションの Token signing method が 384 または 512 で終わる場合は SHA-384 または SHA-512 を使用します。これらは OpenID Connect 仕様に記載されている方法で検証してください。

レスポンモード​

response_mode は、Casdoor が認可レスポンスやエラーをリダイレクト URL にどのように送信するかを決定します:

response_modeDeliveryDefault for
queryIn the query stringresponse_type=code
fragmentIn the fragment, after #Every response type that returns a token
form_postIn a form that the browser submits to the redirect URL with POSTNone

Casdoor はクエリ文字列にトークンを配置しません。トークンを含むレスポンスは、response_mode=query の場合でもフラグメントに配置されます。レスポンスには state と iss が含まれ、アクセストークンを含む場合は token_type=Bearer も含まれます。form_post の場合、これらはフォームのフィールドになります。サインインページと同意ページの両方が、これら3つのすべてのモードをサポートしています。

Auto signin がオンの場合、Casdoor はセッションを持っているユーザーに対し、response_type=code かつ response_mode が空または query の場合に限り、サインインページを読み込まずにサインインを実行します。その他のリクエストではサインインページが読み込まれ、そこでサインインが完了します。

デバイスグラント​

入力手段が限られているデバイスやブラウザを持たないデバイス（スマートテレビや CLI ツールなど）でこのグラントを使用してください。

  1. アプリケーションの Grant types でデバイスグラントをオンにしてください。
  2. ディスカバリードキュメントから device_authorization_endpoint にリクエストを送信します。
  3. レスポンス内の verification_uri を、テキストまたは QR コードとしてユーザーに表示します。
  4. ユーザーは別のデバイスで URL を開き、ユーザーコードを入力してサインインします。Casdoor は verification_uri の背後にあるページを提供するため、UI を構築する必要はありません。
  5. その間、デバイスはユーザーがサインインするまで、自身の device_code を使用してトークンエンドポイントをポーリングします。RFC 8628, セクション 3.4 を参照してください。

アプリケーションの Signin methods テーブルで、サインイン方法としてデバイスログインを提供することもできます。

QR コードのスキャンによるウェブサイトへのサインイン​

同じフローにより、ネイティブアプリにサインインしているユーザーは、アプリで QR コードをスキャンすることでウェブサイトにサインインできます。

  1. Casdoor 管理コンソールで、アプリケーションの Signin methods に Device login を追加し、ルールを Login page に設定してください。
  2. Grant types で Device Code をオンにしてください。

サインインページにはフォームの横に QR コードが表示され、QR コードが承認されると自動的にサインインが完了します。

QR コードには verification_uri が含まれています。例えば https://<casdoor-host>/login/oauth/device/ra91hy?cancelToken=... です。スマホのカメラでスキャンしたユーザーはブラウザで URL を開き、そこでサインインして承認します。アプリ側で既に保持しているアクセストークンを使用して、直接承認することも可能です:

  1. URL のパスからユーザーコードを取得します。上記の例では ra91hy です。

  2. ユーザーが何にサインインしようとしているのかを表示します。

  3. ヘッダー Authorization: Bearer <access-token> とボディを指定して、https://<casdoor-host>/api/login に POST リクエストを送信します:

    {
        "application": ApplicationName,
        "organization": OrganizationName,
        "type": "device",
        "userCode": "ra91hy"
    }

サインインを拒否するには、同じ URL から取得した userCode と cancelToken をクエリパラメータとして https://<casdoor-host>/api/cancel-device-auth に送信します。

複数レプリカでのデバイスグラント​

デフォルトでは、Casdoor は保留中のデバイス認可リクエスト（デバイスコードとユーザーコードのマッピング）をメモリに保持します。複数の Casdoor レプリカがある場合、デバイスのポーリングリクエストとブラウザからの確認が異なるレプリカに届くことがあり、フローが断続的に失敗する可能性があります。

レプリカ間でリクエストを共有するには、conf/app.conf で redisEndpoint を設定します。これにより、Casdoor は Redis に保存します。これはセッション共有にも使用される同じオプションで、フォーマットは host:port[,poolSize[,password[,db]]] です（例: localhost:6379,100,mypassword,2）。追加の設定は不要です。最初のフィールドに ; で区切られた複数のアドレスを指定すると、Redis Cluster が使用されます。起動時に Casdoor が Redis に接続できない場合、警告ログを出力し、インメモリストレージを使用します。Configuration reference を参照してください。

リソースオーナーパスワード認証グラント​

アプリケーションがユーザーを Casdoor にリダイレクトできず、ユーザー名とパスワード自体を収集する場合にのみ、このグラントを使用してください。

  1. アプリケーションの Grant types でパスワードグラントを有効にします。

  2. トークンエンドポイントに POST リクエストを送信します:

    https://<CASDOOR_HOST>/api/login/oauth/access_token

    ボディは次のとおりです:

    {
        "grant_type": "password",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "username": Username,
        "password": Password,
    }

  3. レスポンスからトークンを読み取ります:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Casdoor がパスワードグラントを拒否する場合​

パスワードだけではサインインページのチェックがスキップされてしまいます。そのため、Casdoor はこれらのケースでは、パスワードグラントと暗黙的グラントをトークンエンドポイントで invalid_grant エラーとして拒否します:

Caseerror_description
The user has MFA enabledthe user has MFA enabled and cannot sign in with a password grant, please use the authorization code flow
The organization has turned off sign-inThe organization: <organization> has disabled users to signin
The user must change the password, or must set up MFA that the organization requiresthe user: <organization>/<user> must update the password or set up MFA on the login page first
The user has no local password, for example a user created through an external providerOAuth users cannot use password grant type, please use authorization code flow

IP 制限など、アプリケーションおよび組織の他のサインイン制限も適用されます。パスワードの変更や MFA の設定が必要なユーザーは、まずサインインページでそれらの操作を行う必要があり、その後にパスワードグラントが再び機能するようになります。

認証コードグラント​

ブラウザを開かずに電話番号またはメールアドレスとワンタイムコードでユーザーをサインインさせるネイティブアプリで使用します。これは RFC 6749 セクション 4.5 に準拠した Casdoor の拡張グラントです。アプリケーションで許可されている場合、アカウントが存在しないアドレスでも同じステップでサインアップが行われます。

  1. アプリケーションの Grant types で Verification Code を有効にし、SMS プロバイダー、メールプロバイダー、またはその両方をアプリケーションに追加します。

  2. コードを送信します。フォームデータを含む POST リクエストを https://<casdoor-host>/api/send-verification-code に送信します:

    FieldValue
    applicationIdadmin/<APPLICATION_NAME>
    typephone or email
    destThe phone number or email
    countryCodeThe region of a phone number, e.g. CN or US. Not needed for an E.164 number like +8613800000000
    methodlogin
    captchaTypenone, or the captcha type and captchaToken when the application's captcha provider asks for one

  3. コードをトークンと交換します。POST リクエストを https://<casdoor-host>/api/login/oauth/access_token に送信します:

    {
        "grant_type": "urn:casdoor:params:oauth:grant-type:verification-code",
        "client_id": ClientId,
        "username": "+8613800000000",
        "code": "123456",
        "scope": "openid profile"
    }

    username はコードが送信された電話番号またはメールアドレスです。国内形式の電話番号の場合は、country_code も併せて送信してください。

このグラントにはクライアントシークレットが必要ないため、公開クライアントからも動作します。レスポンスは他のグラントと同じであり、ユーザーをサインイン状態に保つための refresh_token が含まれています。

誤ったコードの入力は、アプリケーションの Failed signin limit にカウントされます。MFA を有効にしているユーザーに対しては Casdoor は拒否応答を返します。そのようなユーザーには認可コードグラントを使用してください。

認証コードによる新規ユーザーのサインアップ​

該当する電話番号またはメールアドレスを持つユーザーが存在しない場合、以下のすべての条件を満たせば、サインアップページと同様にグラントによってユーザーが作成されます:

  • アプリケーションで Enable signup がオンになっており、Disable self signup がオフになっています。
  • アプリケーションの Signup items で、コードで証明できるもの以外の項目が必須になっていません。必須なのは ID、Username、Display name、Password、Confirm password、Agreement、Signup button、Providers だけであることに加え、ユーザーがメールアドレスでサインアップする場合は Email、電話番号でサインアップする場合は Phone が許容される必要があります。デフォルトのサインアップ項目では Email と Phone の両方が必須になっているため、もう一方をオプションに変更してください。
  • 電話番号の場合、その地域が組織の Supported country codes に含まれている必要があります。

上記の条件を満たさない場合、/api/send-verification-code はユーザーが存在しないと回答し、既存のユーザーのみがサインインできるようになります。

モバイルワンクリックグラント​

中国本土のネイティブアプリでは、SMS コードなしでデバイスの電話番号を使ってユーザーをサインインすることもできます。Alibaba Cloud PNVS のワンクリックログイン SDK がトークンを返し、アプリがそれをグラントタイプ urn:casdoor:params:oauth:grant-type:mobile-one-click で交換します。Mobile one-click login を参照してください。

クライアントクレデンシャルズグラント​

ユーザーが存在しないマシン間通信（M2M）のためにこのグラントを使用します。

  1. アプリケーションの Grant types でクライアントクレデンシャルズグラントを有効にします。

  2. POST リクエストを https://<casdoor-host>/api/login/oauth/access_token に送信します:

    {
        "grant_type": "client_credentials",
        "client_id": ClientId,
        "client_secret": ClientSecret,
    }

  3. レスポンスからトークンを読み取ります:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

上記のグラントのトークンとは異なり、このアクセストークンはユーザーではなくアプリケーションに属しています。

リフレッシュトークングラント​

以前のレスポンスで取得したリフレッシュトークンを使用して、新しいアクセストークンを取得します。

  1. アプリケーションの Refresh token expire でリフレッシュトークンの有効期限を設定します。デフォルトは 0 時間です。

  2. POST リクエストを https://<casdoor-host>/api/login/oauth/refresh_token に送信します:

    {
        "grant_type": "refresh_token",
        "refresh_token": REFRESH_TOKEN,
        "scope": SCOPE,
        "client_id": ClientId,
        "client_secret": ClientSecret,
    }

  3. レスポンスからトークンを読み取ります:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Casdoor はリフレッシュリクエストを以下のようにチェックします:

  • トークンが client_secret を送る認可コード交換またはトークン交換で発行された場合、リフレッシュリクエストには正しい client_secret が含まれている必要があります。そうでない場合、Casdoor は invalid_client を返します。シークレットなしで PKCE を使用した公開クライアントは、シークレットなしでリフレッシュできます。
  • リフレッシュトークンはリクエスト元のアプリケーションに属している必要があります。そうでない場合、Casdoor は the token is for wrong application (client_id) というメッセージ付きで invalid_grant を返します。
  • リクエスト内の scope は元のスコープの部分集合である必要があります。省略した場合、新しいトークンは元のスコープを持ちます。
  • 不明なリフレッシュトークンまたは取り消されたリフレッシュトークンは、refresh token is invalid or revoked というメッセージ付きで invalid_grant エラーとなります。サインアウト時など、Casdoor によって無効化されたリフレッシュトークンは、refresh token is expired というメッセージ付きで invalid_grant エラーとなります。

ユーザー名を変更しても、そのユーザーのリフレッシュトークンは無効になりません。トークンを失効させるイベントについては、When Casdoor revokes tokens を参照してください。

リフレッシュ トークンのローテーション​

デフォルトでは、RFC 9700 が公開クライアントに対して推奨しているように、すべてのリフレッシュで新しいリフレッシュ トークンが返され、使用されたトークンは失効します。各リフレッシュ後に新しいリフレッシュ トークンを保存してください。すでに使用されたリフレッシュ トークンは invalid_grant で失敗します。

複数のプロセスが 1 つのリフレッシュ トークンを共有するクライアントでは、ローテーションにより問題が発生します。たとえば、環境変数から取得したトークンを使用して並行ジョブを実行する CLI などです。最初のリフレッシュで、他のすべてのプロセスにとってのトークンが失効してしまいます。このようなクライアントの場合は、アプリケーションの OIDC/OAuth 設定で Disable refresh token rotation を有効にしてください。すると:

  • リフレッシュは同じリフレッシュ トークンを返し、元の有効期限を維持します。
  • 以前のリフレッシュによるアクセストークンは、有効期限が切れるまで有効なままです。
  • サインアウトしても、すべてのプロセスのリフレッシュ トークンは依然として失効します。
注意

ローテーションがない場合、漏洩したリフレッシュ トークンは有効期限が切れるまで機能します。Refresh token expire を短く保ち、公開クライアントには DPoP を優先的に使用してください。

トークン交換グラント​

Token Exchange (RFC 8693) は、異なるプロパティを持つ新しいトークンと既存のトークンを交換します。あるサービスがユーザーの代わりに別のサービスを呼び出す場合や、ダウンストリーム サービスに渡す前にトークンのスコープを狭める場合に使用します。たとえば、API ゲートウェイは、マイクロサービスへのリクエストを転送する前に、広いスコープのトークンを狭いスコープのトークンと交換し、各サービスが必要とする権限のみが付与されるようにします。

POST リクエストを https://<casdoor-host>/api/login/oauth/access_token に送信します:

{
    "grant_type": "urn:ietf:params:oauth:grant-type:token-exchange",
    "client_id": ClientId,
    "client_secret": ClientSecret,
    "subject_token": SubjectToken,
    "subject_token_type": "urn:ietf:params:oauth:token-type:access_token",
    "scope": "openid email"
}
Parameter説明
subject_tokenThe token to exchange, typically an access token or a JSON Web Token (JWT) that you already hold
subject_token_typeurn:ietf:params:oauth:token-type:access_token (default), urn:ietf:params:oauth:token-type:jwt, or urn:ietf:params:oauth:token-type:id_token
scopeOptional. A subset of the scope of the subject token. If you omit it, the new token has the scope of the subject token
audienceOptional. The application that the new access token is for, by its client ID or by its application name. The aud claim of the new access token is then the client ID of that application, and the aud of the new ID token stays the requesting client

レスポンスには、サブジェクト トークンと同じユーザー用の新しいトークンが含まれます:

{
    "access_token": "eyJhb...",
    "id_token": "eyJhb...",
    "refresh_token": "eyJhb...",
    "token_type": "Bearer",
    "expires_in": 10080,
    "scope": "openid email"
}

Casdoor は、要求元クライアントの証明書ではなく、発行元アプリケーションの証明書 (azp クレームで識別されます) を使用してサブジェクト トークンを検証します。要求元クライアントが発行元でない場合、サブジェクト トークンの aud クレームには要求元クライアントのクライアント ID が含まれている必要があります。それ以外の場合、Casdoor は交換を invalid_grant で拒否します。これにより、オーディエンスとして指定されていない限り、あるアプリケーションが別のアプリケーションのトークンを交換することを防ぎます (RFC 8693、セクション 2.1)。このルールは、JWT-Standard を含むすべての Token format に適用されます。

Casdoor は、次のような場合にも交換を拒否します:

CaseError

The subject token has no user, for example a token of the client credentials grantinvalid_grant, subject_token has no user

外部発行元のトークンも、クライアント シークレットなしでサブジェクト トークンとして使用できます。Federated credentials を参照してください。

JWT ベアラート グラント​

JWT bearer grant (RFC 7523) では、クライアントはクライアント シークレットの代わりに署名付き JWT アサーションを提示することでアクセストークンを取得します。クライアントが秘密鍵を保持しており、長期間有効なシークレットを共有したくないサービス間通信で使用します。

  1. アプリケーションの Grant types で JWT Bearer を有効にします。

  2. アプリケーションの Security タブにある Client cert にクライアントの証明書をアップロードします。Casdoor はその証明書の公開キーを使用してアサーションを検証します。

  3. アサーションを作成します。これは、クライアントの秘密鍵で署名され、次のクレームを含む JWT です:

    ClaimDescription
    issIssuer — the client_id of the application
    subサブジェクト — アプリケーションの client_id
    audAudience — the Casdoor token endpoint URL
    expExpiry time (Unix timestamp)

  4. POST リクエストを https://<casdoor-host>/api/login/oauth/access_token に送信します:

    {
        "grant_type": "urn:ietf:params:oauth:grant-type:jwt-bearer",
        "client_assertion_type": "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
        "client_assertion": "<signed-JWT>",
        "client_id": "CLIENT_ID"
    }

  5. レスポンスからトークンを読み取ります:

    {
        "access_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Casdoor は署名と標準的な JWT クレームを検証します。アクセストークンは、クライアント クレデンシャルズ グラントと同様に、アプリケーションに属します。

JWT ベアラート グラントの assertion には、アプリケーションが信頼する外部発行元のトークンを使用することもできます。Federated credentials を参照してください。

フェデレーテッド クレデンシャルズ (ワークロード アイデンティティ)​

フェデレーテッド クレデンシャルズを使用すると、アプリケーションは GitHub Actions、Kubernetes、クラウド ワークロード アイデンティティ、または別の IdP などの外部 OpenID Connect 発行元のトークンを自らのクレデンシャルとして信頼します。そのようなトークンを既に保持しているワークロードは、クライアント シークレットやクライアント証明書なしで Casdoor トークンを取得できます。

  1. Casdoor 管理コンソールで、アプリケーションを開き、OIDC/OAuth タブに移動します。

  2. Federated credentials で、信頼する各発行元とサブジェクトについて行を追加します:

    ColumnDescription
    IssuerThe issuer of the external tokens. It must equal the iss claim exactly, for example https://token.actions.githubusercontent.com
    JWKS URLThe URL of the signing keys of the issuer. If you leave it empty, Casdoor reads jwks_uri from <issuer>/.well-known/openid-configuration, whose issuer must match
    SubjectRequired. The sub claim to accept. * matches any text, for example repo:my-org/my-repo:*
    Audience受け入れる aud 値。空のままにすると、Casdoor は自身のオリジン、トークン エンドポイント https://<casdoor-host>/api/login/oauth/access_token、またはアプリケーションのクライアント ID を受け入れます
    UserThe user that the token stands for: a username, or {claim} to take the username from a claim, for example {email}. If you leave it empty, the token stands for the application itself

  3. Grant types で、ワークロードが使用するグラントを有効にします。

  4. Save をクリックします。

その後、ワークロードは外部トークンを次の 3 つの方法のいずれかで提示します:

  • トークン エンドポイントでの client_assertion として、client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer とともに使用し、任意のグラントでクライアントを認証します。外部トークンの sub はクライアント ID ではないため、リクエストに client_id も送信してください。
  • JWT bearer grant の assertion として。
  • トークン交換グラント の subject_token として。クライアント シークレットは不要です。

たとえば、GitHub Actions ジョブは OIDC トークンを Casdoor トークンと交換します:

curl -X POST https://<casdoor-host>/api/login/oauth/access_token \
  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d client_id=<client-id> \
  -d subject_token=<github-oidc-token> \
  -d subject_token_type=urn:ietf:params:oauth:token-type:jwt

Casdoor は外部トークンを次のように検証します:

  • 署名は発行元のキーでチェックされます。Casdoor はキーを 1 時間キャッシュし、トークンに未知の kid がある場合は、1 分間に最大 1 回だけ再取得します。
  • 署名アルゴリズムは、RS256、RS384、RS512、PS256、PS384、PS512、ES256、ES384、ES512、または EdDSA のいずれかです。
  • トークンには exp クレームが必要です。Casdoor は 1 分のクロックスキューを許容します。
  • 信頼できる発行者のトークンで、サブジェクトがどの行とも一致しない場合は失敗し、例えば the subject: <sub> of issuer: <issuer> is not trusted by application: [<application>] のようなエラーになります。

User が空の場合、新しいトークンはクライアント資格情報グラントと同様にアプリケーション トークンとなり、リフレッシュ トークンや ID トークンは含まれません。それ以外の場合は、アプリケーションの組織内でマッピングされたユーザーのトークンとなります。そのユーザーが存在しない場合、またはトークンにクレームがない場合、Casdoor は invalid_grant を返します。

ディスカバリ ドキュメントの token_endpoint_auth_methods_supported に private_key_jwt が記載されています。

DPoP（送信者制約付きトークン）​

Casdoor は Demonstrating Proof of Possession (DPoP, RFC 9449) をサポートしています。DPoP はアクセストークンをクライアントが保持するキーにバインドするため、プライベート キーなしでは漏洩したトークンは無効になります。

DPoP バインド トークンを取得するには、トークン リクエストで DPoP 証明 JWT を含む DPoP ヘッダーを送信します:

POST /api/login/oauth/access_token
DPoP: <DPoP proof JWT>

Casdoor は、証明の公開鍵を JWK サムプリント (jkt) でトークンにバインドし、Bearer の代わりに token_type DPoP を返します:

{
    "access_token": "eyJhb...",
    "token_type": "DPoP",
    "expires_in": 10080,
    "scope": "openid"
}

リフレッシュ トークン リクエストも同じ DPoP ヘッダーを受け付けます。Casdoor は不正な証明をエラー invalid_dpop_proof で拒否します。DPoP で発行されたリフレッシュ トークンもキーにバインドされているため、更新には同じキーで署名された DPoP 証明が必要です。証明がない場合、または別のキーの証明がある場合、更新は invalid_dpop_proof で失敗します。Casdoor は、リフレッシュ証明の htu クレームをトークン エンドポイント https://<casdoor-host>/api/login/oauth/access_token と照合します。

ディスカバリ ドキュメントの dpop_signing_alg_values_supported に、Casdoor が証明に対して受け入れる署名アルゴリズムが記載されています:

{
    "dpop_signing_alg_values_supported": ["RS256", "RS512", "ES256", "ES384", "ES512", "PS256", "PS384", "PS512"]
}

トークン インテロスペクション レスポンスには、cnf.jkt クレーム内のキー バインディングが表示されます (RFC 9449、セクション 8)。

アクセストークンの検証​

Casdoor は トークン インテロスペクション (RFC 7662) をサポートしています。HTTP Basic 認証でリクエストを認証し、ユーザー名としてクライアント ID、パスワードとしてクライアント シークレットを使用します:

POST /api/login/oauth/introspect HTTP/1.1
Host: CASDOOR_HOST
Accept: application/json
Content-Type: application/x-www-form-urlencoded
Authorization: Basic Y2xpZW50X2lkOmNsaWVudF9zZWNyZXQ=

token=ACCESS_TOKEN&token_type_hint=access_token

レスポンスの例:

{
    "active": true,
    "client_id": "c58c...",
    "username": "admin",
    "token_type": "Bearer",
    "exp": 1647138242,
    "iat": 1646533442,
    "nbf": 1646533442,
    "sub": "7a6b4a8a-b731-48da-bc44-36ae27338817",
    "aud": [
        "c58c..."
    ],
    "iss": "http://localhost:8000"
}

代わりに、アプリケーションの証明書の公開鍵、または JWKS エンドポイント のキーを使用して、自分でトークンの署名を検証することもできます。SDK では ParseJwtToken() でこれを行います。

アクセストークンの使用​

アクセストークンを送信して Casdoor API を呼び出します。例えば、次の 2 つの方法のいずれかで GET または POST を使用して /api/userinfo を呼び出します:

  • Authorization ヘッダーを使用する場合: Authorization: Bearer <access-token>
  • クエリ パラメーターを使用する場合: https://<casdoor-host>/api/userinfo?accessToken=<access-token>

Casdoor は、トークンのスコープが許可するユーザーのフィールドを返します:

{
    "sub": "7a6b4a8a-b731-48da-bc44-36ae27338817",
    "iss": "http://localhost:8000",
    "aud": "c58c..."
}

より多くのフィールドを取得するには、認可リクエストでより多くのスコープをリクエストしてください。

UserInfo と get-account​

EndpointReturns
/api/userinfoThe standard OpenID Connect (OIDC) claims of the user, limited by the scopes of the token
/api/get-accountサインイン中のアカウントの完全なuserオブジェクト。このエンドポイントは Casdoor 固有です。外部 OAuth プロバイダーがある場合、そのプロバイダーのアクセストークンを含みます

外部プロバイダーのアクセストークンの取得​

ユーザーが GitHub や Google などの外部 OAuth プロバイダーを通じてサインインすると、Casdoor はそのプロバイダーのアクセストークンをユーザーの originalToken フィールドに保存します。アプリケーションではこれを使用して、別の OAuth フローを行うことなく、ユーザーに代わってプロバイダーの API (GitHub API や Google Drive API など) を呼び出すことができます。

/api/get-account からトークンを読み取ります:

{
  "status": "ok",
  "data": {
    "name": "user123",
    "originalToken": "ya29.a0AfH6SMBx...",
    ...
  }
}

Casdoor は、ユーザー自身と管理者に対してのみ originalToken を返します。その他のリクエスターに対しては、フィールドをマスクします。
