OAuth 2.0

Casdoor є сервером авторизації OAuth 2.0. Ця сторінка описує, як отримати токен доступу для кожного типу надання прав, як перевірити токен і як його використовувати. Якщо ви не хочете самостійно викликати кінцеві точки, скористайтеся Casdoor SDK або стандартним OIDC-клієнтом.

Кінцеві точки​

EndpointURL
Authorizationhttps://<casdoor-host>/login/oauth/authorize
Tokenhttps://<casdoor-host>/api/login/oauth/access_token
Refresh tokenhttps://<casdoor-host>/api/login/oauth/refresh_token
Token introspectionhttps://<casdoor-host>/api/login/oauth/introspect
Token revocationhttps://<casdoor-host>/api/login/oauth/revoke
UserInfohttps://<casdoor-host>/api/userinfo

У прикладах ClientId і ClientSecret — це Client ID та Client secret вашого додатка Casdoor.

Підтримувані типи надання прав​

Grant TypeRFCUse Case
Authorization CodeRFC 6749 §4.1Default; web/mobile apps with a backend. Enabled by default.
ImplicitRFC 6749 §4.2Frontend-only apps without a backend.
Resource Owner PasswordRFC 6749 §4.3Apps with no frontend redirect; user credentials sent directly.
Client CredentialsRFC 6749 §4.4Service-to-service calls with no user involved.
Refresh TokenRFC 6749 §6Renew an access token without re-authenticating.
Device AuthorizationRFC 8628Devices with limited input or no browser.
Token ExchangeRFC 8693Swap an existing token for one with different scope or audience.
JWT BearerRFC 7523Service auth using a signed JWT assertion instead of a client secret.
Verification CodeCasdoor extensionNative apps that sign users in (and up) with a code sent by SMS or email.
Mobile One-ClickРозширення CasdoorНативні додатки, що здійснюють вхід (та реєстрацію) користувачів за номером телефону пристрою через Alibaba Cloud PNVS.

Надання права за кодом авторизації ввімкнено за замовчуванням. Інші типи надання прав увімкніть у полі Grant types на сторінці редагування додатка.

Надання права за кодом авторизації​

Використовуйте цей тип надання прав для додатків, які здійснюють вхід користувачів через браузер. Це рекомендований тип надання прав.

  1. Перенаправте користувача на кінцеву точку авторизації:

    https://<CASDOOR_HOST>/login/oauth/authorize?
    client_id=CLIENT_ID&
    redirect_uri=REDIRECT_URI&
    response_type=code&
    scope=openid&
    state=STATE

  2. Користувач входить у систему. Casdoor перенаправляє браузер на вашу URL-адресу перенаправлення з кодом авторизації:

    https://REDIRECT_URI?code=CODE&state=STATE&iss=ISSUER

    iss — це URL-адреса емітента Casdoor, визначена у RFC 9207. Порівняйте її зі значенням issuer з документа discovery, щоб переконатися, що відповідь надійшла від того ж сервера Casdoor, на який ви перенаправили користувача. Casdoor додає iss до кожної відповіді авторизації та до кожної помилки, яку він надсилає назад на URL-адресу перенаправлення, а документ discovery оголошує про це параметром "authorization_response_iss_parameter_supported": true.

  3. Обмініть код на токени. Надішліть запит POST на кінцеву точку токенів:

    https://<CASDOOR_HOST>/api/login/oauth/access_token

    Із тілом запиту:

    {
        "grant_type": "authorization_code",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "code": Code,
    }

  4. Зчитайте токени з відповіді:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Код авторизації дійсний протягом 5 хвилин і використовується лише один раз. Друга спроба обміну того самого коду завершується помилкою invalid_grant з описом authorization code has been used for token: [...].

Відповіді кінцевої точки токенів та кінцевої точки оновлення токенів містять заголовки Cache-Control: no-store та Pragma: no-cache, щоб жоден кеш не зберігав токени.

Області​

Запитуйте області дії (scopes) за допомогою параметра scope в URL авторизації. Вони визначають, які поля користувача повертаються токенами та кінцевою точкою UserInfo.

Область застосуванняОпис
openid (default)sub, iss, aud
profilename, displayName, avatar
emailemail address
addressaddress (OIDC object in JWT-Standard; see OIDC address claim)
phoneномер телефону

Розділяйте кілька областей дії символом %20:

https://<CASDOOR_HOST>/login/oauth/authorize?
client_id=...&
scope=openid%20email

Щодо тверджень (claims) для кожної області дії дивіться специфікацію OpenID Connect.

PKCE​

Casdoor підтримує Proof Key for Code Exchange (PKCE), який захищає код авторизації публічних клієнтів, таких як мобільні додатки та односторінкові вебзастосунки (SPA).

  1. Згенеруйте випадковий верифікатор коду (code verifier) довжиною від 43 до 128 символів.

  2. Обчисліть виклик коду (code challenge): SHA-256 хеш верифікатора, закодований у формат Base64-URL.

  3. Додайте два параметри до URL авторизації:

    &code_challenge_method=S256&code_challenge=YOUR_CHALLENGE

  4. Додайте параметр code_verifier із оригінальним верифікатором до запиту на отримання токена.

При використанні PKCE параметр client_secret є необов'язковим у запиті на отримання токена. Якщо ви його надсилаєте, він має бути правильним.

примітка

Коли Casdoor сам автентифікує користувачів через зовнішнього постачальника OAuth, що вимагає PKCE (наприклад, Twitter або власний постачальник з увімкненим PKCE), Casdoor генерує верифікатор коду для кожного процесу автентифікації. Вам не потрібно реалізовувати PKCE для цієї частини.

Прив'язка токена до одного сервісу​

Якщо ваш додаток викликає кілька бекенд-сервісів, ви можете прив'язати токен до одного з них, щоб токен, виданий для одного сервісу, не можна було використовувати в іншому. Для цього Casdoor підтримує Resource Indicators (RFC 8707).

  1. Додайте параметр resource з абсолютним URI, що ідентифікує сервіс, до URL авторизації:

    https://<CASDOOR_HOST>/login/oauth/authorize?
    client_id=CLIENT_ID&
    redirect_uri=REDIRECT_URI&
    response_type=code&
    scope=openid&
    state=STATE&
    resource=https://api.example.com

  2. Надішліть той самий параметр resource у запиті на отримання токена:

    {
        "grant_type": "authorization_code",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "code": Code,
        "resource": "https://api.example.com"
    }

Твердження aud (audience) у токені доступу стає URI ресурсу, а не ID клієнта. Сервіс перевіряє, чи токен було видано для нього, аналізуючи aud. Значення resource має бути точно таким самим в обох запитах.

Casdoor передає параметр resource через інтерактивний вхід. Якщо користувачеві потрібно ввести пароль, пройти багатофакторну автентифікацію (MFA), використати WebAuthn або схвалити сторінку згоди, параметр зберігається під час переспрямувань. Він також зберігається, коли Casdoor автоматично входить користувача за наявним сеансом.

Під час оновлення токена новий токен доступу зберігає значення aud з початкового надання (grant). Ви можете повторити параметр resource у запиті на оновлення як параметр рядка запиту або поле тіла запиту. Якщо ви це робите, його значення має збігатися з початковим наданням. В іншому випадку Casdoor поверне помилку invalid_grant з описом resource parameter does not match the original grant.

Пропуск сторінки входу за допомогою підказки провайдера​

Щоб одразу переспрямувати користувача до одного постачальника OAuth без показу сторінки входу Casdoor, додайте provider_hint=<provider-name> до URL авторизації:

https://<CASDOOR_HOST>/login/oauth/authorize?
client_id=CLIENT_ID&
redirect_uri=REDIRECT_URI&
response_type=code&
scope=openid&
state=STATE&
provider_hint=github

Потім Casdoor видає невелику сторінку переспрямування без завантаження повного фронтенду і надсилає користувача до постачальника. Це скорочує час очікування на переспрямування на повільних пристроях та з'єднаннях.

Реєстрація в процесі авторизації​

Користувач, який створює обліковий запис під час процесу авторизації, переспрямовується на ваш URL переспрямування з кодом авторизації одразу після завершення реєстрації, так само як після входу. Casdoor передає параметри авторизації, такі як client_id, response_type та redirect_uri, через процес реєстрації. Вашому додатку не потрібні зміни для цього.

Керування запитом на вхід​

За замовчуванням користувач, який вже має сеанс Casdoor, може бути автентифікований без повторного введення облікових даних. Додайте параметри OpenID Connect prompt та max_age до URL авторизації, щоб змінити цю поведінку:

ParameterEffect
prompt=loginThe user must enter credentials again, even with an existing session
max_age=<seconds>Користувач повинен повторно ввести облікові дані, якщо він зробив це більше ніж <seconds> секунд тому, або якщо Casdoor не знає часу останньої автентифікації
prompt=noneCasdoor shows no page. It signs the user in with the existing session, or sends an error back to the redirect URL

prompt приймає список значень, розділених пробілами. Якщо наявний сеанс не задовольняє умови prompt=login або max_age, вхід із цим сеансом завершується помилкою login_required з повідомленням Please sign in again. Час введення облікових даних користувачем зазначено у твердженні auth_time ID-токена.

Використовуйте prompt=none, щоб перевірити, наприклад, з прихованого iframe, чи користувач ще автентифікований. У цьому випадку Casdoor пропускає автоматичне переспрямування до одного постачальника і відповідає так, як це відбулося б при успішній відповіді, включаючи state та iss, і однією з цих помилок:

ErrorReason
login_requiredNo Casdoor session, the user of the session isn't in the organization of the application, or the session doesn't satisfy max_age
consent_requiredThe user must approve the consent page first
interaction_requiredThe user must update the password, set up or complete MFA, select a plan, or fill in the prompt page first
access_deniedThe sign-in failed for another reason. error_description says why
server_errorThe request to Casdoor failed

Implicit grant​

Використовуйте цей тип надання (grant) лише для додатків без бекенду. Надавайте перевагу типу надання Authorization Code Grant із PKCE.

  1. У розділі Grant types додатка увімкніть Token, щоб повертати токен доступу, ID Token, щоб повертати ID-токен, або обидва варіанти.

  2. Переспрямуйте користувача на:

    https://<CASDOOR_HOST>/login/oauth/authorize?client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&response_type=token&scope=openid&state=STATE

  3. Після входу користувача Casdoor переспрямовує браузер на:

    https://REDIRECT_URI#access_token=ACCESS_TOKEN&token_type=Bearer&state=STATE&iss=ISSUER

response_type може мати значення token, id_token або id_token token. Кінцева точка авторизації ніколи не повертає токен оновлення. Якщо тип надання, необхідний для вибраного response type, не увімкнено, Casdoor показує помилку Grant_type: token is not supported in this application (або id_token).

Якщо scope містить openid і відповідь містить ID-токен, надішліть параметр nonce. Casdoor копіює його в ID-токен і відхиляє запит без нього: The nonce parameter is required for this response type.

обережно

Implicit grant на кінцевій точці токенів (grant_type=token з ім'ям користувача та паролем) вимагає користувача з локальним паролем. Користувачі, створені лише через зовнішнього постачальника, які не мають локального пароля, не можуть ним користуватися і отримають помилку invalid_grant. До них застосовуються ті самі правила, що й для password grant. Використовуйте authorization code grant для таких користувачів.

Гібридний потік​

У гібридному потоці OpenID Connect кінцева точка авторизації повертає код авторизації разом із токенами. Ваш фронтенд може використовувати токени одразу, а ваш бекенд обмінює код, як у дозволі коду авторизації.

response_type — це комбінація code, token та id_token, розділена пробілами. Значення для гібридного потоку:

response_typeThe authorization endpoint returns
code id_tokencode and id_token
code tokencode and access_token
code token id_tokencode, access_token та id_token

  1. У Grant types додатка увімкніть Token для типу відповіді, що містить token, і ID Token для того, що містить id_token.

  2. Перенаправте користувача на кінцеву точку авторизації з типом відповіді та nonce:

    https://<CASDOOR_HOST>/login/oauth/authorize?client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&response_type=code%20id_token&scope=openid&state=STATE&nonce=NONCE

    nonce обов'язковий, коли scope містить openid і тип відповіді містить id_token, або є code token.

  3. Після входу користувача Casdoor перенаправляє браузер на вашу URL-адресу перенаправлення. Значення містяться у фрагменті, якщо ви не зазначили інший режим відповіді.

  4. Обміняйте код на кінцевій точці токенів. Лише цей обмін повертає refresh token.

ID token містить такі твердження специфікації OpenID Connect:

ClaimWhen it's present
auth_timeWhen Casdoor knows the time at which the user last entered credentials
at_hashWhen the ID token comes with an access token, and in the ID token of the authorization code grant
c_hashWhen the ID token comes with an authorization code

at_hash і c_hash використовують SHA-256, або SHA-384 чи SHA-512, якщо Token signing method додатка закінчується на 384 або 512. Перевіряйте їх згідно зі специфікацією OpenID Connect.

Режими відповіді​

response_mode визначає, як Casdoor надсилає відповідь авторизації або помилку на URL-адресу перенаправлення:

response_modeDeliveryDefault for
queryIn the query stringresponse_type=code
fragmentIn the fragment, after #Every response type that returns a token
form_postIn a form that the browser submits to the redirect URL with POSTNone

Casdoor ніколи не розміщує токени у рядку запиту. Відповідь, що містить токен, розміщується у фрагменті, навіть при response_mode=query. Відповідь містить state і iss, а також token_type=Bearer, коли вона містить access token. При form_post вони є полями форми. Сторінка входу та сторінка згоди підтримують усі три режими.

Якщо увімкнено Auto signin, Casdoor виконує вхід користувача, який має сесію, без завантаження сторінки входу лише для response_type=code з порожнім response_mode або query. Інші запити завантажують сторінку входу, яка потім завершує вхід.

Дозвіл пристрою (Device grant)​

Використовуйте цей дозвіл для пристроїв з обмеженим введенням або без браузера, таких як смарт-ТВ та інструменти CLI.

  1. Увімкніть дозвіл пристрою у Grant types додатка.
  2. Надішліть запит до device_authorization_endpoint з документа discovery.
  3. Покажіть користувачу verification_uri з відповіді як текст або як QR-код.
  4. Користувач відкриває URL-адресу на іншому пристрої, вводить код користувача та виконує вхід. Casdoor надає сторінку за verification_uri, тому вам не потрібно створювати для неї UI.
  5. Тим часом пристрій опитує кінцеву точку токенів своїм device_code, доки користувач не виконає вхід. Див. RFC 8628, розділ 3.4.

Ви також можете запропонувати вхід через пристрій як метод входу у таблиці Signin methods додатка.

Дозвольте користувачам входити на ваш сайт, скануючи QR-код​

Той самий потік дозволяє користувачам, які вже увійшли у ваш нативний додаток, увійти на ваш сайт, скануючи QR-код за допомогою додатка.

  1. У адміністративній консолі Casdoor додайте Device login до Signin methods додатка з правилом Login page.
  2. Увімкніть Device Code у Grant types.

Сторінка входу тепер показує QR-код поруч із формою та самостійно завершує вхід після схвалення QR-коду.

QR-код містить verification_uri, наприклад https://<casdoor-host>/login/oauth/device/ra91hy?cancelToken=.... Користувач, який сканує його камерою телефону, відкриває URL-адресу в браузері, виконує вхід і схвалює там же. Ваш додаток може схвалити його напряму, використовуючи access token, який він уже має:

  1. Візьміть код користувача зі шляху URL-адреси. У прикладі це ra91hy.

  2. Покажіть користувачу, куди він збирається увійти.

  3. Надішліть POST запит до https://<casdoor-host>/api/login із заголовком Authorization: Bearer <access-token> та тілом:

    {
        "application": ApplicationName,
        "organization": OrganizationName,
        "type": "device",
        "userCode": "ra91hy"
    }

Щоб відхилити вхід, надішліть userCode та cancelToken з тієї ж URL-адреси як параметри запиту до https://<casdoor-host>/api/cancel-device-auth.

Дозвіл пристрою з кількома репліками​

За замовчуванням Casdoor зберігає очікуючі запити авторизації пристроїв, які пов'язують коди пристроїв з кодами користувачів, у пам'яті. При наявності кількох реплік Casdoor запит опитування пристрою та підтвердження в браузері можуть потрапити на різні репліки, і потік періодично завершується невдачею.

Щоб спільно використовувати запити між репліками, встановіть redisEndpoint у conf/app.conf. Тоді Casdoor зберігає їх у Redis. Це той самий параметр, що й для спільного використання сесій, у форматі host:port[,poolSize[,password[,db]]], наприклад localhost:6379,100,mypassword,2, і додаткові параметри не потрібні. Кілька адрес у першому полі, розділені ;, використовують Redis Cluster. Якщо Casdoor не може зв'язатися з Redis при запуску, він логує попередження і використовує сховище в пам'яті. Див. Довідник конфігурації.

Дозвіл пароля власника ресурсу (Resource owner password credentials grant)​

Використовуйте цей дозвіл лише коли ваш додаток не може перенаправити користувача до Casdoor і сам збирає ім'я користувача та пароль.

  1. Увімкніть дозвіл пароля у Grant types додатка.

  2. Надішліть POST запит до кінцевої точки токенів:

    https://<CASDOOR_HOST>/api/login/oauth/access_token

    З тілом запиту:

    {
        "grant_type": "password",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "username": Username,
        "password": Password,
    }

  3. Читаємо токени з відповіді:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Коли Casdoor відхиляє надання пароля​

Пароль сам по собі пропускає перевірки сторінки входу. Тому Casdoor відхиляє надання пароля та неявне надання на кінцевій точці токенів із помилкою invalid_grant у цих випадках:

Caseerror_description
The user has MFA enabledthe user has MFA enabled and cannot sign in with a password grant, please use the authorization code flow
The organization has turned off sign-inThe organization: <organization> has disabled users to signin
The user must change the password, or must set up MFA that the organization requiresthe user: <organization>/<user> must update the password or set up MFA on the login page first
The user has no local password, for example a user created through an external providerOAuth users cannot use password grant type, please use authorization code flow

Інші обмеження входу для додатка та організації, такі як IP-обмеження, також діють. Користувач, якому потрібно змінити пароль або налаштувати MFA, робить це спочатку на сторінці входу, після чого надання пароля знову працює.

Надання коду підтвердження​

Використовуйте цей тип надання у нативних додатках, які авторизують користувачів за номером телефону або електронною адресою та одноразовим кодом без відкриття браузера. Це розширене надання Casdoor, дозволене розділом 4.5 RFC 6749. Якщо додаток це дозволяє, адреса, яка ще не має облікового запису, реєструється на тому самому кроці.

  1. Увімкніть Verification Code у розділі Grant types додатка та додайте SMS-провайдера, поштового провайдера або обох до додатка.

  2. Надішліть код. Надішліть запит POST із даними форми на https://<casdoor-host>/api/send-verification-code:

    FieldValue
    applicationIdadmin/<APPLICATION_NAME>
    typephone or email
    destThe phone number or email
    countryCodeThe region of a phone number, e.g. CN or US. Not needed for an E.164 number like +8613800000000
    methodlogin
    captchaTypenone, or the captcha type and captchaToken when the application's captcha provider asks for one

  3. Обміняйте код на токени. Надішліть запит POST на https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "urn:casdoor:params:oauth:grant-type:verification-code",
        "client_id": ClientId,
        "username": "+8613800000000",
        "code": "123456",
        "scope": "openid profile"
    }

    username — це номер телефону або електронна адреса, на яку було надіслано код. Для номера телефону в національному форматі також надсилайте country_code.

Це надання не потребує секретного ключа клієнта (client secret), тому воно працює від публічного клієнта. Відповідь така ж, як і для інших типів надань, і містить refresh_token, який підтримує сесію користувача.

Неправильні коди враховуються до ліміту Failed signin limit додатка. Casdoor відхиляє користувачів, у яких увімкнено MFA. Використовуйте надання коду авторизації для них.

Реєстрація нових користувачів із кодом підтвердження​

Якщо жоден користувач не має такого номера телефону або електронної адреси, надання створює користувача, так само як і сторінка реєстрації, якщо виконуються всі наступні умови:

  • Для додатка увімкнено Enable signup, а Disable self signup вимкнено.
  • Поля Signup items додатка не вимагають нічого окрім того, що підтверджується кодом. Можуть бути обов'язковими лише ID, Username, Display name, Password, Confirm password, Agreement, Signup button і Providers, а також Email, коли користувач реєструється через електронну адресу, або Phone, коли користувач реєструється через номер телефону. Стандартні поля реєстрації вимагають і Email, і Phone, тому зробіть інше поле необов'язковим.
  • Для номера телефону його регіон має бути вказаний у Supported country codes організації.

Інакше /api/send-verification-code повідомить, що користувач не існує, і тільки наявні користувачі можуть входити в систему.

Надання мобільного входу в один клік​

Нативні додатки в материковому Китаї також можуть авторизовувати користувачів за номером телефону пристрою без SMS-коду: SDK одноклікового входу Alibaba Cloud PNVS повертає токен, і додаток обмінює його з типом надання urn:casdoor:params:oauth:grant-type:mobile-one-click. Див. Mobile one-click login.

Надання облікових даних клієнта​

Використовуйте це надання для взаємодії між машинами (machine-to-machine), де немає користувача.

  1. Увімкніть надання облікових даних клієнта у розділі Grant types додатка.

  2. Надішліть запит POST на https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "client_credentials",
        "client_id": ClientId,
        "client_secret": ClientSecret,
    }

  3. Читаємо токен з відповіді:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

На відміну від токенів із наведених вище типів надань, цей токен доступу належить додатку, а не користувачу.

Надання refresh token​

Використовуйте refresh token із попередньої відповіді, щоб отримати новий токен доступу.

  1. Налаштуйте термін дії refresh token у полі Refresh token expire додатка. За замовчуванням — 0 годин.

  2. Надішліть запит POST на https://<casdoor-host>/api/login/oauth/refresh_token:

    {
        "grant_type": "refresh_token",
        "refresh_token": REFRESH_TOKEN,
        "scope": SCOPE,
        "client_id": ClientId,
        "client_secret": ClientSecret,
    }

  3. Читаємо токени з відповіді:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Casdoor перевіряє запит на оновлення таким чином:

  • Якщо токен був виданий під час обміну кодом авторизації, який надсилав client_secret, або під час обміну токеном, запит на оновлення повинен містити правильний client_secret. Інакше Casdoor поверне invalid_client. Публічний клієнт, який використовував PKCE без секретного ключа, оновлює токен без нього.
  • Refresh token повинен належати додатку, що робить запит. Інакше Casdoor поверне invalid_grant із повідомленням the token is for wrong application (client_id).
  • scope у запиті повинен бути підмножиною початкового scope. Якщо ви його опустите, новий токен матиме початковий scope.
  • Невідомий або відкликаний refresh token спричиняє помилку invalid_grant із повідомленням refresh token is invalid or revoked. Refresh token, який Casdoor анулював, наприклад, при виході з системи, спричиняє помилку invalid_grant із повідомленням refresh token is expired.

Перейменування користувача не анулює його refresh tokens. Щодо подій, які дійсно відкликають токени, див. When Casdoor revokes tokens.

Ротація refresh token​

За замовчуванням кожне оновлення повертає новий refresh token і відкликає той, що був використаний, як рекомендує RFC 9700 для публічних клієнтів. Зберігайте новий refresh token після кожного оновлення. Вже використаний refresh token спричиняє помилку invalid_grant.

Ротація порушує роботу клієнтів, у яких кілька процесів спільно використовують один refresh token, наприклад CLI, який запускає паралельні завдання з токеном зі змінної середовища: перше оновлення скасовує токен для всіх інших. Для таких клієнтів увімкніть Disable refresh token rotation у налаштуваннях OIDC/OAuth додатку. Після цього:

  • Оновлення повертає той самий refresh token, який зберігає свій початковий термін дії.
  • Access-токени попередніх оновлень залишаються дійсними до закінчення їхнього терміну дії.
  • Вихід із системи все одно скасовує refresh token для всіх процесів.
обережно

Без ротації вкрадений refresh token працюватиме до закінчення його терміну дії. Встановіть коротке значення для Refresh token expire, а для публічних клієнтів віддайте перевагу DPoP.

Token exchange grant​

Token Exchange (RFC 8693) замінює токен на новий токен з іншими властивостями. Використовуйте його, коли один сервіс викликає інший від імені користувача, або щоб звузити область дії (scope) токена перед передачею його нижчестоящому сервісу. Наприклад, API gateway обмінює токен із широким scope на токен із вузьким scope перед тим, як переслати запит до мікросервісу, щоб кожен сервіс отримував лише необхідні йому права.

Надішліть POST-запит на https://<casdoor-host>/api/login/oauth/access_token:

{
    "grant_type": "urn:ietf:params:oauth:grant-type:token-exchange",
    "client_id": ClientId,
    "client_secret": ClientSecret,
    "subject_token": SubjectToken,
    "subject_token_type": "urn:ietf:params:oauth:token-type:access_token",
    "scope": "openid email"
}
ParameterОпис
subject_tokenThe token to exchange, typically an access token or a JSON Web Token (JWT) that you already hold
subject_token_typeurn:ietf:params:oauth:token-type:access_token (default), urn:ietf:params:oauth:token-type:jwt, or urn:ietf:params:oauth:token-type:id_token
scopeOptional. A subset of the scope of the subject token. If you omit it, the new token has the scope of the subject token
audienceOptional. The application that the new access token is for, by its client ID or by its application name. The aud claim of the new access token is then the client ID of that application, and the aud of the new ID token stays the requesting client

Відповідь містить новий токен для того самого користувача, що й subject token:

{
    "access_token": "eyJhb...",
    "id_token": "eyJhb...",
    "refresh_token": "eyJhb...",
    "token_type": "Bearer",
    "expires_in": 10080,
    "scope": "openid email"
}

Casdoor перевіряє subject token за сертифікатом додатку, який його видав (що визначається заявою azp), а не за сертифікатом клієнта, що надсилає запит. Якщо клієнт, що надсилає запит, не є емітером, заява aud subject token повинна включати client ID цього клієнта. Інакше Casdoor відхиляє обмін з помилкою invalid_grant. Це запобігає тому, щоб один додаток обмінював токени іншого додатка без явного зазначення в аудиторії (RFC 8693, розділ 2.1). Це правило діє для будь-якого Token format, включаючи JWT-Standard.

Casdoor також відмовляє в обміні в цих випадках:

CaseError
Subject token не є активним токеном Casdoor, наприклад, через те, що він був скасований або прострочений. Якщо subject_token_type встановлено як urn:ietf:params:oauth:token-type:id_token, Casdoor шукає токен як ID token, інакше — як access tokeninvalid_grant, subject_token is revoked or unknown
The subject token has no user, for example a token of the client credentials grantinvalid_grant, subject_token has no user
The user is forbidden to sign ininvalid_grant
The user isn't in the organization of the requesting application, and the application isn't sharedinvalid_grant
audience isn't a known applicationinvalid_target

Токен зовнішнього емітера також може бути subject token, без client secret. Див. Federated credentials.

JWT bearer grant​

За допомогою JWT bearer grant (RFC 7523) клієнт отримує access token, надаючи підписане JWT-твердження (assertion) замість client secret. Використовуйте його для міжсервісної взаємодії, де клієнт має закритий ключ, і ви не хочете поширювати довгостроковий секрет.

  1. Увімкніть JWT Bearer у Grant types додатку.

  2. Завантажте сертифікат клієнта в Client cert на вкладці Security додатку. Casdoor перевіряє твердження за відкритим ключем цього сертифіката.

  3. Створіть твердження: JWT, підписаний закритим ключем клієнта, який містить такі заяви (claims):

    ClaimDescription
    issIssuer — the client_id of the application
    subСуб'єкт — client_id додатку
    audAudience — the Casdoor token endpoint URL
    expExpiry time (Unix timestamp)

  4. Надішліть POST-запит на https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "urn:ietf:params:oauth:grant-type:jwt-bearer",
        "client_assertion_type": "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
        "client_assertion": "<signed-JWT>",
        "client_id": "CLIENT_ID"
    }

  5. Прочитайте токен із відповіді:

    {
        "access_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Casdoor перевіряє підпис і стандартні JWT-заяви. Access token належить додатку, так само як і при використанні client credentials grant.

assertion для JWT bearer grant також може бути токеном зовнішнього емітера, якому довіряє додаток. Див. Federated credentials.

Federated credentials (workload identity)​

За допомогою federated credentials додаток довіряє токенам зовнішнього OpenID Connect емітера, такого як GitHub Actions, Kubernetes, workload identity хмарного провайдера чи іншого IdP, як своєму обліковому документу. Робоче навантаження (workload), яке вже має такий токен, отримує токен Casdoor без client secret або client certificate.

  1. У адміністративній консолі Casdoor відкрийте додаток і перейдіть на вкладку OIDC/OAuth.

  2. У Federated credentials додайте рядок для кожного емітера та суб'єкта, яким ви довіряєте:

    ColumnDescription
    IssuerThe issuer of the external tokens. It must equal the iss claim exactly, for example https://token.actions.githubusercontent.com
    JWKS URLThe URL of the signing keys of the issuer. If you leave it empty, Casdoor reads jwks_uri from <issuer>/.well-known/openid-configuration, whose issuer must match
    SubjectRequired. The sub claim to accept. * matches any text, for example repo:my-org/my-repo:*
    AudienceЗначення aud, яке приймається. Якщо залишити порожнім, Casdoor приймає власний origin, свой token endpoint https://<casdoor-host>/api/login/oauth/access_token або client ID додатку
    UserThe user that the token stands for: a username, or {claim} to take the username from a claim, for example {email}. If you leave it empty, the token stands for the application itself

  3. У Grant types увімкніть тип надання доступу (grant), який використовує робоче навантаження.

  4. Натисніть Save.

Потім робоче навантаження подає свій зовнішній токен одним із трьох способів:

  • Як client_assertion на token endpoint, з client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer, для автентифікації клієнта в будь-якому grant. Також надсилайте client_id у запиті, оскільки sub зовнішнього токена не є client ID.
  • Як assertion для JWT bearer grant.
  • Як subject_token для token exchange grant. Client secret не потрібен.

Наприклад, завдання GitHub Actions обмінює свій OIDC токен на токен Casdoor:

curl -X POST https://<casdoor-host>/api/login/oauth/access_token \
  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d client_id=<client-id> \
  -d subject_token=<github-oidc-token> \
  -d subject_token_type=urn:ietf:params:oauth:token-type:jwt

Casdoor перевіряє зовнішній токен наступним чином:

  • Підпис перевіряється за ключами емітера. Casdoor кешує ключі протягом однієї години і повторно отримує їх, максимум раз на хвилину, коли токен містить невідомий kid.
  • Алгоритм підпису має бути одним із RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384, ES512 або EdDSA.
  • Токен повинен мати заяву exp. Casdoor допускає розбіжність годинника (clock skew) в одну хвилину.
  • Токен від довіреного емітера, суб'єкт якого не збігається з жодним рядком конфігурації, не пройде перевірку, наприклад, з помилкою the subject: <sub> of issuer: <issuer> is not trusted by application: [<application>].

Якщо поле User порожнє, новий токен є токеном застосунку (application token), як у разі надання прав за обліковими даними клієнта (client credentials grant), без refresh-токена або ID-токена. В іншому випадку це токен користувача, прив'язаного до організації застосунку. Якщо такого користувача не існує, або токену бракує necessary claim, Casdoor повертає invalid_grant.

Документ discovery містить private_key_jwt у списку token_endpoint_auth_methods_supported.

DPoP (токени з обмеженням відправника)​

Casdoor підтримує Demonstrating Proof of Possession (DPoP, RFC 9449). DPoP прив'язує access-токен до ключа, який зберігається у клієнта, тому вкрадений токен стає марним без наявності закритого ключа.

Щоб отримати токен, прив'язаний через DPoP, додайте заголовок DPoP із JWT-доказом DPoP до запиту на отримання токена:

POST /api/login/oauth/access_token
DPoP: <DPoP proof JWT>

Casdoor прив'язує токен до відкритого ключа доказу за його JWK thumbprint (jkt) та повертає значення token_type DPoP замість Bearer:

{
    "access_token": "eyJhb...",
    "token_type": "DPoP",
    "expires_in": 10080,
    "scope": "openid"
}

Запит на оновлення refresh-токена приймає той самий заголовок DPoP. Casdoor відхиляє недійсний доказ із помилкою invalid_dpop_proof. Refresh-токен, виданий із використанням DPoP, також прив'язаний до ключа: для його оновлення потрібен доказ DPoP, підписаний тим самим ключем. Без доказу або з доказом іншого ключа оновлення завершується невдало з помилкою invalid_dpop_proof. Casdoor перевіряє claim htu у доказі для оновлення щодо кінцевої точки токенів, https://<casdoor-host>/api/login/oauth/access_token.

Документ discovery перелічує алгоритми підпису, які Casdoor приймає для доказів, у полі dpop_signing_alg_values_supported:

{
    "dpop_signing_alg_values_supported": ["RS256", "RS512", "ES256", "ES384", "ES512", "PS256", "PS384", "PS512"]
}

Відповідь на запит introspection токена показує прив'язку до ключа в claim cnf.jkt (RFC 9449, розділ 8).

Перевірка access-токена​

Casdoor підтримує introspection токенів (RFC 7662). Автентифікуйте запит за допомогою базової HTTP-автентифікації, використовуючи Client ID як ім'я користувача та Client Secret як пароль:

POST /api/login/oauth/introspect HTTP/1.1
Host: CASDOOR_HOST
Accept: application/json
Content-Type: application/x-www-form-urlencoded
Authorization: Basic Y2xpZW50X2lkOmNsaWVudF9zZWNyZXQ=

token=ACCESS_TOKEN&token_type_hint=access_token

Приклад відповіді:

{
    "active": true,
    "client_id": "c58c...",
    "username": "admin",
    "token_type": "Bearer",
    "exp": 1647138242,
    "iat": 1646533442,
    "nbf": 1646533442,
    "sub": "7a6b4a8a-b731-48da-bc44-36ae27338817",
    "aud": [
        "c58c..."
    ],
    "iss": "http://localhost:8000"
}

Альтернативно, ви можете самостійно перевірити підпис токена за допомогою відкритого ключа сертифіката застосунку або ключів із JWKS endpoint. SDK роблять це у методі ParseJwtToken().

Відкликання токена​

Casdoor підтримує відкликання токенів (RFC 7009). Надішліть запит POST із параметрами форми:

POST /api/login/oauth/revoke HTTP/1.1
Host: CASDOOR_HOST
Content-Type: application/x-www-form-urlencoded
Authorization: Basic Y2xpZW50X2lkOmNsaWVudF9zZWNyZXQ=

token=REFRESH_TOKEN&token_type_hint=refresh_token
ParameterRequiredDescription
tokenТакAccess token або refresh token, який потрібно відкликати
token_type_hintНіaccess_token або refresh_token. Casdoor спочатку шукає токен як цей тип, а потім — як інший
client_idТакClient ID додатка. Надсилайте його через HTTP Basic authentication або як параметр форми
client_secretДив. описClient secret додатка. Обов'язковий для токенів, виданих через authorization code grant без PKCE, client credentials grant та token exchange grant. Публічні клієнти, що використовували PKCE, можуть надсилати лише client_id

Access token та refresh token одного grant відкликаються разом. Якщо refresh token використовується кількома access tokens (через те, що rotation refresh token вимкнено), всі вони відкликаються. Casdoor повертає HTTP 200 з пустим тілом, коли токен відкликано, термін його дії вже минув, він невідомий або належить іншому додатку. Відсутній client_id, невідомий клієнт або неправильний client secret повертають HTTP 401 з помилкою invalid_client, а відсутній token повертає HTTP 400 з помилкою invalid_request.

Використання access-токена​

Надсилайте access-токен для викликів API Casdoor. Наприклад, викличте /api/userinfo за допомогою методу GET або POST одним із двох способів:

  • З заголовком Authorization: Authorization: Bearer <access-token>
  • З параметром запиту: https://<casdoor-host>/api/userinfo?accessToken=<access-token>

Casdoor повертає поля користувача, дозволені scope токена:

{
    "sub": "7a6b4a8a-b731-48da-bc44-36ae27338817",
    "iss": "http://localhost:8000",
    "aud": "c58c..."
}

Щоб отримати більше полів, запитайте додаткові scopes у запиті авторизації.

UserInfo та get-account​

EndpointReturns
/api/userinfoThe standard OpenID Connect (OIDC) claims of the user, limited by the scopes of the token
/api/get-accountПовний об'єкт користувача акаунту, що увійшов у систему. Ця кінцева точка специфічна для Casdoor. Вона включає access-токен зовнішнього OAuth-провайдера, якщо він існує

Отримання access-токена зовнішнього провайдера​

Коли користувач входить через зовнішній OAuth-провайдер, наприклад GitHub або Google, Casdoor зберігає access-токен цього провайдера у полі originalToken об'єкта користувача. Ваш застосунок може використати його для викликів API провайдера, таких як GitHub API або Google Drive API, від імені користувача без повторного проходження OAuth-потоку.

Читайте токен із /api/get-account:

{
  "status": "ok",
  "data": {
    "name": "user123",
    "originalToken": "ya29.a0AfH6SMBx...",
    ...
  }
}

Casdoor повертає originalToken лише самому користувачу та адміністраторам. Для всіх інших запитальників це поле замасковане.
