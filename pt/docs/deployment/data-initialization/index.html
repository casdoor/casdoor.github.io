Inicializar e gerenciar dados com um arquivo

Este guia explica como carregar dados no Casdoor a partir de um arquivo JSON ou YAML, como permitir que o Casdoor mantenha seus objetos sincronizados com esse arquivo e como exportar os dados de uma instância em execução.

Resultados da aprendizagem​

  • Carregue organizações, aplicações, usuários e outros objetos quando o Casdoor iniciar.
  • Mantenha os objetos do Casdoor em um arquivo no Git e aplique alterações sem reiniciar.
  • Exporte os dados de uma instância e carregue-os em outra instância.

O que você precisa​

  • Uma instância do Casdoor e acesso ao seu conf/app.conf ou às suas variáveis de ambiente
  • Para as seções sobre Kubernetes: acesso kubectl ao cluster, ou o Helm chart

Sobre o arquivo de dados de inicialização​

Quando você distribui o Casdoor como parte de um produto maior, pode pré-carregar organizações, aplicações, usuários e outros objetos, para que o produto funcione sem configuração manual. O Casdoor lê esses objetos de um único arquivo, o arquivo de dados de inicialização.

O arquivo atende a dois propósitos:

  • Inicialização: O Casdoor carrega o arquivo uma vez, quando inicia.
  • Configuração como código: O Casdoor monitora o arquivo e aplica cada alteração enquanto está em execução. Veja Gerenciar configuração como código.

Um modelo está disponível em init_data.json.template. Um arquivo que termina em .yaml ou .yml é lido como YAML com a mesma estrutura.

Carregar dados na inicialização​

  1. Copie init_data.json.template para init_data.json no diretório onde o Casdoor é executado, e edite-o.

    Para manter o arquivo em outro lugar, defina initDataFile em conf/app.conf:

    initDataFile = /path/to/your/init_data.json

  2. Escolha o que acontece com os objetos que já existem. Defina no máximo uma das seguintes opções em conf/app.conf:

    OptionObjects that already exist
    Neither option (default)Deleted and created again from the file at every start. Changes made in the admin console are lost on restart
    initDataNewOnly = trueLeft as they are. Casdoor only adds objects that don't exist yet
    initDataMerge = trueUpdated with only the fields that the file contains. See Manage configuration as code

  3. Inicie o Casdoor.

Carregar o arquivo no Docker​

Monte o arquivo no container:

docker run ... -v /path/to/init_data.json:/init_data.json

Carregar o arquivo no Kubernetes​

Com o Helm chart, coloque os objetos sob initData.data no seu arquivo de valores e defina initData.enabled: true. Veja Gerenciar configuração como código.

Sem o chart:

  1. Armazene o arquivo em um Secret, pois ele geralmente contém senhas e segredos de cliente. Um ConfigMap também funciona.

    apiVersion: v1
    kind: Secret
    metadata:
      name: casdoor-init-data
    stringData:
      init_data.yaml: |
        organizations:
          - owner: admin
            name: acme
            displayName: Acme

  2. Monte o Secret como um diretório e aponte initDataFile para o arquivo nele:

    apiVersion: apps/v1
    kind: Deployment
    ...
    spec:
      template:
        ...
        spec:
          containers:
          ...
            env:
            - name: initDataFile
              value: /init-data/init_data.yaml
            - name: initDataMerge
              value: "true"
            - name: initDataWatchInterval
              value: "30"
            volumeMounts:
            - mountPath: /init-data
              name: casdoor-init-data-volume
              readOnly: true
          volumes:
          - secret:
              secretName: casdoor-init-data
            name: casdoor-init-data-volume
cuidado

Não monte o arquivo com subPath. O Kubernetes não atualiza uma montagem subPath quando o Secret ou ConfigMap muda, então o Casdoor nunca vê o novo conteúdo.

Gerenciar configuração como código​

Para manter organizações, aplicações, usuários, provedores, roles e permissões no Git e implantar mudanças como qualquer outra configuração, faça o Casdoor aplicar o arquivo continuamente.

  1. Defina as seguintes opções em conf/app.conf, ou passe-as como variáveis de ambiente com os mesmos nomes:

    initDataFile = ./init_data.yaml
    initDataMerge = true
    initDataWatchInterval = 30

  2. Escreva os objetos no arquivo. Por exemplo, init_data.yaml:

    organizations:
      - owner: admin
        name: acme
        displayName: Acme
        passwordType: bcrypt
    applications:
      - owner: admin
        name: app-acme
        organization: acme
        displayName: Acme Portal
        redirectUris:
          - https://portal.acme.example.com/callback
    users:
      - owner: acme
        name: alice
        displayName: Alice
        password: change-me
        signupApplication: app-acme
    roles:
      - owner: acme
        name: admins
        displayName: Admins
        users: [acme/alice]
        isEnabled: true

  3. Inicie o Casdoor. A partir de agora, o Casdoor aplica o arquivo novamente sempre que seu conteúdo mudar.

Com o Helm chart, coloque os mesmos objetos sob initData.data. O chart armazena-os em um Secret e ativa merge e watch por padrão:

initData:
  enabled: true
  data:
    organizations:
      - owner: admin
        name: acme
        displayName: Acme

Os pods em execução aplicam um helm upgrade que altera initData.data dentro de initData.watchInterval segundos, mais o tempo que o kubelet precisa para atualizar o Secret montado, que é de aproximadamente um minuto.

Como o Casdoor aplica o arquivo​

BehaviorDescription
MergeCasdoor updates an existing object with only the fields that the file contains. The other fields keep their values. The file can therefore manage a few settings of an object, such as the redirect URLs of an application, while you edit the rest in the admin console
WatchCasdoor checks the file every initDataWatchInterval seconds and applies it again when the content has changed, without a restart
PasswordsCasdoor uses the password of a user only when it creates the user, so users can change their passwords afterward. Casdoor writes organization secrets, such as masterPassword, on every apply when the file contains them
Removed objectsCasdoor doesn't delete objects that you remove from the file
Runtime dataCasdoor skips records and sessions in merge mode
ErrorsIf an object fails to apply, Casdoor logs the error once and keeps running with the objects that it applied up to that point. It retries the file on every check until the file applies
dica

Se preferir terraform plan, importação de objetos existentes e detecção de drift, use o Terraform provider. Ele gerencia os mesmos objetos através da API.

Exportar dados​

Exporte todos os dados de uma instância do Casdoor para um arquivo JSON para backup ou migração.

Exportar com o binário​

Execute o Casdoor com a flag -export. Esta é a maneira recomendada. Funciona com o binário, no Docker e no Kubernetes, e não requer a toolchain do Go.

# Export to default location (init_data_dump.json)
./casdoor -export

# Export to a custom path
./casdoor -export -exportPath /path/to/backup.json

O Casdoor inicializa a conexão com o banco de dados, escreve o arquivo e sai.

Exportar a partir do código-fonte​

Na árvore de código-fonte do Casdoor, execute:

go test ./object -v -run TestDumpToFile

O comando cria init_data_dump.json no diretório object.

Carregar a exportação em outra instância​

  1. Renomeie init_data_dump.json para init_data.json.
  2. Coloque o arquivo no diretório onde a instância alvo do Casdoor é executada.
  3. Inicie a instância alvo. Ela carrega os dados na inicialização.
