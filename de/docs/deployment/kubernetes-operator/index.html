Casdoor mit dem Kubernetes Operator ausführen

Dieser Leitfaden erklärt, wie Sie Casdoor auf Kubernetes mit dem Casdoor Operator ausführen und wie Sie Organisationen und Anwendungen als Kubernetes-Ressourcen deklarieren.

Lernziele​

  • Den Operator installieren.
  • Eine Casdoor-Instanz aus einer Casdoor-Ressource ausführen, mit SQLite für eine Testversion und mit PostgreSQL, Redis und einem Ingress für die Produktion.
  • Organisationen und Anwendungen mit CasdoorOrganization und CasdoorApplication erstellen und die Client-Anmeldedaten einer Anwendung aus einem Secret mounten.
  • Instanzen aktualisieren und entfernen.

Voraussetzungen​

  • Ein Kubernetes-Cluster, Version 1.29 oder neuer
  • kubectl
  • Für die Produktion: eine MySQL- oder PostgreSQL-Datenbank und einen Redis-Server, auf die der Cluster zugreifen kann
Möchtest du es nicht selbst betreiben?

Casdoor Cloud bietet dir eine dedizierte Casdoor-Instanz, die wir hosten und für dich aktuell halten, ab 29 USD/Monat ohne Gebühren pro Benutzer. Neue Konten erhalten ein Startguthaben von 20 USD zum Testen.

Operator oder Helm-Chart?​

Beide verwenden dasselbe Casdoor-Image.

  • Das Helm-Chart installiert eine einzelne Casdoor-Version, die über eine values-Datei konfiguriert wird. Wähle es aus, wenn du eine Instanz betreibst und sie mit Helm verwaltest.
  • Der Operator fügt dem Cluster drei Ressourcentypen hinzu. Casdoor führt eine Instanz aus; CasdoorOrganization und CasdoorApplication verwalten den Inhalt einer Instanz, und jede Anwendung erhält ein Secret mit ihrer Client-ID, ihrem Client-Secret und Zertifikat. Wähle ihn aus, wenn du mehrere Instanzen betreibst, wenn die Anwendungen, die sich bei Casdoor anmelden, im selben Cluster bereitgestellt werden, oder wenn du den Cluster mit GitOps-Tools wie Argo CD oder Flux verwaltest.

Installiere den Operator​

kubectl apply --server-side -k https://github.com/casdoor/casdoor-operator/config/default

Der Befehl installiert die drei Custom Resource Definitions und eine Cluster-Rolle und führt den Operator im Namespace casdoor-operator-system aus:

kubectl -n casdoor-operator-system get pods

Der Operator überwacht jeden Namespace. Um ihn auf einen einzelnen Namespace zu beschränken, füge --watch-namespace=<namespace> zu den Argumenten des Deployments casdoor-operator-controller-manager hinzu.

Um eine Version festzulegen, füge ?ref=<tag> zur URL hinzu und setze das Image-Tag in deiner eigenen kustomization:

kustomization.yaml
resources:
- https://github.com/casdoor/casdoor-operator/config/default?ref=v2.2.0
images:
- name: casbin/casdoor-operator
  newTag: "2.2.0"

Die Releases sind auf GitHub aufgelistet, und die Images befinden sich auf Docker Hub.

Erstelle eine Casdoor-Instanz​

  1. Erstelle ein Secret mit dem Passwort des Kontos built-in/admin:

    kubectl create secret generic casdoor-admin --from-literal=password='<password>'

  2. Erstelle eine Casdoor-Ressource. Diese führt eine einzelne Replik aus, deren Daten in einer SQLite-Datei auf einem 1Gi-Volume gespeichert werden:

    casdoor.yaml
    apiVersion: operator.casdoor.org/v1alpha1
    kind: Casdoor
    metadata:
      name: casdoor
    spec:
      database:
        driver: sqlite
        storage:
          size: 1Gi
      initAdminPasswordSecretRef:
        name: casdoor-admin
        key: password
    kubectl apply -f casdoor.yaml
    kubectl get casdoor
    NAME      READY   REPLICAS   IMAGE                   URL                               AGE
    casdoor   True    1          casbin/casdoor:4.19.0   http://casdoor.default.svc:8000   2m

  3. Öffne Casdoor:

    kubectl port-forward svc/casdoor 8000:8000

    Gehe zu http://localhost:8000 und melde dich als admin mit dem Passwort aus dem Secret an.

Der Operator erstellt ein Deployment, einen Service und das Volume. Das Passwort wird angewendet, wenn Casdoor eine leere Datenbank initialisiert, und erfordert Casdoor 4.19.0 oder neuer. Ohne initAdminPasswordSecretRef fragt Casdoor beim ersten Besuch nach dem Passwort von built-in/admin.

Betrieb von Casdoor in der Produktion​

Die folgende Instanz führt drei Repliken mit PostgreSQL für Daten, Redis für Sitzungen und einem Ingress mit TLS aus:

apiVersion: v1
kind: Secret
metadata:
  name: casdoor-credentials
stringData:
  db-password: <database password>
  admin-password: <admin password>
---
apiVersion: operator.casdoor.org/v1alpha1
kind: Casdoor
metadata:
  name: casdoor
spec:
  replicas: 3
  database:
    driver: postgres
    host: postgres.default.svc
    user: casdoor
    name: casdoor
    passwordSecretRef:
      name: casdoor-credentials
      key: db-password
  redis:
    endpoint: redis.default.svc:6379
  initAdminPasswordSecretRef:
    name: casdoor-credentials
    key: admin-password
  ingress:
    className: nginx
    host: door.example.com
    tlsSecretName: door-example-com-tls
  resources:
    requests:
      cpu: 100m
      memory: 256Mi

Was der Operator damit macht:

  • Origin: origin standardmäßig auf den Ingress-Host gesetzt, sodass der OIDC-Issuer https://door.example.com ist. Setze spec.origin, wenn Casdoor anders exponiert wird.
  • Replicas: Mehr als eine Replik erfordert redis, da Casdoor dort Sitzungen speichert; ohne dieses wird ein Benutzer abgemeldet, sobald eine Anfrage einen anderen Pod erreicht. SQLite unterstützt nur eine Replik. Der API-Server lehnt eine Casdoor-Ressource ab, die gegen eine dieser Regeln verstößt.
  • Database: Casdoor erstellt die MySQL- oder PostgreSQL-Datenbank, falls sie nicht existiert. Setze database.create: false, wenn der Datenbankbenutzer keine Datenbanken erstellen kann.
  • Secrets: Passwörter werden aus Secrets gelesen und niemals in ein ConfigMap geschrieben. Wenn du das Datenbank- oder Redis-Passwort in seinem Secret änderst, werden die Pods mit dem neuen Wert neu gestartet.
  • Availability: Bei zwei oder mehr Repliken fügt der Operator eine PodDisruptionBudget hinzu. Die Casdoor-Ressource hat eine scale-Subresource, sodass kubectl scale casdoor casdoor --replicas=5 und ein HorizontalPodAutoscaler darauf funktionieren.
  • Health: Die Probes verwenden /api/health. Die Bedingung Ready wechselt auf True, wenn jede Replik der aktuellen Version verfügbar ist.

Konfigurieren der Instanz​

FieldDescription
imageCasdoor image. Defaults to the version the operator was released with.
replicasNumber of pods, 1 by default.
originPublic URL, used as the OIDC issuer.
database.drivermysql, postgres or sqlite.
database.host, port, name, user, sslModeConnection settings. name defaults to casdoor.
database.passwordSecretRefSecret key holding the database password.
database.dataSourceNameSecretRefSecret key holding a complete dataSourceName, which replaces the fields above.
database.createCreate the MySQL or PostgreSQL database if it is missing. true by default.
database.storageVolume for the SQLite file. Without it, the file lives in an emptyDir and is lost with the pod. The volume is kept when the Casdoor resource is deleted.
redis.endpoint, passwordSecretRef, dbSession store. Several addresses separated by ; use Redis Cluster.
initAdminPasswordSecretRefPassword of built-in/admin for a new database.
apiCredentialsSecretRefCredentials the operator uses to call the Casdoor API. See API credentials.
initData.secretRef, newOnlySecret key holding an init data file. With newOnly, the default, objects that already exist are left alone.
configOther configuration items, such as defaultLanguage: zh. Items covered by the fields above are ignored.
envExtra environment variables for the Casdoor container, applied last.
service.type, port, annotationsService settings. Port 8000 by default.
ingress.host, className, tlsSecretName, annotationsCreates an Ingress when set.
resources, nodeSelector, tolerations, affinity, topologySpreadConstraints, priorityClassName, serviceAccountName, imagePullSecrets, podLabels, podAnnotationsPassed to the pod.

Führe kubectl explain casdoor.spec aus, um das vollständige Schema anzuzeigen.

Verwalten von Organisationen und Anwendungen​

API-Anmeldeinformationen​

Um Objekte in einer Instanz zu erstellen, ruft der Operator die Casdoor-API mit der Client-ID und dem Client-Secret von app-built-in auf, der Anwendung der Organisation built-in, die jede Organisation verwalten kann.

  • Mit initAdminPasswordSecretRef meldet sich der Operator einmalig als built-in/admin an, nachdem er zum ersten Mal gestartet wurde, liest die Anmeldeinformationen von app-built-in und speichert sie im Secret <name>-api-credentials. Danach verwendet er das Passwort nicht mehr.
  • Wenn das Passwort geändert wurde, bevor sich der Operator angemeldet hat, oder du möchtest es ihm nicht geben, kopiere die Client-ID und das Client-Secret von app-built-in aus der Admin-Konsole in ein Secret mit den Schlüsseln clientId und clientSecret und zeige spec.apiCredentialsSecretRef darauf.

Die Bedingung APIReady der Casdoor-Ressource zeigt an, ob die Anmeldeinformationen verfügbar sind:

kubectl get casdoor casdoor -o jsonpath='{.status.conditions[?(@.type=="APIReady")].message}'

Wenn das Passwort falsch ist, versucht der Operator alle 5 Minuten erneut, was unterhalb der Anzahl fehlgeschlagener Anmeldungen liegt, die das Konto sperrt.

Erstelle eine Organisation und eine Anwendung​

apiVersion: operator.casdoor.org/v1alpha1
kind: CasdoorOrganization
metadata:
  name: acme
spec:
  casdoorRef:
    name: casdoor
  displayName: ACME Corp
  websiteUrl: https://acme.example.com
  passwordType: bcrypt
  languages: [en, zh]
---
apiVersion: operator.casdoor.org/v1alpha1
kind: CasdoorApplication
metadata:
  name: acme-portal
spec:
  casdoorRef:
    name: casdoor
  organization: acme
  displayName: ACME Portal
  redirectUris:
  - https://portal.acme.example.com/callback
  grantTypes: [authorization_code, refresh_token]
  tokenFormat: JWT-Standard
  expireInHours: 24
  cert: cert-built-in
kubectl get casdoororg,casdoorapp
NAME                                            CASDOOR   READY   AGE
casdoororganization.operator.casdoor.org/acme   casdoor   True    10s

NAME                                                  CASDOOR   ORGANIZATION   CLIENT ID              READY   AGE
casdoorapplication.operator.casdoor.org/acme-portal   casdoor   acme           44f1aa1fbe1afc436140   True    10s

casdoorRef.name ist der Name einer Casdoor-Ressource im selben Namespace. name setzt den Namen des Objekts in Casdoor, wenn er sich vom Namen der Kubernetes-Ressource unterscheidet.

Verwenden der Anmeldeinformationen einer Anwendung​

Für jede Anwendung schreibt der Operator ein Secret namens <name>-casdoor oder den Namen in credentialsSecretName mit den Schlüsseln endpoint, clientId, clientSecret, organizationName, applicationName und certificate. Die Schlüssel entsprechen den Einstellungen der Casdoor-SDKs, sodass eine Anwendung im Cluster sie aus Umgebungsvariablen lesen kann:

containers:
- name: portal
  image: example/portal
  envFrom:
  - secretRef:
      name: acme-portal-casdoor
    prefix: CASDOOR_

Casdoor generiert die Client-ID und das Client-Secret, es sei denn, du setzt clientId oder clientSecretSecretRef. Der endpoint ist der Origin der Instanz oder ihre Service-Adresse, wenn sie keinen Origin hat.

Verstehen, welche Felder der Operator schreibt​

  • Felder in der Spec: Sie behalten die Namen der Casdoor-API. Der Operator schreibt sie an Casdoor und stellt sie innerhalb von 10 Minuten wieder her, wenn sie in der Admin-Konsole bearbeitet werden.

  • Felder, die nicht in der Spec festgelegt sind: Sie behalten ihre Werte in Casdoor, sodass Sie sie in der Admin-Konsole bearbeiten können. Legen Sie alle Felder ohne dediziertes Spec-Feld, wie signinMethods, providers oder mfaItems, in extraFields fest:

    spec:
      extraFields:
        enableSigninSession: true
        signinMethods:
        - name: Password
          displayName: Password
          rule: All

  • Bereits vorhandene Objekte: Eine Ressource mit dem Namen eines vorhandenen Objekts übernimmt dieses und schreibt nur die Felder in ihrer Spec.

  • Löschung: Das Löschen einer CasdoorApplication löscht die Anwendung in Casdoor. Das Löschen einer CasdoorOrganization belässt die Organisation und ihre Benutzer in Casdoor, es sei denn, die Ressource hat deletionPolicy: Delete.

Einen Casdoor-Server verwenden, den der Operator nicht ausführt​

CasdoorOrganization und CasdoorApplication funktionieren auch mit einem Casdoor-Server außerhalb des Clusters, z. B. einer Casdoor Cloud-Instanz. Platzieren Sie die Client-ID und das Client-Secret einer Anwendung seiner built-in-Organisation in einem Secret und verwenden Sie casdoorRef.external:

apiVersion: v1
kind: Secret
metadata:
  name: door-api
stringData:
  clientId: <client ID of app-built-in>
  clientSecret: <client secret of app-built-in>
---
apiVersion: operator.casdoor.org/v1alpha1
kind: CasdoorApplication
metadata:
  name: grafana
spec:
  casdoorRef:
    external:
      endpoint: https://door.example.com
      credentialsSecretRef:
        name: door-api
  organization: acme
  redirectUris:
  - https://grafana.example.com/login/generic_oauth

LDAP​

Der Service exposes den LDAP-Server von Casdoor auf Port 389. Innerhalb der Pod lauscht Casdoor auf Port 10389, da die Pod als Benutzer 1000 ausgeführt wird und einige Container-Runtimes das Binden von Ports unter 1024 nicht erlauben. Um einen anderen Port innerhalb der Pod zu verwenden, setzen Sie ldapServerPort in config.

Casdoor aktualisieren​

Ändern Sie spec.image oder aktualisieren Sie den Operator, um ein neueres Standard-Image zu erhalten. Der Operator rollt die Pods nacheinander; bei SQLite stoppt er den alten Pod, bevor er den neuen startet, da zwei Prozesse dieselbe Datenbankdatei nicht öffnen können. Casdoor aktualisiert das Datenbankschema beim Start. Bevor Sie von Version 3 zu Version 4 wechseln, lesen Sie Upgrade from v3 to v4.

Deinstallation​

  1. Löschen Sie die CasdoorApplication- und CasdoorOrganization-Ressourcen, während der Operator noch läuft, damit er ihre Finalizer entfernen kann:

    kubectl delete casdoorapplications,casdoororganizations --all -A

  2. Löschen Sie die Instanzen und das SQLite-Volume, wenn Sie die Daten nicht benötigen:

    kubectl delete casdoor casdoor
    kubectl delete pvc casdoor-data

  3. Entfernen Sie den Operator:

    kubectl delete -k https://github.com/casdoor/casdoor-operator/config/default
