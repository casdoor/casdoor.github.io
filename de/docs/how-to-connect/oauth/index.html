OAuth 2.0

Casdoor ist ein OAuth 2.0-Autorisierungsserver. Diese Seite beschreibt, wie Sie mit jedem Grant-Typ ein Access Token erhalten, wie Sie ein Token verifizieren und wie Sie es verwenden. Wenn Sie die Endpunkte nicht selbst aufrufen möchten, verwenden Sie ein Casdoor SDK oder einen standardmäßigen OIDC-Client.

Endpunkte​

EndpointURL
Authorizationhttps://<casdoor-host>/login/oauth/authorize
Tokenhttps://<casdoor-host>/api/login/oauth/access_token
Refresh tokenhttps://<casdoor-host>/api/login/oauth/refresh_token
Token introspectionhttps://<casdoor-host>/api/login/oauth/introspect
UserInfohttps://<casdoor-host>/api/userinfo

In den Beispielen sind ClientId und ClientSecret die Client ID und das Client secret der Casdoor-Anwendung.

Unterstützte Grant-Typen​

Grant TypeRFCUse Case
Authorization CodeRFC 6749 §4.1Default; web/mobile apps with a backend. Enabled by default.
ImplicitRFC 6749 §4.2Frontend-only apps without a backend.
Resource Owner PasswordRFC 6749 §4.3Apps with no frontend redirect; user credentials sent directly.
Client CredentialsRFC 6749 §4.4Service-to-service calls with no user involved.
Refresh TokenRFC 6749 §6Renew an access token without re-authenticating.
Device AuthorizationRFC 8628Devices with limited input or no browser.
Token ExchangeRFC 8693Swap an existing token for one with different scope or audience.
JWT BearerRFC 7523Service auth using a signed JWT assertion instead of a client secret.
Verification CodeCasdoor extensionNative apps that sign users in (and up) with a code sent by SMS or email.
Mobile One-ClickCasdoor-ErweiterungNative Apps, bei denen sich Benutzer über die Telefonnummer des Geräts anmelden (und registrieren), durch Alibaba Cloud PNVS.

Der Authorization Code Grant ist standardmäßig aktiviert. Aktivieren Sie andere Grant-Typen unter Grant types auf der Bearbeitungsseite der Anwendung.

Authorization Code Grant​

Verwenden Sie diesen Grant für Anwendungen, bei denen sich Benutzer über den Browser anmelden. Dies ist der empfohlene Grant.

  1. Leiten Sie den Benutzer zum Autorisierungsendpunkt um:

    https://<CASDOOR_HOST>/login/oauth/authorize?
    client_id=CLIENT_ID&
    redirect_uri=REDIRECT_URI&
    response_type=code&
    scope=openid&
    state=STATE

  2. Der Benutzer meldet sich an. Casdoor leitet den Browser mit einem Autorisierungscode an Ihre Redirect URL um:

    https://REDIRECT_URI?code=CODE&state=STATE&iss=ISSUER

    iss ist die Issuer URL von Casdoor, wie in RFC 9207 definiert. Vergleichen Sie sie mit dem issuer im Discovery Document, um sicherzustellen, dass die Antwort vom Casdoor-Server stammt, an den Sie den Benutzer weitergeleitet haben. Casdoor fügt iss zu jeder Autorisierungsantwort und zu jedem Fehler hinzu, der an die Redirect URL zurückgesendet wird; das Discovery Document kündigt dies mit "authorization_response_iss_parameter_supported": true an.

  3. Tauschen Sie den Code gegen Tokens aus. Senden Sie eine POST-Anfrage an den Token-Endpunkt:

    https://<CASDOOR_HOST>/api/login/oauth/access_token

    Mit dem Body:

    {
        "grant_type": "authorization_code",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "code": Code,
    }

  4. Lesen Sie die Tokens aus der Antwort:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Ein Autorisierungscode ist 5 Minuten gültig und funktioniert nur einmal. Ein zweiter Austausch desselben Codes schlägt mit invalid_grant und der Beschreibung authorization code has been used for token: [...] fehl.

Die Antworten des Token-Endpunkts und des Refresh-Token-Endpunkts enthalten die Header Cache-Control: no-store und Pragma: no-cache, damit kein Cache die Tokens speichert.

Berechtigungsbereiche​

Fordern Sie Scopes mit dem Parameter scope der Autorisierungs-URL an. Sie bestimmen, welche Benutzerfelder die Tokens und der UserInfo-Endpunkt zurückgeben.

BereichBeschreibung
openid (default)sub, iss, aud
profilename, displayName, avatar
emailemail
addressaddress (OIDC object in JWT-Standard; see OIDC address claim)
phonetelefonnummer

Trennen Sie mehrere Scopes mit %20:

https://<CASDOOR_HOST>/login/oauth/authorize?
client_id=...&
scope=openid%20email

Informationen zu den Claims hinter jedem Scope finden Sie in der OpenID Connect-Spezifikation.

PKCE​

Casdoor unterstützt Proof Key for Code Exchange (PKCE), was den Autorisierungscode öffentlicher Clients wie mobiler und Single-Page-Anwendungen schützt.

  1. Generieren Sie einen zufälligen Code Verifier mit 43 bis 128 Zeichen.

  2. Berechnen Sie den Code Challenge: den Base64-URL-kodierten SHA-256-Hash des Verifiers.

  3. Fügen Sie zwei Parameter zur Autorisierungs-URL hinzu:

    &code_challenge_method=S256&code_challenge=YOUR_CHALLENGE

  4. Fügen Sie den Parameter code_verifier mit dem ursprünglichen Verifier zur Token-Anfrage hinzu.

Bei Verwendung von PKCE ist client_secret in der Token-Anfrage optional. Wenn Sie es senden, muss es korrekt sein.

Notiz

Wenn Casdoor selbst Benutzer bei einem externen OAuth-Provider anmeldet, der PKCE erfordert, wie Twitter oder ein benutzerdefinierter Provider mit aktiviertem PKCE, generiert Casdoor den Code Verifier für jeden Flow. Sie müssen PKCE für diesen Teil nicht implementieren.

Token an einen Dienst binden​

Wenn Ihre Anwendung mehrere Backend-Dienste aufruft, können Sie ein Token an einen dieser Dienste binden, sodass ein für einen Dienst ausgestelltes Token nicht bei einem anderen verwendet werden kann. Casdoor unterstützt hierfür Resource Indicators (RFC 8707).

  1. Fügen Sie den Parameter resource mit einer absoluten URI, die den Dienst identifiziert, zur Autorisierungs-URL hinzu:

    https://<CASDOOR_HOST>/login/oauth/authorize?
    client_id=CLIENT_ID&
    redirect_uri=REDIRECT_URI&
    response_type=code&
    scope=openid&
    state=STATE&
    resource=https://api.example.com

  2. Senden Sie dieselbe resource in der Token-Anfrage:

    {
        "grant_type": "authorization_code",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "code": Code,
        "resource": "https://api.example.com"
    }

Der aud-Claim (Audience) des Access Tokens ist dann die Resource URI und nicht die Client ID. Der Dienst überprüft, ob ein Token für ihn ausgestellt wurde, indem er aud prüft. Der Wert von resource muss in beiden Anfragen exakt gleich sein.

Casdoor übergibt den resource-Parameter während der interaktiven Anmeldung. Wenn der Benutzer ein Passwort eingeben, Multi-Faktor-Authentifizierung (MFA) abschließen, WebAuthn nutzen oder die Consent-Seite genehmigen muss, bleibt der Parameter während der Weiterleitungen erhalten. Er wird auch beibehalten, wenn Casdoor den Benutzer automatisch mit einer bestehenden Sitzung anmeldet.

Beim Aktualisieren des Tokens behält das neue Access Token das aud des ursprünglichen Grants. Sie können resource in der Refresh-Anfrage wiederholen, entweder als Query-Parameter oder als Feld im Body. Wenn Sie dies tun, muss es derselbe Wert wie im ursprünglichen Grant sein. Andernfalls gibt Casdoor invalid_grant mit der Beschreibung resource parameter does not match the original grant zurück.

Anmeldeseite mit Provider-Hinweis überspringen​

Um den Benutzer direkt zu einem OAuth-Provider zu leiten, ohne die Casdoor-Anmeldeseite anzuzeigen, fügen Sie provider_hint=<provider-name> zur Autorisierungs-URL hinzu:

https://<CASDOOR_HOST>/login/oauth/authorize?
client_id=CLIENT_ID&
redirect_uri=REDIRECT_URI&
response_type=code&
scope=openid&
state=STATE&
provider_hint=github

Casdoor liefert dann eine kleine Umleitungsseite, ohne das vollständige Frontend zu laden, und leitet den Benutzer zum Provider weiter. Dies verkürzt die Zeit bis zur Weiterleitung auf langsamen Geräten und Verbindungen.

Registrierung im Autorisierungsflow​

Ein Benutzer, der während des Autorisierungsflows ein Konto erstellt, wird sofort nach Abschluss der Registrierung mit einem Autorisierungscode an Ihre Redirect URL weitergeleitet, genau wie nach einer Anmeldung. Casdoor übergibt die Autorisierungsparameter wie client_id, response_type und redirect_uri durch die Registrierung hindurch. Ihre Anwendung benötigt dafür keine Änderungen.

Steuern der Anmelde-Aufforderung​

Standardmäßig kann ein Benutzer, der bereits eine Casdoor-Sitzung hat, angemeldet werden, ohne erneut Anmeldedaten einzugeben. Fügen Sie die OpenID Connect-Parameter prompt und max_age zur Autorisierungs-URL hinzu, um dies zu ändern:

ParameterEffect
prompt=loginThe user must enter credentials again, even with an existing session
max_age=<seconds>Der Benutzer muss seine Anmeldedaten erneut eingeben, wenn er sie vor mehr als <seconds> Sekunden zum letzten Mal eingegeben hat oder wenn Casdoor nicht weiß, wann er dies getan hat
prompt=noneCasdoor shows no page. It signs the user in with the existing session, or sends an error back to the redirect URL

prompt akzeptiert eine durch Leerzeichen getrennte Liste von Werten. Wenn die vorhandene Sitzung prompt=login oder max_age nicht erfüllt, schlägt die Anmeldung mit dieser Sitzung mit login_required und der Meldung Please sign in again fehl. Die Zeit, zu der der Benutzer seine Anmeldedaten eingegeben hat, befindet sich im auth_time-Claim des ID-Tokens.

Verwenden Sie prompt=none, um beispielsweise aus einem ausgeblendeten iframe heraus zu prüfen, ob der Benutzer noch angemeldet ist. Casdoor überspringt dann die automatische Weiterleitung an einen einzelnen Anbieter und antwortet auf dieselbe Weise wie eine erfolgreiche Antwort gehen würde, mit state und iss, sowie mit einem dieser Fehler:

ErrorReason
login_requiredNo Casdoor session, the user of the session isn't in the organization of the application, or the session doesn't satisfy max_age
consent_requiredThe user must approve the consent page first
interaction_requiredThe user must update the password, set up or complete MFA, select a plan, or fill in the prompt page first
access_deniedThe sign-in failed for another reason. error_description says why
server_errorThe request to Casdoor failed

Implicit Grant​

Verwenden Sie diesen Grant nur für Anwendungen ohne Backend. Bevorzugen Sie den Authorization Code Grant mit PKCE.

  1. Aktivieren Sie in Grant types der Anwendung Token, um ein Access Token zurückzugeben, ID Token, um ein ID-Token zurückzugeben, oder beide.

  2. Leiten Sie den Benutzer weiter zu:

    https://<CASDOOR_HOST>/login/oauth/authorize?client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&response_type=token&scope=openid&state=STATE

  3. Nachdem sich der Benutzer angemeldet hat, leitet Casdoor den Browser weiter zu:

    https://REDIRECT_URI#access_token=ACCESS_TOKEN&token_type=Bearer&state=STATE&iss=ISSUER

response_type kann token, id_token oder id_token token sein. Der Autorisierungsendpunkt gibt niemals ein Refresh Token zurück. Wenn der Grant Type, den ein Response Type benötigt, nicht aktiviert ist, zeigt Casdoor Grant_type: token is not supported in this application (oder id_token) an.

Wenn scope openid enthält und die Antwort ein ID-Token enthält, senden Sie einen nonce-Parameter. Casdoor kopiert ihn in das ID-Token und verweigert die Anfrage ohne ihn: The nonce parameter is required for this response type.

Vorsicht

Der Implicit Grant am Token-Endpunkt (grant_type=token mit einem Benutzernamen und einem Passwort) erfordert einen Benutzer mit einem lokalen Passwort. Benutzer, die nur über einen externen Anbieter erstellt wurden und kein lokales Passwort haben, können ihn nicht verwenden und erhalten invalid_grant. Es gelten dieselben Regeln wie für den Password Grant. Verwenden Sie den Authorization Code Grant für diese Benutzer.

Hybrid Flow​

Im OpenID Connect Hybrid Flow gibt der Autorisierungsendpunkt einen Authorization Code zusammen mit Tokens zurück. Ihr Frontend kann die Tokens sofort verwenden, und Ihr Backend tauscht den Code wie im Authorization Code Grant aus.

response_type ist eine durch Leerzeichen getrennte Kombination aus code, token und id_token. Die Hybrid-Werte sind:

response_typeThe authorization endpoint returns
code id_tokencode and id_token
code tokencode and access_token
code token id_tokencode, access_token und id_token

  1. Aktivieren Sie in Grant types der Anwendung Token für einen Response Type, der token enthält, und ID Token für einen, der id_token enthält.

  2. Leiten Sie den Benutzer zum Autorisierungsendpunkt mit dem Response Type und einem nonce weiter:

    https://<CASDOOR_HOST>/login/oauth/authorize?client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&response_type=code%20id_token&scope=openid&state=STATE&nonce=NONCE

    nonce ist erforderlich, wenn scope openid enthält und der Response Type id_token enthält oder code token ist.

  3. Nachdem sich der Benutzer angemeldet hat, leitet Casdoor den Browser zu Ihrer Redirect URL weiter. Die Werte befinden sich im Fragment, es sei denn, Sie fordern einen anderen Response Mode an.

  4. Tauschen Sie den Code am Token-Endpunkt aus. Nur dieser Austausch gibt ein Refresh Token zurück.

Das ID-Token trägt diese Claims der OpenID Connect-Spezifikation:

ClaimWhen it's present
auth_timeWhen Casdoor knows the time at which the user last entered credentials
at_hashWhen the ID token comes with an access token, and in the ID token of the authorization code grant
c_hashWhen the ID token comes with an authorization code

at_hash und c_hash verwenden SHA-256, oder SHA-384 bzw. SHA-512, wenn die Token signing method der Anwendung mit 384 oder 512 endet. Verifizieren Sie sie so, wie die OpenID Connect-Spezifikation es beschreibt.

Response Modes​

response_mode bestimmt, wie Casdoor die Autorisierungsantwort oder den Fehler an die Redirect URL sendet:

response_modeDeliveryDefault for
queryIn the query stringresponse_type=code
fragmentIn the fragment, after #Every response type that returns a token
form_postIn a form that the browser submits to the redirect URL with POSTNone

Casdoor setzt niemals Tokens in die Query String. Eine Antwort, die ein Token enthält, geht ins Fragment, auch bei response_mode=query. Die Antwort enthält state und iss, sowie token_type=Bearer, wenn sie ein Access Token enthält. Bei form_post sind sie Felder des Formulars. Die Anmelde-Seite und die Zustimmungs-Seite unterstützen alle drei Modi.

Mit aktivierter Option Auto signin meldet Casdoor einen Benutzer, der eine Sitzung hat, an, ohne die Anmelde-Seite zu laden, nur für response_type=code mit leerem response_mode oder query. Andere Anfragen laden die Anmelde-Seite, die dann die Anmeldung abschließt.

Device Grant​

Verwenden Sie diesen Grant für Geräte mit eingeschränkter Eingabe oder ohne Browser, wie Smart TVs und CLI-Tools.

  1. Aktivieren Sie den Device Grant in Grant types der Anwendung.
  2. Senden Sie eine Anfrage an den device_authorization_endpoint aus dem Discovery Document.
  3. Zeigen Sie die verification_uri aus der Antwort dem Benutzer an, als Text oder als QR-Code.
  4. Der Benutzer öffnet die URL auf einem anderen Gerät, gibt den User Code ein und meldet sich an. Casdoor stellt die Seite hinter verification_uri bereit, sodass Sie keine UI dafür erstellen müssen.
  5. Währenddessen pollt das Gerät den Token-Endpunkt mit seinem device_code, bis der Benutzer sich angemeldet hat. Siehe RFC 8628, Abschnitt 3.4.

Sie können die Geräte-Anmeldung auch als Anmelde-Methode in der Tabelle Signin methods der Anwendung anbieten.

Benutzern ermöglichen, sich durch Scannen eines QR-Codes bei Ihrer Website anzumelden​

Derselbe Flow ermöglicht es Benutzern, die in Ihrer nativen App angemeldet sind, sich bei Ihrer Website anzumelden, indem sie einen QR-Code mit der App scannen.

  1. Fügen Sie in der Casdoor Admin Console Device login zu den Signin methods der Anwendung hinzu, mit der Regel Login page.
  2. Aktivieren Sie Device Code in Grant types.

Die Anmeldeseite zeigt jetzt einen QR-Code neben dem Formular an und schließt die Anmeldung selbstständig ab, sobald der QR-Code genehmigt wurde.

Der QR-Code enthält den verification_uri, zum Beispiel https://<casdoor-host>/login/oauth/device/ra91hy?cancelToken=.... Ein Benutzer, der ihn mit der Kamera eines Telefons scannt, öffnet die URL im Browser, meldet sich an und genehmigt dort. Ihre App kann stattdessen direkt genehmigen, mit dem Zugriffstoken, das sie bereits besitzt:

  1. Entnehmen Sie den Benutzercode aus dem Pfad der URL. Im Beispiel ist er ra91hy.

  2. Zeigen Sie dem Benutzer an, bei welchem Dienst er sich anmelden wird.

  3. Senden Sie eine POST-Anfrage an https://<casdoor-host>/api/login mit dem Header Authorization: Bearer <access-token> und dem Body:

    {
        "application": ApplicationName,
        "organization": OrganizationName,
        "type": "device",
        "userCode": "ra91hy"
    }

Um die Anmeldung abzulehnen, senden Sie userCode und das cancelToken aus derselben URL als Query-Parameter an https://<casdoor-host>/api/cancel-device-auth.

Gerätezugriffsberechtigung mit mehreren Replikaten​

Standardmäßig speichert Casdoor ausstehende Geräte-Autorisierungsanfragen, die Gerätecodes auf Benutzercodes abbilden, im Speicher. Bei mehreren Replikaten von Casdoor können die Abfragelanfrage des Geräts und die Bestätigung im Browser unterschiedliche Replikate erreichen, wodurch der Ablauf dann intermittierend fehlschlägt.

Um die Anfragen zwischen Replikaten zu teilen, setzen Sie redisEndpoint in conf/app.conf. Casdoor speichert sie dann in Redis. Dies ist dieselbe Option, die Sitzungen teilt, im Format host:port[,poolSize[,password[,db]]], zum Beispiel localhost:6379,100,mypassword,2, und es sind keine weiteren Optionen erforderlich. Mehrere Adressen im ersten Feld, getrennt durch ;, verwenden Redis Cluster. Wenn Casdoor Redis beim Start nicht erreichen kann, protokolliert es eine Warnung und verwendet den In-Memory-Speicher. Siehe Konfigurationsreferenz.

Resource Owner Password Credentials Grant​

Verwenden Sie diese Berechtigung nur, wenn Ihre Anwendung den Benutzer nicht zu Casdoor umleiten kann und Benutzername und Passwort selbst erfasst.

  1. Aktivieren Sie die Passwort-Berechtigung unter Grant types der Anwendung.

  2. Senden Sie eine POST-Anfrage an den Token-Endpunkt:

    https://<CASDOOR_HOST>/api/login/oauth/access_token

    Mit dem Body:

    {
        "grant_type": "password",
        "client_id": ClientId,
        "client_secret": ClientSecret,
        "username": Username,
        "password": Password,
    }

  3. Lesen Sie die Tokens aus der Antwort:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Wenn Casdoor die Passwort-Berechtigung ablehnt​

Ein alleiniges Passwort würde die Prüfungen der Anmeldeseite umgehen. Casdoor lehnt daher die Passwort-Berechtigung und die implizite Berechtigung am Token-Endpunkt mit invalid_grant in diesen Fällen ab:

Caseerror_description
The user has MFA enabledthe user has MFA enabled and cannot sign in with a password grant, please use the authorization code flow
The organization has turned off sign-inThe organization: <organization> has disabled users to signin
The user must change the password, or must set up MFA that the organization requiresthe user: <organization>/<user> must update the password or set up MFA on the login page first
The user has no local password, for example a user created through an external providerOAuth users cannot use password grant type, please use authorization code flow

Die anderen Anmeldebeschränkungen der Anwendung und der Organisation, wie IP-Beschränkungen, gelten ebenfalls. Ein Benutzer, der sein Passwort ändern oder MFA einrichten muss, tut dies zuerst auf der Anmeldeseite, wonach die Passwort-Berechtigung wieder funktioniert.

Verifizierungscode-Berechtigung​

Verwenden Sie diese Berechtigung in nativen Apps, die Benutzer mit einer Telefonnummer oder E-Mail-Adresse und einem einmaligen Code anmelden, ohne einen Browser zu öffnen. Es ist eine Erweiterungs-Berechtigung von Casdoor, wie in RFC 6749, Abschnitt 4.5 erlaubt. Wenn die Anwendung dies zulässt, wird eine Adresse, die noch kein Konto hat, im selben Schritt registriert.

  1. Aktivieren Sie Verification Code unter Grant types der Anwendung und fügen Sie der Anwendung einen SMS-Anbieter, einen E-Mail-Anbieter oder beide hinzu.

  2. Senden Sie den Code. Senden Sie eine POST-Anfrage mit Formulardaten an https://<casdoor-host>/api/send-verification-code:

    FieldValue
    applicationIdadmin/<APPLICATION_NAME>
    typephone or email
    destThe phone number or email
    countryCodeThe region of a phone number, e.g. CN or US. Not needed for an E.164 number like +8613800000000
    methodlogin
    captchaTypenone, or the captcha type and captchaToken when the application's captcha provider asks for one

  3. Tauschen Sie den Code gegen Tokens. Senden Sie eine POST-Anfrage an https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "urn:casdoor:params:oauth:grant-type:verification-code",
        "client_id": ClientId,
        "username": "+8613800000000",
        "code": "123456",
        "scope": "openid profile"
    }

    username ist die Telefonnummer oder E-Mail-Adresse, an die der Code gesendet wurde. Für eine Telefonnummer im nationalen Format senden Sie auch country_code.

Die Berechtigung benötigt kein Client-Secret, funktioniert also von einem öffentlichen Client. Die Antwort ist dieselbe wie für die anderen Berechtigungen und enthält ein refresh_token, das den Benutzer angemeldet hält.

Falsche Codes zählen gegen die Failed signin limit der Anwendung. Casdoor lehnt Benutzer ab, die MFA aktiviert haben. Verwenden Sie für sie die Autorisierungscode-Berechtigung.

Neue Benutzer mit einem Verifizierungscode registrieren​

Wenn kein Benutzer die Telefonnummer oder E-Mail-Adresse hat, erstellt die Berechtigung den Benutzer, so wie die Registrierungsseite es tun würde, wenn alle folgenden Bedingungen erfüllt sind:

  • Enable signup ist für die Anwendung aktiviert und Disable self signup ist deaktiviert.
  • Die Signup items der Anwendung verlangen nichts über das hinaus, was der Code beweist. Nur ID, Username, Display name, Password, Confirm password, Agreement, Signup button und Providers dürfen erforderlich sein, plus Email, wenn sich der Benutzer mit einer E-Mail-Adresse registriert, oder Phone, wenn sich der Benutzer mit einer Telefonnummer registriert. Die Standard-Registrierungsfelder erfordern sowohl Email als auch Phone, machen Sie also das andere optional.
  • Für eine Telefonnummer muss ihre Region in den Supported country codes der Organisation enthalten sein.

Andernfalls antwortet /api/send-verification-code, dass der Benutzer nicht existiert, und nur vorhandene Benutzer können sich anmelden.

Mobile One-Click Grant​

Native Apps in Festlandchina können Benutzer auch mit der Telefonnummer des Geräts anmelden, ohne einen SMS-Code: Das One-Click-Login-SDK von Alibaba Cloud PNVS gibt ein Token zurück, und die App tauscht es mit dem Grant-Typ urn:casdoor:params:oauth:grant-type:mobile-one-click. Siehe Mobile One-Click Login.

Client Credentials Grant​

Verwenden Sie diese Berechtigung für Machine-to-Machine-Aufrufe, bei denen kein Benutzer vorhanden ist.

  1. Aktivieren Sie die Client-Credentials-Berechtigung unter Grant types der Anwendung.

  2. Senden Sie eine POST-Anfrage an https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "client_credentials",
        "client_id": ClientId,
        "client_secret": ClientSecret,
    }

  3. Lesen Sie das Token aus der Antwort:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Im Gegensatz zu den Tokens der oben genannten Berechtigungen gehört dieses Zugriffstoken zur Anwendung und nicht zu einem Benutzer.

Refresh Token Grant​

Verwenden Sie das Refresh-Token aus einer früheren Antwort, um ein neues Access-Token zu erhalten.

  1. Legen Sie die Lebensdauer von Refresh-Tokens in Refresh token expire der Anwendung fest. Der Standardwert ist 0 Stunden.

  2. Senden Sie eine POST-Anfrage an https://<casdoor-host>/api/login/oauth/refresh_token:

    {
        "grant_type": "refresh_token",
        "refresh_token": REFRESH_TOKEN,
        "scope": SCOPE,
        "client_id": ClientId,
        "client_secret": ClientSecret,
    }

  3. Lesen Sie die Tokens aus der Antwort:

    {
        "access_token": "eyJhb...",
        "id_token": "eyJhb...",
        "refresh_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Casdoor prüft die Refresh-Anforderung wie folgt:

  • Wenn das Token durch einen Austausch eines Autorisierungs-Codes ausgestellt wurde, bei dem ein client_secret gesendet wurde, oder durch einen Token-Austausch, muss die Refresh-Anforderung das korrekte client_secret enthalten. Andernfalls gibt Casdoor invalid_client zurück. Ein öffentlicher Client, der PKCE ohne Secret verwendet hat, erneuert sich auch ohne dieses.
  • Das Refresh-Token muss zur anfragenden Anwendung gehören. Andernfalls gibt Casdoor invalid_grant mit the token is for wrong application (client_id) zurück.
  • Ein scope in der Anfrage muss eine Teilmenge des ursprünglichen Scopes sein. Wenn Sie ihn weglassen, erhält das neue Token den ursprünglichen Scope.
  • Ein unbekanntes oder widerrufenes Refresh-Token schlägt mit invalid_grant und refresh token is invalid or revoked fehl. Ein Refresh-Token, das Casdoor invalidiert hat, beispielsweise beim Abmelden, schlägt mit invalid_grant und refresh token is expired fehl.

Die Umbenennung eines Benutzers macht die Refresh-Tokens des Benutzers nicht ungültig. Für Ereignisse, die Tokens tatsächlich widerrufen, siehe When Casdoor revokes tokens.

Rotation von Refresh-Tokens​

Standardmäßig gibt jeder Refresh ein neues Refresh-Token zurück und widerruft das verwendete, wie es RFC 9700 für öffentliche Clients empfiehlt. Speichern Sie das neue Refresh-Token nach jedem Refresh. Ein bereits verwendetes Refresh-Token schlägt mit invalid_grant fehl.

Die Rotation unterbricht Clients, in denen mehrere Prozesse ein gemeinsames Refresh-Token verwenden, beispielsweise eine CLI, die parallele Jobs mit einem Token aus einer Umgebungsvariable ausführt: Der erste Refresh widerruft das Token für alle anderen. Aktivieren Sie für solche Clients Disable refresh token rotation in den OIDC/OAuth-Einstellungen der Anwendung. Dann gilt:

  • Ein Refresh gibt dasselbe Refresh-Token zurück, das seine ursprüngliche Ablaufzeit behält.
  • Die Access-Tokens früherer Refreshs bleiben gültig, bis sie ablaufen.
  • Das Abmelden widerruft weiterhin das Refresh-Token für alle Prozesse.
Vorsicht

Ohne Rotation funktioniert ein geleaktes Refresh-Token, bis es abläuft. Halten Sie Refresh token expire kurz und bevorzugen Sie DPoP für öffentliche Clients.

Token Exchange Grant​

Token Exchange (RFC 8693) tauscht ein Token gegen ein neues Token mit anderen Eigenschaften. Verwenden Sie dies, wenn ein Dienst im Auftrag eines Benutzers einen anderen Dienst aufruft, oder um den Scope eines Tokens einzuschränken, bevor Sie es an einen nachgelagerten Dienst weitergeben. Beispielsweise tauscht ein API-Gateway ein Token mit breitem Scope gegen ein Token mit engem Scope, bevor es eine Anfrage an einen Microservice weiterleitet, sodass jeder Dienst nur die Berechtigungen erhält, die er benötigt.

Senden Sie eine POST-Anfrage an https://<casdoor-host>/api/login/oauth/access_token:

{
    "grant_type": "urn:ietf:params:oauth:grant-type:token-exchange",
    "client_id": ClientId,
    "client_secret": ClientSecret,
    "subject_token": SubjectToken,
    "subject_token_type": "urn:ietf:params:oauth:token-type:access_token",
    "scope": "openid email"
}
ParameterBeschreibung
subject_tokenThe token to exchange, typically an access token or a JSON Web Token (JWT) that you already hold
subject_token_typeurn:ietf:params:oauth:token-type:access_token (default), urn:ietf:params:oauth:token-type:jwt, or urn:ietf:params:oauth:token-type:id_token
scopeOptional. A subset of the scope of the subject token. If you omit it, the new token has the scope of the subject token
audienceOptional. The application that the new access token is for, by its client ID or by its application name. The aud claim of the new access token is then the client ID of that application, and the aud of the new ID token stays the requesting client

Die Antwort enthält ein neues Token für denselben Benutzer wie das Subjekt-Token:

{
    "access_token": "eyJhb...",
    "id_token": "eyJhb...",
    "refresh_token": "eyJhb...",
    "token_type": "Bearer",
    "expires_in": 10080,
    "scope": "openid email"
}

Casdoor validiert das Subjekt-Token mit dem Zertifikat der Anwendung, die es ausgestellt hat (identifiziert durch den azp-Claim), und nicht mit dem Zertifikat des anfragenden Clients. Wenn der anfragende Client nicht der Aussteller ist, muss der aud-Claim des Subjekt-Tokens die Client-ID des anfragenden Clients enthalten. Andernfalls lehnt Casdoor den Austausch mit invalid_grant ab. Dies verhindert, dass eine Anwendung Tokens einer anderen Anwendung austauscht, ohne als Audience benannt zu werden (RFC 8693, Abschnitt 2.1). Diese Regel gilt für jedes Token format, einschließlich JWT-Standard.

Casdoor verweigert den Austausch auch in folgenden Fällen:

CaseError
Das Subjekt-Token ist kein aktives Casdoor-Token, beispielsweise weil es widerrufen wurde oder abgelaufen ist. Mit subject_token_type auf urn:ietf:params:oauth:token-type:id_token sucht Casdoor das Token als ID-Token, andernfalls als Access-Tokeninvalid_grant, subject_token is revoked or unknown
The subject token has no user, for example a token of the client credentials grantinvalid_grant, subject_token has no user
The user is forbidden to sign ininvalid_grant
The user isn't in the organization of the requesting application, and the application isn't sharedinvalid_grant
audience isn't a known applicationinvalid_target
The audience application isn't in the organization of the user, and isn't sharedinvalid_target

Ein Token eines externen Ausstellers kann ebenfalls das Subjekt-Token sein, ohne ein Client-Secret. Siehe Federated credentials.

JWT Bearer Grant​

Mit dem JWT bearer grant (RFC 7523) erhält ein Client ein Access-Token, indem er eine signierte JWT-Assertion anstelle eines Client-Secrets vorlegt. Verwenden Sie dies für Service-zu-Service-Aufrufe, bei denen der Client einen privaten Schlüssel besitzt und Sie kein langlebiges Secret teilen möchten.

  1. Aktivieren Sie JWT Bearer in Grant types der Anwendung.

  2. Laden Sie das Zertifikat des Clients in Client cert im Tab Security der Anwendung hoch. Casdoor überprüft Assertions mit dem öffentlichen Schlüssel dieses Zertifikats.

  3. Erstellen Sie die Assertion: ein JWT, das mit dem privaten Schlüssel des Clients signiert ist und die folgenden Claims enthält:

    ClaimDescription
    issIssuer — the client_id of the application
    subSubjekt — die client_id der Anwendung
    audAudience — the Casdoor token endpoint URL
    expExpiry time (Unix timestamp)

  4. Senden Sie eine POST-Anfrage an https://<casdoor-host>/api/login/oauth/access_token:

    {
        "grant_type": "urn:ietf:params:oauth:grant-type:jwt-bearer",
        "client_assertion_type": "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
        "client_assertion": "<signed-JWT>",
        "client_id": "CLIENT_ID"
    }

  5. Lesen Sie das Token aus der Antwort:

    {
        "access_token": "eyJhb...",
        "token_type": "Bearer",
        "expires_in": 10080,
        "scope": "openid"
    }

Casdoor überprüft die Signatur und die standardmäßigen JWT-Claims. Das Access-Token gehört zur Anwendung, wie beim Client Credentials Grant.

Die assertion des JWT bearer grants kann auch ein Token eines externen Ausstellers sein, dem die Anwendung vertraut. Siehe Federated credentials.

Federated Credentials (Workload Identity)​

Mit Federated Credentials vertraut eine Anwendung den Tokens eines externen OpenID Connect-Ausstellers, wie GitHub Actions, Kubernetes, einer Cloud-Workload Identity oder einem anderen IdP, als ihre Zugangsdaten. Eine Workload, die bereits ein solches Token besitzt, erhält ein Casdoor-Token ohne Client-Secret oder Client-Zertifikat.

  1. Öffnen Sie in der Casdoor-Admin-Konsole die Anwendung und wechseln Sie zum Tab OIDC/OAuth.

  2. Fügen Sie in Federated credentials für jeden vertrauten Aussteller und Subjekt eine Zeile hinzu:

    ColumnDescription
    IssuerThe issuer of the external tokens. It must equal the iss claim exactly, for example https://token.actions.githubusercontent.com
    JWKS URLThe URL of the signing keys of the issuer. If you leave it empty, Casdoor reads jwks_uri from <issuer>/.well-known/openid-configuration, whose issuer must match
    SubjectRequired. The sub claim to accept. * matches any text, for example repo:my-org/my-repo:*
    AudienceDer akzeptierte aud-Wert. Wenn Sie dieses Feld leer lassen, akzeptiert Casdoor seinen eigenen Ursprung, seinen Token-Endpoint https://<casdoor-host>/api/login/oauth/access_token oder die Client-ID der Anwendung
    UserThe user that the token stands for: a username, or {claim} to take the username from a claim, for example {email}. If you leave it empty, the token stands for the application itself

  3. Aktivieren Sie in Grant types den Grant, den die Workload verwendet.

  4. Klicken Sie auf Save.

Die Workload legt ihr externes Token dann auf eine von drei Arten vor:

  • Als client_assertion am Token-Endpunkt mit client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer, um den Client bei jedem Grant zu authentifizieren. Senden Sie auch die client_id in der Anfrage, da die sub eines externen Tokens keine Client-ID ist.
  • Als assertion des JWT-Bearer-Grants.
  • Als subject_token des Token-Austausch-Grants. Es wird kein Client-Secret benötigt.

Beispielsweise tauscht ein GitHub Actions-Job sein OIDC-Token gegen ein Casdoor-Token:

curl -X POST https://<casdoor-host>/api/login/oauth/access_token \
  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d client_id=<client-id> \
  -d subject_token=<github-oidc-token> \
  -d subject_token_type=urn:ietf:params:oauth:token-type:jwt

Casdoor überprüft ein externes Token wie folgt:

  • Die Signatur wird mit den Schlüsseln des Issuers geprüft. Casdoor speichert die Schlüssel eine Stunde lang im Cache und ruft sie erneut ab (höchstens einmal pro Minute), wenn ein Token einen unbekannten kid hat.
  • Der Signaturalgorithmus muss einer von RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384, ES512 oder EdDSA sein.
  • Das Token muss einen exp-Claim enthalten. Casdoor erlaubt eine Toleranz von einer Minute für die Uhrzeitdifferenz.
  • Ein Token eines vertrauenswürdigen Issuers, dessen Subjekt keiner Zeile entspricht, schlägt fehl, beispielsweise mit the subject: <sub> of issuer: <issuer> is not trusted by application: [<application>].

Ist User leer, handelt es sich beim neuen Token um ein Anwendungs-Token, wie beim Client-Credentials-Grant, ohne Refresh-Token oder ID-Token. Andernfalls ist es ein Token des zugeordneten Benutzers in der Organisation der Anwendung. Falls dieser Benutzer nicht existiert oder dem Token der Claim fehlt, gibt Casdoor invalid_grant zurück.

Das Discovery-Dokument listet private_key_jwt unter token_endpoint_auth_methods_supported auf.

DPoP (sender-constrained tokens)​

Casdoor unterstützt Demonstrating Proof of Possession (DPoP, RFC 9449). DPoP bindet ein Access-Token an einen vom Client gehaltenen Schlüssel, sodass ein geleaktes Token ohne den privaten Schlüssel nutzlos ist.

Um ein DPoP-gebundenes Token zu erhalten, senden Sie einen DPoP-Header mit einem DPoP-Proof-JWT in der Token-Anfrage:

POST /api/login/oauth/access_token
DPoP: <DPoP proof JWT>

Casdoor bindet das Token an den öffentlichen Schlüssel des Proofs über seinen JWK-Fingerabdruck (jkt) und gibt als token_type DPoP statt Bearer zurück:

{
    "access_token": "eyJhb...",
    "token_type": "DPoP",
    "expires_in": 10080,
    "scope": "openid"
}

Die Refresh-Token-Anfrage akzeptiert denselben DPoP-Header. Casdoor lehnt einen ungültigen Proof mit dem Fehler invalid_dpop_proof ab. Ein Refresh-Token, das mit DPoP ausgestellt wurde, ist ebenfalls an den Schlüssel gebunden: Für seine Aktualisierung ist ein DPoP-Proof erforderlich, der mit demselben Schlüssel signiert ist. Ohne Proof oder mit einem Proof eines anderen Schlüssels schlägt die Aktualisierung mit invalid_dpop_proof fehl. Casdoor prüft den htu-Claim eines Refresh-Proofs gegen den Token-Endpunkt https://<casdoor-host>/api/login/oauth/access_token.

Das Discovery-Dokument listet die Signaturalgorithmen auf, die Casdoor für Proofs in dpop_signing_alg_values_supported akzeptiert:

{
    "dpop_signing_alg_values_supported": ["RS256", "RS512", "ES256", "ES384", "ES512", "PS256", "PS384", "PS512"]
}

Die Antwort der Token-Introspection zeigt die Schlüsselbindung im cnf.jkt-Claim an (RFC 9449, Abschnitt 8).

Verify an access token​

Casdoor unterstützt Token-Introspection (RFC 7662). Authentifizieren Sie die Anfrage mit HTTP Basic Authentication, wobei die Client-ID als Benutzername und das Client-Secret als Passwort verwendet werden:

POST /api/login/oauth/introspect HTTP/1.1
Host: CASDOOR_HOST
Accept: application/json
Content-Type: application/x-www-form-urlencoded
Authorization: Basic Y2xpZW50X2lkOmNsaWVudF9zZWNyZXQ=

token=ACCESS_TOKEN&token_type_hint=access_token

Beispielantwort:

{
    "active": true,
    "client_id": "c58c...",
    "username": "admin",
    "token_type": "Bearer",
    "exp": 1647138242,
    "iat": 1646533442,
    "nbf": 1646533442,
    "sub": "7a6b4a8a-b731-48da-bc44-36ae27338817",
    "aud": [
        "c58c..."
    ],
    "iss": "http://localhost:8000"
}

Alternativ können Sie die Signatur des Tokens selbst mit dem öffentlichen Schlüssel des Zertifikats der Anwendung oder mit den Schlüsseln des JWKS-Endpunkts überprüfen. Die SDKs tun dies in ParseJwtToken().

Use an access token​

Senden Sie das Access-Token, um die Casdoor-API aufzurufen. Rufen Sie beispielsweise /api/userinfo mit GET oder POST auf eine von zwei Arten auf:

  • Mit dem Authorization-Header: Authorization: Bearer <access-token>
  • Mit einem Query-Parameter: https://<casdoor-host>/api/userinfo?accessToken=<access-token>

Casdoor gibt die Felder des Benutzers zurück, die der Scope des Tokens zulässt:

{
    "sub": "7a6b4a8a-b731-48da-bc44-36ae27338817",
    "iss": "http://localhost:8000",
    "aud": "c58c..."
}

Um weitere Felder zu erhalten, fordern Sie mehr Scopes in der Autorisierungsanfrage an.

Get the access token of an external provider​

Wenn sich ein Benutzer über einen externen OAuth-Provider wie GitHub oder Google anmeldet, speichert Casdoor das Access-Token dieses Providers im Feld originalToken des Benutzers. Ihre Anwendung kann es verwenden, um die API des Providers, wie die GitHub API oder die Google Drive API, im Namen des Benutzers aufzurufen, ohne einen weiteren OAuth-Flow durchzuführen.

Lesen Sie das Token aus /api/get-account:

{
  "status": "ok",
  "data": {
    "name": "user123",
    "originalToken": "ya29.a0AfH6SMBx...",
    ...
  }
}

Casdoor gibt originalToken nur an den Benutzer selbst und an Administratoren zurück. Für alle anderen Anfragenden wird das Feld maskiert.
