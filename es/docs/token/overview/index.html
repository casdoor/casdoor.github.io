Visión general

Casdoor está construido sobre OAuth y usa tokens para la autenticación y autorización de usuarios.

Access token e ID token​

Un inicio de sesión devuelve dos JSON Web Tokens (JWT) diferentes:

  • El access token se utiliza para llamar a APIs. Su claim tokenType es access-token.
  • El ID token indica a su aplicación quién inició sesión. Su claim tokenType es id-token.

Ambos tokens llevan los mismos claims de usuario, en el mismo Token format, y están firmados con la misma clave. Difieren en estos claims:

ClaimAccess tokenID token
tokenTypeaccess-tokenid-token
jtiIts own IDIts own ID
audThe client ID, or the resource of RFC 8707, or the audience of a token exchangeAlways the client ID
at_hash, c_hashNot presentPresent in the cases that OpenID Connect defines

Para una aplicación compartida, el aud de ambos tokens es <client-id>-org-<organization>, el client ID de la aplicación para la organización del usuario. Como los dos tokens son separados, uno no puede usarse en lugar del otro, como requiere la sección 3.12 de RFC 8725. Envíe el access token a las APIs y use el ID token solo para leer la identidad del usuario.

El endpoint /api/login devuelve el ID token en el campo data3 de su respuesta.

Campos del token​

Casdoor almacena cada token emitido como un registro con estos campos:

CampoDescripción
owner, nameThe ID of the token record
createdTimeWhen Casdoor issued the token
applicationThe application that the token was issued to
organization, userThe user of the token
codeThe authorization code that the token was issued for
accessToken, refreshToken, idTokenLos tres tokens. Casdoor también almacena un hash de cada uno, en accessTokenHash, refreshTokenHash e idTokenHash
expiresInThe lifetime of the access token, in seconds. 0 means that Casdoor has revoked the token
scopeThe granted scope
tokenTypeBearer, or DPoP for a token bound with DPoP
grantTypeThe grant that issued the token, when it matters for refreshing
resourceThe resource or the token exchange audience that the token is bound to
sessionIdThe Casdoor browser session in which the user signed in, if any

Ciclo de vida del token e invalidación​

Cuando un usuario inicia sesión, Casdoor emite un access token y un refresh token. El access token se usa para autenticación de API; el refresh token se usa para obtener nuevos access tokens sin volver a autenticar.

Para revocar un token, Casdoor establece su expiresIn en 0. El endpoint de introspección de tokens devuelve entonces "active": false, y el endpoint de actualización rechaza el refresh token con invalid_grant y refresh token is expired.

Cuándo revoca Casdoor los tokens​

EventTokens that Casdoor revokes
The user signs out with SSO logout and logoutAll=trueAll tokens of the user
The user signs out of one session, or an administrator ends a session on the Sessions pageThe tokens that were issued in that session
The user's password is changed through /api/set-password, by the user, by an administrator, or with the forgot-password flowAll tokens of the user, in all applications. Applications must sign the user in again
A new sign-in to an application with Enable exclusive signin on and Max sessions at most 1The earlier tokens of the user for that application. See Exclusive sign-in
The user is forbidden to sign in, or deletedAll tokens of the user
RP-initiated logout with id_token_hintThe token of the hint

Los tokens que fueron emitidos sin una sesión de navegador, como los tokens de la concesión de credenciales de cliente, no se ven afectados por el final de una sesión. Una sesión de Casdoor creada desde un access token termina cuando ese token es revocado o ha expirado.

Limpieza automática de tokens caducados​

Casdoor elimina automáticamente los registros de tokens que han estado caducados durante un tiempo, para que la tabla token no crezca sin límite. Un token se elimina una vez que ha estado caducado durante más tiempo que el periodo de retención de su organización, contado desde la hora de caducidad del propio token.

Establezca el periodo de retención en Token retention days en la pestaña Advanced de la organización. Vacío o 0 significa el valor predeterminado de 30 días. Los tokens de organizaciones que ya no existen usan 30 días.

El trabajo de limpieza se ejecuta:

  • una vez al iniciarse, en segundo plano, para no retrasar el arranque del servidor
  • diariamente a medianoche, hora del servidor

La limpieza elimina hasta 1,000 tokens por lote y solo afecta a los tokens ya caducados después del periodo de retención. Nunca se tocan los tokens activos.

Opciones de formato de token​

Al emitir JWTs, elija entre cuatro formatos:

  • JWT
  • JWT-Empty
  • JWT-Custom
  • JWT-Standard

Las opciones de formato de token funcionan de la siguiente manera:

  • JWT: incluye todos los campos de User en la carga útil del token
  • JWT-Empty: incluye solo los campos de User no vacíos
  • JWT-Custom: incluye los campos personalizados de Token de User que seleccione (elija atributos en Token fields)
  • JWT-Standard: incluye claims estándar de OIDC (email, teléfono, género, dirección) en formato compatible con OIDC

Establezca el formato en Token format en la pestaña OIDC/OAuth de la aplicación. Un valor vacío significa JWT. Una nueva aplicación obtiene el Default token format de su organización, y los Default token fields de su organización como sus Token fields, desde la pestaña Advanced de la organización. Cambiar estos valores predeterminados no cambia las aplicaciones existentes. Las aplicaciones que los clientes crean mediante registro dinámico de clientes obtienen los mismos valores predeterminados.

información

Solo JWT-Standard produce un claim address compatible con OIDC. En los formatos JWT, JWT-Empty y JWT-Custom, el campo address se incluye como una matriz []string sin procesar (la propiedad Address del usuario), lo cual no cumple con la especificación OIDC. Si su aplicación analiza el claim address como un objeto, use el formato de token JWT-Standard.

Formato de grupo​

Token group format en la pestaña OIDC/OAuth de la aplicación decide cómo el claim groups nombra los grupos del usuario, en cualquier formato de token y en la respuesta de /api/userinfo:

OptionValue in groups
ID (org/group)<organization>/<group>. This is the default
Path (org/parent/group)La ruta completa del grupo desde su grupo superior, como <organization>/<parent-group>/<group>
Name (group)<group>

Path (org/parent/group) reemplaza la opción useGroupPathInToken de conf/app.conf, que ya no existe.

Restricción de campos con Token fields​

La configuración Token fields en la aplicación (usada para elegir atributos de usuario personalizados para el formato JWT-Custom) también actúa como una lista blanca para el endpoint /userinfo.

  • Cuando Token fields está vacío, no se aplica ninguna lista blanca: la carga útil del token y la respuesta de /userinfo incluyen su conjunto completo de campos predeterminados. Este es el comportamiento predeterminado.
  • Cuando Token fields enumera uno o más campos, solo se devuelven esos campos. Cualquier atributo de usuario que no esté en la lista se omite tanto de la carga útil del token JWT-Custom como de la respuesta de /userinfo.

La lista blanca se compara con los nombres subyacentes de las propiedades del usuario. Por ejemplo, para exponer el nombre para mostrar, el correo electrónico y el avatar a través de /userinfo, agregue Name, Email y Avatar a Token fields. Los campos siguen respetando los ámbitos OAuth solicitados; por ejemplo, Email solo se devuelve cuando se concede el ámbito email, Location (la reclamación address) solo con el ámbito address, y Phone solo con el ámbito phone. Las reclamaciones sub y aud siempre se devuelven independientemente de la lista blanca.

precaución

Configurar Token fields restringe /userinfo, no solo el token. Si anteriormente dependía de que /userinfo devolviera todos los campos, agregar entradas aquí comenzará a filtrar esa respuesta. Deje Token fields vacío para mantener la respuesta completa.

Reclamación de dirección OIDC​

La especificación OIDC define la reclamación address como un objeto JSON con los siguientes campos:

FieldDescription
formattedFull mailing address, formatted for display
street_addressComponente de la dirección postal (puede incluir número de casa, nombre de la calle, apartado de correos, etc.)
localityCity or locality
regiónState, province, prefecture, or region
postal_codeZip code or postal code
countryCountry name

Cómo Casdoor asigna los datos del usuario a la reclamación de dirección​

Casdoor almacena la información de dirección en dos campos separados de usuario:

  • Location (cadena): Una cadena de ubicación general (por ejemplo, "New York"). Este campo se utiliza como el valor de address de cadena simple devuelto por el endpoint /api/userinfo cuando se solicita el ámbito address.
  • Address (matriz de cadenas): Una matriz de cadenas de líneas de dirección (por ejemplo, ["123 Main St", "Anytown, NY 12345", "USA"]). Este campo es la fuente para la reclamación address compatible con OIDC en los tokens JWT-Standard.

Reclamación de dirección JWT-Standard​

Cuando se solicita el ámbito address y se utiliza el formato JWT-Standard, Casdoor devuelve el siguiente objeto en el token:

{
  "address": {
    "street_address": "123 Main St\nAnytown, NY 12345\nUSA",
    "formatted": "",
    "locality": "",
    "region": "",
    "postal_code": "",
    "country": ""
  }
}

El campo street_address contiene las entradas de la matriz Address del usuario unidas con nuevas líneas. Los subcampos restantes de la dirección OIDC (formatted, locality, region, postal_code, country) están actualmente vacíos porque Casdoor almacena toda la dirección como líneas de formato libre en la matriz Address en lugar de en campos por componente.

Formatos no estándar (JWT, JWT-Empty, JWT-Custom)​

En los formatos de token JWT, JWT-Empty y JWT-Custom, el campo address es la propiedad Address sin procesar del objeto de usuario — una matriz JSON de cadenas — no un objeto de dirección OIDC:

{
  "address": ["123 Main St", "Anytown, NY 12345", "USA"]
}

Los clientes OIDC que esperan que la reclamación address sea un objeto JSON (según la especificación OIDC) fallarán al analizar esto. Cambie a JWT-Standard si necesita una reclamación address conforme a la especificación en el token.

Reclamaciones OIDC estándar​

Todos los formatos de token JWT incluyen estas reclamaciones estándar de OpenID Connect en la carga útil:

  • sub - Identificador de sujeto (ID de usuario único)
  • email - Dirección de correo electrónico del usuario
  • email_verified - Booleano que indica si la dirección de correo electrónico está verificada: el usuario la confirmó con un código o un enlace mágico de Casdoor, o el proveedor de OAuth que creó al usuario la avaló
  • name o preferred_username - Nombre para mostrar del usuario
  • picture o avatar - URL del avatar del usuario

La reclamación email_verified permite a las aplicaciones externas que usan Casdoor como proveedor de identidad determinar el estado de verificación del correo electrónico directamente desde el token sin llamadas adicionales a la API.

Cuando un usuario se registra a través de un proveedor de OAuth, Casdoor toma el estado de verificación de la dirección de correo electrónico del proveedor. Por ejemplo, Google lo informa en su reclamación email_verified, y un proveedor de OAuth personalizado puede mapear un campo emailVerified. Proveedores como GitHub, GitLab, Gitee, Facebook, LinkedIn, DingTalk, Lark y Twitter cuentan cada dirección de correo electrónico que devuelven como verificada.

El formato JWT también transporta los campos lastSigninTime y lastSigninIp del usuario. En un token de concesión de contraseña, describen el inicio de sesión anterior, porque Casdoor registra el inicio de sesión después de emitir el token. La hora del inicio de sesión actual es la reclamación iat.

Atributos de token personalizados​

Con el formato JWT-Custom, defina atributos personalizados y sus tipos de datos. Cada atributo tiene un campo Type que controla cómo se incluyen los valores en el JWT:

  • Array: El valor del atributo siempre se devolverá como una matriz, incluso si contiene un solo elemento. Esto asegura la compatibilidad con clientes OIDC que esperan tipos de matriz para campos como roles, grupos o permisos.
  • String: El valor del atributo se devolverá como una sola cadena (el primer elemento si existen múltiples valores).

Los atributos vacíos se omiten automáticamente del token para mantener la carga útil limpia. Al configurar atributos para roles, grupos o permisos, se recomienda usar el tipo Array para una mejor conformidad con OIDC y compatibilidad con sistemas como Rancher y Keycloak.
