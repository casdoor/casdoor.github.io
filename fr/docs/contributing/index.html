Guide du contributeur

Bienvenue sur Casdoor. Ce guide explique comment contribuer.

Pour les informations incorrectes ou manquantes dans la documentation, ouvrez une issue ou suggérez une modification.

S'impliquer​

Moyens de contribuer :

  • Utiliser Casdoor et signaler des problèmes. Pour les bugs ou les idées de fonctionnalités, commencez par GitHub Discussions ou Discord avant d'ouvrir une issue GitHub.
info

Lorsque vous signalez un problème, décrivez-le en anglais.

  • Améliorer la documentation. Les corrections et clarifications de la documentation sont une excellente première contribution.

  • Traiter des issues. Casdoor Easy Tasks répertorie des issues adaptées aux débutants avec différents niveaux de difficulté.

Soumettre des modifications​

Lorsque vous êtes prêt à contribuer au code ou à la documentation :

  1. Forker le dépôt vers votre compte.
  2. Cloner votre fork localement.
  3. Créer une nouvelle branche et effectuer vos modifications.
  4. Maintenir votre branche à jour avec la branche amont master.
  5. Valider avec des messages clairs et concis.
  6. Pousser votre branche vers votre fork.
  7. Ouvrir une pull request depuis votre branche vers la branche master.

Pull requests​

Avant de commencer​

  • Vous devez signer le CLA (Contributor License Agreement) lors de l'ouverture de votre première pull request.
  • Décrivez l'objectif de la PR et ce qu'elle modifie.
  • Une modification logique par PR. Si la PR effectue plusieurs tâches non liées, divisez-la en plusieurs PR.
  • Un commit par PR. Regroupez vos modifications en un seul commit.
  • Pour les nouveaux fichiers, ajoutez l'en-tête de licence Casdoor au début.

Commits conventionnels​

Les titres des PR (et les messages de commit) doivent suivre la spécification Conventional Commits.

prudence

Les titres des PR doivent être en minuscules.

Exemples :

  • fix — Correction de bug : fix: prevent racing of requests
  • feat — Nouvelle fonctionnalité : feat: allow provided config object to extend other configs
  • docs — Documentation : docs: correct spelling of CHANGELOG

Voir Conventional Commits pour la spécification complète.

Lier les PR aux issues​

Liez une PR à une issue afin que l'issue se ferme automatiquement lorsque la PR est fusionnée. Dans la description de la PR ou dans un message de commit sur la branche par défaut, utilisez l'un de ces mots-clés suivi du numéro de l'issue : close, fix, ou resolve.

Exemple : Fix: #902

Voir GitHub : Lier une pull request à une issue.

Mettre à jour votre PR​

Si les reviewers demandent des modifications, mettez à jour la même PR au lieu de la fermer et d'en ouvrir une nouvelle :

  1. Apportez les modifications en local.
  2. Amendez le commit : git commit --amend
  3. Poussez : git push --force

Directives de code​

  • Lisibilité : La logique importante doit être documentée. Suivez le style de code existant dans le projet.

Nommage​

  • Code : camelCase (ex. signupUrl).
  • Chaînes UI : Title Case avec espaces (ex. “Signup URL”).

Mise à jour des données i18n​

We use Caslingo and i18next for translations. When you add new UI strings with i18next under web/, run:

cd i18n && go test

This regenerates web/src/locales/**/data.json. New keys are filled with English by default. After the PR is merged, Caslingo machine translates the new keys and commits them; better translations can be suggested on Caslingo.

prudence

Ne traduisez pas dans une langue dont vous n'êtes pas sûr ; laissez la valeur par défaut (anglais) telle quelle.

Conventions de namespace​

Les clés de traduction sont organisées en namespaces. Utilisez le namespace le plus spécifique pour une clé—ne placez pas de chaînes spécifiques à un domaine dans general:.

NamespacePortée
generalTermes UI véritablement génériques (ex. Save, Cancel)
authFlux de connexion, inscription, MFA, mot de passe
providerOAuth, SAML, LDAP et autres fournisseurs
paymentProduits, commandes, paiements, abonnements
subscriptionChaînes spécifiques aux abonnements

Lors de l'ajout d'une nouvelle clé, vérifiez si elle existe déjà dans un namespace plus spécifique avant de l'ajouter à general.

Tests de déduplication​

Le répertoire i18n/ contient des tests qui détectent les clés dupliquées entre les namespaces :

cd i18n && go test -run TestDeduplicateFrontendI18n
cd i18n && go test -run TestDeduplicateBackendI18n

TestDeduplicateFrontendI18n scanne web/src/locales/ et TestDeduplicateBackendI18n scanne les fichiers de localisation du backend. Les deux échouent si une clé apparaît dans general alors qu'un namespace plus spécifique la définit déjà. Exécutez ces tests avant de soumettre une PR touchant les fichiers de traduction.
