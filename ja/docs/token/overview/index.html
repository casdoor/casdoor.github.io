概要

Casdoor は OAuth を基盤としており、ユーザー認証と認可のためにトークンをを使用しています。

アクセストークンと ID トークン​

サインインすると、異なる 2 つの JSON Web Token (JWT) が返されます:

  • アクセストークンは API 呼び出しに使用されます。その tokenType クレームは access-token です。
  • ID トークンは、アプリケーションに対して誰がサインインしたかを伝えます。その tokenType クレームは id-token です。

両方のトークンには同じユーザークレームが含まれており、同じ Token format でエンコードされ、同じ鍵で署名されています。これらのクレームについては異なります:

ClaimAccess tokenID token
tokenTypeaccess-tokenid-token
jtiIts own IDIts own ID
audThe client ID, or the resource of RFC 8707, or the audience of a token exchangeAlways the client ID
at_hash, c_hashNot presentPresent in the cases that OpenID Connect defines

共有アプリケーションの場合、両方のトークンの aud は <client-id>-org-<organization> です。これは、ユーザーの組織に対するアプリケーションのクライアント ID です。2 つのトークンは別々であるため、RFC 8725 セクション 3.12 の要件に従い、互いに代用することはできません。API へのリクエストにはアクセストークンを送信し、ID トークンはユーザーのアイデンティティを読み取るためにのみ使用してください。

/api/login エンドポイントは、レスポンスの data3 フィールドに ID トークンを返します。

トークンフィールド​

Casdoor は発行された各トークンを、以下のフィールドを持つレコードとして保存します:

フィールド説明
owner, nameThe ID of the token record
createdTimeWhen Casdoor issued the token
applicationThe application that the token was issued to
organization, userThe user of the token
codeThe authorization code that the token was issued for
accessToken, refreshToken, idToken3 つのトークンです。Casdoor はそれぞれについてハッシュ値も accessTokenHash, refreshTokenHash, idTokenHash に保存します
expiresInThe lifetime of the access token, in seconds. 0 means that Casdoor has revoked the token
scopeThe granted scope
tokenTypeBearer, or DPoP for a token bound with DPoP
grantTypeThe grant that issued the token, when it matters for refreshing
resourceThe resource or the token exchange audience that the token is bound to
sessionIdThe Casdoor browser session in which the user signed in, if any

トークンのライフサイクルと無効化​

ユーザーがサインインすると、Casdoor はアクセストークンとリフレッシュトークンを発行します。アクセストークンは API 認証に使用され、リフレッシュトークンは再認証なしに新しいアクセストークンを取得するために使用されます。

トークンを失効させるために、Casdoor はその expiresIn を 0 に設定します。その後、トークンイントロスペクションエンドポイントは "active": false を返し、リフレッシュエンドポイントはリフレッシュトークンを invalid_grant および refresh token is expired で拒否します。

Casdoor がトークンを失効させるタイミング​

EventTokens that Casdoor revokes
The user signs out with SSO logout and logoutAll=trueAll tokens of the user
The user signs out of one session, or an administrator ends a session on the Sessions pageThe tokens that were issued in that session
The user's password is changed through /api/set-password, by the user, by an administrator, or with the forgot-password flowAll tokens of the user, in all applications. Applications must sign the user in again
A new sign-in to an application with Enable exclusive signin on and Max sessions at most 1The earlier tokens of the user for that application. See Exclusive sign-in
The user is forbidden to sign in, or deletedAll tokens of the user
RP-initiated logout with id_token_hintThe token of the hint

ブラウザセッションなしで発行されたトークン（クライアント資格情報グラントのトークンなど）は、セッションの終了の影響を受けません。アクセストークンから作成された Casdoor セッションは、そのトークンが失効または期限切れになったときに終了します。

期限切れトークンの自動クリーンアップ​

Casdoor は一定期間経過した期限切れトークンのレコードを自動的に削除するため、token テーブルが無制限に成長することはありません。トークンは、その組織の保持期間を超えて期限切れになってから削除されます。保持期間はトークン自身の期限切れ時刻から計算されます。

保持期間は、組織 の Advanced タブにある Token retention days で設定します。空または 0 の場合は、デフォルトの 30 日が使用されます。存在しない組織のトークンは 30 日となります。

クリーンアップジョブは以下のように実行されます:

  • サーバー起動時に一度、バックグラウンドで実行されるため、サーバーの起動が遅延することはありません
  • 毎日深夜 0 時（サーバー時間）に実行されます

クリーンアップはバッチごとに最大 1,000 個のトークンを削除し、保持期間を過ぎた有効期限切れのトークンのみに影響します。アクティブなトークンは決して削除されません。

トークン形式オプション​

JWT を発行する際は、4 つの形式から選択します:

  • JWT
  • JWT-Empty
  • JWT-Custom
  • JWT-Standard

トークン形式オプションの動作は次のとおりです:

  • JWT: トークンペイロードにすべての User フィールドを含めます
  • JWT-Empty: 空ではない User フィールドのみを含めます
  • JWT-Custom: 選択したカスタム User Token フィールドを含めます (Token fields で属性を選択してください)
  • JWT-Standard: OIDC 準拠の形式で標準的な OIDC クレーム (email, phone, gender, address) を含めます

アプリケーションの OIDC/OAuth タブにある Token format で形式を設定します。値が空の場合は JWT を意味します。新しいアプリケーションは、organization の Advanced タブから組織の Default token format と、その組織の Default token fields を自身の Token fields として取得します。これらのデフォルトを変更しても、既存のアプリケーションは変更されません。クライアントが dynamic client registration を通じて作成するアプリケーションも同じデフォルトを取得します。

情報

OIDC 準拠の address クレームを生成するのは JWT-Standard のみです。 JWT、JWT-Empty、および JWT-Custom 形式では、address フィールドは生の []string 配列 (ユーザーの Address プロパティ) として含まれ、これは OIDC 仕様に準拠していません。アプリケーションが address クレームをオブジェクトとして解析する場合、JWT-Standard トークン形式を使用してください。

グループ形式​

アプリケーションの OIDC/OAuth タブにある Token group format は、すべてのトークン形式と /api/userinfo の応答において、groups クレームがユーザーのグループをどのように名前付けするかを決定します:

OptionValue in groups
ID (org/group)<organization>/<group>. This is the default
Path (org/parent/group)トップグループからのグループの完全なパス (例: <organization>/<parent-group>/<group>)
Name (group)<group>

Path (org/parent/group) は、存在しなくなった conf/app.conf の useGroupPathInToken オプションを置き換えます。

Token fields によるフィールド制限​

アプリケーションの Token fields 設定 (JWT-Custom 形式用のカスタムユーザー属性を選択するために使用) は、/userinfo エンドポイントのホワイトリストとしても機能します。

  • Token fields が空の場合、ホワイトリストは適用されません: トークンペイロードと /userinfo 応答には、デフォルトの完全なフィールドセットが含まれます。これがデフォルトの動作です。
  • Token fields に 1 つ以上のフィールドがリストされている場合、それらのフィールドのみが返されます。リストに含まれていないユーザー属性は、両方の JWT-Custom トークンペイロードと /userinfo 応答から省略されます。

ホワイトリストは基盤となるユーザープロパティ名に対してマッチングされます。例えば、/userinfo を介して表示名、メール、アバターを公開するには、Token fields に Name、Email、Avatar を追加します。フィールドは要求された OAuth スコープに従います — 例えば Email は email スコープが付与された場合にのみ返され、Location (address クレーム) は address スコープでのみ返され、Phone は phone スコープでのみ返されます。sub および aud クレームはホワイトリストに関係なく常に返されます。

注意

Token fields の設定は、トークンだけでなく /userinfo も制限します。以前に /userinfo がすべてのフィールドを返すことに依存していた場合、ここにエントリを追加するとその応答のフィルタリングが始まります。完全な応答を維持するには Token fields を空のままにしてください。

OIDC Address Claim​

OIDC specification では、address クレームは次のフィールドを持つ JSON オブジェクトとして定義されています:

FieldDescription
formattedFull mailing address, formatted for display
street_address住所の番地コンポーネント (番地、道路名、私書箱などを含めることができます)
localityCity or locality
リージョンState, province, prefecture, or region
postal_codeZip code or postal code
countryCountry name

Casdoor がユーザーデータを address クレームにマッピングする方法​

Casdoor は住所情報を 2 つの別々のユーザーフィールドに保存します:

  • Location (文字列): 一般的な場所を示す文字列 (例: "New York")。このフィールドは、address スコープが要求されたときに /api/userinfo エンドポイントによって返されるプレーン文字列の address 値として使用されます。
  • Address (文字列の配列): 住所行の文字列の配列 (例: ["123 Main St", "Anytown, NY 12345", "USA"])。このフィールドは、JWT-Standard トークン内の OIDC 準拠の address クレームのソースです。

JWT-Standard address クレーム​

address スコープが要求され、JWT-Standard 形式が使用されている場合、Casdoor はトークン内で次のオブジェクトを返します:

{
  "address": {
    "street_address": "123 Main St\nAnytown, NY 12345\nUSA",
    "formatted": "",
    "locality": "",
    "region": "",
    "postal_code": "",
    "country": ""
  }
}

street_address フィールドには、ユーザーの Address 配列のエントリが改行で結合されて含まれます。残りの OIDC address サブフィールド (formatted, locality, region, postal_code, country) は、Casdoor がアドレス全体をコンポーネントごとのフィールドではなく Address 配列内のフリーフォーム行として保存しているため、現在空です。

非標準形式 (JWT, JWT-Empty, JWT-Custom)​

JWT、JWT-Empty、および JWT-Custom トークン形式では、address フィールドはユーザーオブジェクトの生の Address プロパティ — 文字列の JSON 配列 — であり、OIDC address オブジェクトではありません:

{
  "address": ["123 Main St", "Anytown, NY 12345", "USA"]
}

address クレームが JSON オブジェクトであることを期待する OIDC クライアント (OIDC 仕様に基づく) はこれを解析できません。トークン内で仕様準拠の address クレームが必要な場合は、JWT-Standard に切り替えてください。

Standard OIDC Claims​

すべての JWT トークン形式には、ペイロードにこれらの標準的な OpenID Connect クレームが含まれます:

  • sub - Subject identifier (unique user ID)
  • email - ユーザーのメールアドレス
  • email_verified - メールアドレスが検証済みかどうかを示すブール値: ユーザーがコードまたは Casdoor のマジックリンクで確認したか、ユーザーを作成した OAuth プロバイダーがその正当性を保証しています
  • name または preferred_username - ユーザーの表示名
  • picture または avatar - ユーザーのアバター URL

email_verified クレームにより、Casdoor をアイデンティティプロバイダーとして使用している外部アプリケーションは、追加の API 呼び出しなしにトークンから直接メール検証ステータスを判断できます。

ユーザーが OAuth プロバイダー経由でサインアップする場合、Casdoor はプロバイダーからメールアドレスの検証ステータスを取得します。例えば、Google は email_verified クレームでこれを報告し、カスタム OAuth プロバイダーは emailVerified フィールドをマッピングできます。GitHub、GitLab、Gitee、Facebook、LinkedIn、DingTalk、Lark、Twitter などのプロバイダーは、返されるすべてのメールアドレスを検証済みとみなします。

JWT フォーマットには、ユーザーの lastSigninTime および lastSigninIp フィールドも含まれます。パスワードグラントのトークンでは、これらは前回のサインインを表します。なぜなら、Casdoor はトークンを発行した後にサインインを記録するからです。現在のサインインの時刻は iat クレームです。

カスタムトークン属性​

JWT-Custom フォーマットを使用すると、カスタム属性とそのデータ型を定義できます。各属性には、値が JWT にどのように含まれるかを制御する Type フィールドがあります:

  • Array: 属性値は、単一の要素しか含まれていない場合でも、常に配列として返されます。これは、roles、groups、permissions などのフィールドに対して配列型を期待する OIDC クライアントとの互換性を確保します。
  • String: 属性値は単一の文字列として返されます（複数の値が存在する場合は最初の要素）。

空の属性は、ペイロードをクリーンに保つためにトークンから自動的に省略されます。roles、groups、または permissions の属性を設定する場合、Rancher や Keycloak などのシステムとのより良い OIDC コンプライアンスと互換性のために、Array 型を使用することをお勧めします。
