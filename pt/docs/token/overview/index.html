Visão Geral

O Casdoor é construído sobre OAuth e usa tokens para autenticação e autorização de usuários.

Token de acesso e token de ID​

Um login retorna dois JSON Web Tokens (JWTs) diferentes:

  • O token de acesso serve para chamar APIs. Sua claim tokenType é access-token.
  • O token de ID informa à sua aplicação quem fez login. Sua claim tokenType é id-token.

Ambos os tokens carregam as mesmas claims de usuário, no mesmo Token format, e são assinados com a mesma chave. Eles diferem nestas claims:

ClaimAccess tokenID token
tokenTypeaccess-tokenid-token
jtiIts own IDIts own ID
audThe client ID, or the resource of RFC 8707, or the audience of a token exchangeAlways the client ID
at_hash, c_hashNot presentPresent in the cases that OpenID Connect defines

Para uma aplicação compartilhada, o aud de ambos os tokens é <client-id>-org-<organization>, o client ID da aplicação para a organização do usuário. Como os dois tokens são separados, um não pode ser usado no lugar do outro, conforme exigido pela seção 3.12 da RFC 8725. Envie o token de acesso para as APIs e use o token de ID apenas para ler a identidade do usuário.

O endpoint /api/login retorna o token de ID no campo data3 de sua resposta.

Campos do token​

O Casdoor armazena cada token emitido como um registro com estes campos:

CampoDescrição
owner, nameThe ID of the token record
createdTimeWhen Casdoor issued the token
applicationThe application that the token was issued to
organization, userThe user of the token
codeThe authorization code that the token was issued for
accessToken, refreshToken, idTokenOs três tokens. O Casdoor também armazena um hash de cada um, em accessTokenHash, refreshTokenHash e idTokenHash
expiresInThe lifetime of the access token, in seconds. 0 means that Casdoor has revoked the token
scopeThe granted scope
tokenTypeBearer, or DPoP for a token bound with DPoP
grantTypeThe grant that issued the token, when it matters for refreshing
resourceThe resource or the token exchange audience that the token is bound to
sessionIdThe Casdoor browser session in which the user signed in, if any

Ciclo de vida e invalidação de tokens​

Quando um usuário faz login, o Casdoor emite um token de acesso e um token de refresh. O token de acesso é usado para autenticação de API; o token de refresh é usado para obter novos tokens de acesso sem reautenticar.

Para revogar um token, o Casdoor define seu expiresIn como 0. O endpoint de introspecção de token então retorna "active": false, e o endpoint de refresh rejeita o token de refresh com invalid_grant e refresh token is expired.

Quando o Casdoor revoga tokens​

EventTokens that Casdoor revokes
The user signs out with SSO logout and logoutAll=trueAll tokens of the user
The user signs out of one session, or an administrator ends a session on the Sessions pageThe tokens that were issued in that session
The user's password is changed through /api/set-password, by the user, by an administrator, or with the forgot-password flowAll tokens of the user, in all applications. Applications must sign the user in again
A new sign-in to an application with Enable exclusive signin on and Max sessions at most 1The earlier tokens of the user for that application. See Exclusive sign-in
The user is forbidden to sign in, or deletedAll tokens of the user
RP-initiated logout with id_token_hintThe token of the hint

Tokens emitidos sem uma sessão de navegador, como tokens da concessão de credenciais de cliente, não são afetados pelo fim de uma sessão. Uma sessão Casdoor criada a partir de um token de acesso termina quando esse token é revogado ou expirou.

Limpeza automática de tokens expirados​

O Casdoor exclui automaticamente registros de tokens que estão expirados há algum tempo, para que a tabela token não cresça indefinidamente. Um token é removido assim que tiver estado expirado por mais tempo do que o período de retenção de sua organização, contado a partir do tempo de expiração do próprio token.

Defina o período de retenção em Token retention days na aba Advanced da organização. Vazio ou 0 significa o padrão de 30 dias. Tokens de organizações que não existem mais usam 30 dias.

O job de limpeza executa:

  • uma vez na inicialização, em segundo plano, para não atrasar o início do servidor
  • diariamente à meia-noite, horário do servidor

A limpeza exclui até 1.000 tokens por lote e afeta apenas tokens já expirados após o período de retenção. Tokens ativos nunca são alterados.

Opções de formato de token​

Ao emitir JWTs, escolha entre quatro formatos:

  • JWT
  • JWT-Empty
  • JWT-Custom
  • JWT-Standard

As opções de formato de token funcionam da seguinte maneira:

  • JWT: inclui todos os campos de User no payload do token
  • JWT-Empty: inclui apenas os campos de User não vazios
  • JWT-Custom: inclui os campos personalizados de Token de usuário que você selecionar (escolha atributos nos campos Token fields)
  • JWT-Standard: inclui claims OIDC padrão (email, telefone, gênero, endereço) em formato compatível com OIDC

Defina o formato em Token format na aba OIDC/OAuth da aplicação. Um valor vazio significa JWT. Uma nova aplicação recebe o Default token format de sua organização e os Default token fields de sua organização como seus Token fields, a partir da aba Advanced da organização. Alterar esses padrões não altera as aplicações existentes. Aplicações criadas por clientes através do registro dinâmico de cliente recebem os mesmos padrões.

informação

Somente JWT-Standard produz uma claim address compatível com OIDC. Nos formatos JWT, JWT-Empty e JWT-Custom, o campo address é incluído como um array bruto []string (a propriedade Address do usuário), que não está em conformidade com a especificação OIDC. Se sua aplicação interpreta a claim address como um objeto, use o formato de token JWT-Standard.

Formato de grupo​

O Token group format na aba OIDC/OAuth da aplicação decide como a claim groups nomeia os grupos do usuário, em todos os formatos de token e na resposta de /api/userinfo:

OptionValue in groups
ID (org/group)<organization>/<group>. This is the default
Path (org/parent/group)The full path of the group from its top group, such as <organization>/<parent-group>/<group>
Name (group)<group>

Path (org/parent/group) substitui a opção useGroupPathInToken de conf/app.conf, que não existe mais.

Restringindo campos com Token fields​

A configuração Token fields na aplicação (usada para escolher atributos personalizados de usuário para o formato JWT-Custom) também atua como uma lista de permissões (whitelist) para o endpoint /userinfo.

  • Quando Token fields está vazio, nenhuma lista de permissões é aplicada: o payload do token e a resposta de /userinfo incluem seu conjunto completo de campos padrão. Este é o comportamento padrão.
  • Quando Token fields lista um ou mais campos, apenas esses campos são retornados. Qualquer atributo de usuário não listado é omitido de ambos o payload do token JWT-Custom e a resposta de /userinfo.

A lista de permissões corresponde aos nomes das propriedades subjacentes do usuário. Por exemplo, para expor o nome de exibição, email e avatar através de /userinfo, adicione Name, Email e Avatar a Token fields. Os campos ainda respeitam os escopos OAuth solicitados — por exemplo, Email só é retornado quando o escopo email é concedido, Location (a claim address) somente com o escopo address, e Phone somente com o escopo phone. As claims sub e aud são sempre retornadas independentemente da lista de permissões.

cuidado

Configurar Token fields restringe /userinfo, não apenas o token. Se você anteriormente dependia de /userinfo retornando todos os campos, adicionar entradas aqui começará a filtrar essa resposta. Deixe Token fields vazio para manter a resposta completa.

Claim de Endereço OIDC​

A especificação OIDC define a claim address como um objeto JSON com os seguintes campos:

FieldDescription
formattedFull mailing address, formatted for display
street_addressComponente do endereço de rua (pode incluir número da casa, nome da rua, caixa postal, etc.)
localityCity or locality
regiãoState, province, prefecture, or region
postal_codeZip code or postal code
countryCountry name

Como o Casdoor mapeia dados do usuário para a claim de endereço​

O Casdoor armazena informações de endereço em dois campos separados do usuário:

  • Location (string): Uma string de localização geral (por exemplo, "New York"). Este campo é usado como o valor address de string simples retornado pelo endpoint /api/userinfo quando o escopo address é solicitado.
  • Address (array de strings): Um array de strings de linhas de endereço (por exemplo, ["123 Main St", "Anytown, NY 12345", "USA"]). Este campo é a fonte para a claim address compatível com OIDC em tokens JWT-Standard.

Claim de endereço JWT-Standard​

Quando o escopo address é solicitado e o formato JWT-Standard é usado, o Casdoor retorna o seguinte objeto no token:

{
  "address": {
    "street_address": "123 Main St\nAnytown, NY 12345\nUSA",
    "formatted": "",
    "locality": "",
    "region": "",
    "postal_code": "",
    "country": ""
  }
}

O campo street_address contém as entradas do array Address do usuário unidas com novas linhas. Os subcampos restantes do endereço OIDC (formatted, locality, region, postal_code, country) estão atualmente vazios porque o Casdoor armazena todo o endereço como linhas de texto livre no array Address, em vez de campos por componente.

Formatos não padrão (JWT, JWT-Empty, JWT-Custom)​

Nos formatos de token JWT, JWT-Empty e JWT-Custom, o campo address é a propriedade Address bruta do objeto do usuário — um array JSON de strings — não um objeto de endereço OIDC:

{
  "address": ["123 Main St", "Anytown, NY 12345", "USA"]
}

Clientes OIDC que esperam que a claim address seja um objeto JSON (de acordo com a especificação OIDC) falharão ao interpretar isso. Mude para JWT-Standard se você precisar de uma claim address compatível com a especificação no token.

Claims OIDC Padrão​

Todos os formatos de token JWT incluem estas claims OpenID Connect padrão no payload:

  • sub - Identificador do assunto (ID de usuário exclusivo)
  • email - Endereço de e-mail do usuário
  • email_verified - Booleano indicando se o endereço de e-mail está verificado: o usuário confirmou com um código ou link mágico do Casdoor, ou o provedor OAuth que criou o usuário atestou a verificação
  • name ou preferred_username - Nome de exibição do usuário
  • picture ou avatar - URL do avatar do usuário

A claim email_verified permite que aplicações externas usando o Casdoor como provedor de identidade determinem o status de verificação do e-mail diretamente do token sem chamadas adicionais à API.

Quando um usuário se cadastra através de um provedor OAuth, o Casdoor obtém o status de verificação do endereço de e-mail do provedor. Por exemplo, o Google relata isso em sua claim email_verified, e um provedor OAuth Customizado pode mapear um campo emailVerified. Provedores como GitHub, GitLab, Gitee, Facebook, LinkedIn, DingTalk, Lark e Twitter consideram todos os endereços de e-mail que retornam como verificados.

O formato JWT também transporta os campos lastSigninTime e lastSigninIp do usuário. Em um token de concessão por senha, eles descrevem o login anterior, porque o Casdoor registra o login após emitir o token. O horário do login atual é a claim iat.

Atributos Personalizados de Token​

Com o formato JWT-Custom, defina atributos personalizados e seus tipos de dados. Cada atributo tem um campo Type que controla como os valores são incluídos no JWT:

  • Array: O valor do atributo será sempre retornado como um array, mesmo que contenha um único elemento. Isso garante compatibilidade com clientes OIDC que esperam tipos de array para campos como roles, groups ou permissions.
  • String: O valor do atributo será retornado como uma única string (o primeiro elemento se houver múltiplos valores).

Atributos vazios são automaticamente omitidos do token para manter o payload limpo. Ao configurar atributos para roles, groups ou permissions, recomenda-se usar o tipo Array para melhor conformidade com OIDC e compatibilidade com sistemas como Rancher e Keycloak.
