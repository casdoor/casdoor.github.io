Déployer Casdoor sur Kubernetes

Ce guide explique comment déployer Casdoor sur un cluster Kubernetes à l'aide du manifeste d'exemple provenant du dépôt Casdoor et comment l'exposer avec Ingress.

Objectifs d'apprentissage​

  • Déployez Casdoor avec le manifeste d'exemple k8s.yaml.
  • Exposez Casdoor hors du cluster avec un Ingress.
  • Protégez une application au niveau de la couche ingress avec oauth2-proxy et Casdoor.

Prérequis​

  • Un cluster Kubernetes et kubectl
  • Une base de données prise en charge accessible depuis le cluster
  • Un contrôleur d'ingress, tel qu'ingress-nginx, pour exposer Casdoor
  • Un clone du dépôt Casdoor
Vous ne souhaitez pas l'héberger vous-même ?

Casdoor Cloud vous offre une instance Casdoor dédiée que nous hébergeons et maintenons à jour pour vous, à partir de 29 $/mois sans frais par utilisateur. Les nouveaux comptes bénéficient de 20 $ de crédit gratuit pour l'essayer.

À propos du manifeste d'exemple​

La racine du dépôt Casdoor contient k8s.yaml, un manifeste d'exemple avec un Service et un Deployment. C'est un point de départ. Pour un déploiement que vous pouvez configurer et mettre à jour via des valeurs, utilisez plutôt le chart Helm. Pour exécuter plusieurs instances, ou pour déclarer des organisations et des applications comme ressources Kubernetes, utilisez l'opérateur Kubernetes.

# Example: deploying Casdoor on Kubernetes
# Adjust this file for your environment
apiVersion: v1
kind: Service
metadata:
  # EDIT: set namespace if not using default
  #namespace: casdoor
  name: casdoor-svc
  labels:
    app: casdoor
spec:
  # EDIT: set namespace if not using default
  type: NodePort
  ports:
    - port: 8000
  selector:
    app: casdoor
---
apiVersion: apps/v1
kind: Deployment
metadata:
  # EDIT: set namespace if not using default
  #namespace: casdoor
  name: casdoor-deployment
  labels:
    app: casdoor
spec:
  # EDIT: use 1 replica if not using Redis
  replicas: 1
  selector:
    matchLabels:
      app: casdoor
  template:
    metadata:
      labels:
        app: casdoor
    spec:
      containers:
        - name: casdoor-container
          image: casbin/casdoor:latest
          imagePullPolicy: Always
          ports:
            - containerPort: 8000
          volumeMounts:
            # the mounted directory path in THE CONTAINER
            - mountPath: /conf
              name: conf
          env:       
            - name: RUNNING_IN_DOCKER
              value: "true"
      #if you want to deploy this in real prod env, consider the config map
      volumes:
        - name: conf
          hostPath:
            #EDIT IT: the mounted directory path in THE HOST
            path: /conf

Déployer Casdoor​

  1. Configurez la connexion à la base de données dans conf/app.conf. Voir Configurer la base de données.

  2. Assurez-vous que la base de données est en cours d'exécution et que le cluster peut extraire l'image casbin/casdoor.

  3. Adaptez k8s.yaml à votre environnement : l'espace de noms, le type de Service et le chemin du volume conf sur l'hôte.

  4. Appliquez le manifeste :

    kubectl apply -f k8s.yaml

  5. Vérifiez que le pod fonctionne :

    kubectl get pods
conseil

En production, placez app.conf dans un ConfigMap au lieu d'un volume hostPath.

Exposer Casdoor avec Ingress​

Créez un Ingress qui route votre domaine vers le Service Casdoor. Remplacez auth.yourdomain.com par votre domaine.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: casdoor-ingress
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  rules:
  - host: auth.yourdomain.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: casdoor-svc
            port:
              number: 8000
  tls:
  - hosts:
    - auth.yourdomain.com
    secretName: casdoor-tls-secret

Vos applications peuvent désormais connecter les utilisateurs avec Casdoor via un SDK ou via OAuth 2.0 et OpenID Connect (OIDC). C'est la configuration recommandée, car le code de votre application contrôle le flux de connexion.

Protéger une application au niveau de la couche ingress​

Pour exiger une connexion pour une application sans modifier son code, placez oauth2-proxy devant elle. oauth2-proxy gère le flux OAuth 2.0 complet :

  • Il redirige l'utilisateur vers Casdoor pour se connecter.
  • Il gère le callback avec le code d'autorisation.
  • Il conserve la session de l'utilisateur dans un cookie.
  • Il valide et rafraîchit les jetons.
note

N'utilisez pas l'annotation nginx.ingress.kubernetes.io/auth-url d'ingress-nginx directement avec Casdoor. L'annotation attend un point de terminaison qui valide un jeton. Elle ne peut pas exécuter un flux OAuth 2.0 avec redirections et sessions.

Le manifeste suivant déploie oauth2-proxy et route app.yourdomain.com à travers celui-ci :

apiVersion: apps/v1
kind: Deployment
metadata:
  name: oauth2-proxy
spec:
  replicas: 1
  selector:
    matchLabels:
      app: oauth2-proxy
  template:
    metadata:
      labels:
        app: oauth2-proxy
    spec:
      containers:
      - name: oauth2-proxy
        image: quay.io/oauth2-proxy/oauth2-proxy:v7.5.1
        args:
        - --provider=oidc
        - --oidc-issuer-url=https://auth.yourdomain.com
        - --client-id=YOUR_CLIENT_ID
        - --client-secret=YOUR_CLIENT_SECRET
        - --redirect-url=https://app.yourdomain.com/oauth2/callback
        - --cookie-secret=RANDOM_SECRET_32_CHARS
        - --email-domain=*
        - --upstream=http://your-app-service:8080
        - --http-address=0.0.0.0:4180
        ports:
        - containerPort: 4180
---
apiVersion: v1
kind: Service
metadata:
  name: oauth2-proxy-svc
spec:
  ports:
  - port: 4180
    targetPort: 4180
  selector:
    app: oauth2-proxy
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
spec:
  ingressClassName: nginx
  rules:
  - host: app.yourdomain.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: oauth2-proxy-svc
            port:
              number: 4180
  tls:
  - hosts:
    - app.yourdomain.com
    secretName: app-tls-secret
PlaceholderValue
auth.yourdomain.comDomain of Casdoor
YOUR_CLIENT_ID, YOUR_CLIENT_SECRETClient ID and client secret of the Casdoor application
app.yourdomain.comDomain of the protected application. Add https://app.yourdomain.com/oauth2/callback to the Redirect URLs of the Casdoor application
RANDOM_SECRET_32_CHARSRandom secret that encrypts the session cookie
your-app-service:8080Service and port of the protected application

Pour plus d'options, voir le guide d'intégration OAuth2 Proxy.

Sécuriser le déploiement​

  • Utilisez HTTPS : OAuth 2.0 exige des connexions sécurisées. Émettez des certificats TLS pour vos ressources Ingress, par exemple avec cert-manager.
  • Gardez les secrets dans des Secrets : Stockez les secrets clients et les secrets de cookies dans des Secrets Kubernetes, et non dans des ConfigMaps ou dans des manifests.
  • Restreignez l'accès avec RBAC : Limitez qui peut lire la configuration d'authentification et les Secrets.
  • Partagez les sessions entre les répliques : Si vous exécutez plusieurs répliques d'oauth2-proxy, configurez Redis comme magasin de sessions, afin que les sessions survivent aux redémarrages des pods et fonctionnent sur chaque réplique.
