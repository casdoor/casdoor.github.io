Вебхуки

Casdoor може повідомляти ваш додаток про події, надсилаючи HTTP POST запити з JSON-пакетом на налаштований URL. Використовуйте webhooks для реакції на реєстрацію, вхід, вихід, оновлення профілю та багато інших подій.

Як працюють webhooks​

Коли в Casdoor відбувається подія:

  1. Casdoor надсилає POST запит на вказаний webhook URL.
  2. Запит містить JSON-пакет із деталями події.
  3. Ваш додаток обробляє пакет і виконує відповідні дії залежно від типу події.

Підтримувані події​

Webhooks можна підписати на широкий набір подій, згрупованих за областями:

Події автентифікації та сесій​

  • signup, login, logout - Процеси автентифікації користувачів
  • sso-logout, unlink - Єдиний вхід (SSO) та відв'язування акаунтів
  • new-user - Користувацька подія створення нового користувача
  • new-user-ldap - Користувацька подія, що спрацьовує при створенні нового користувача через синхронізацію LDAP
  • new-user-syncer - Користувацька подія, що спрацьовує при створенні нового користувача через синхронізатор бази даних

logout і sso-logout спрацьовують також для GET запитів, наприклад, коли relying party OpenID Connect (OIDC) перенаправляє браузер на GET /api/logout для RP-initiated logout. Casdoor фіксує ці дві дії навіть якщо logPostOnly у файлі конфігурації дорівнює true, який інакше пропускає всі GET запити. Без cookie сесії запис бере користувача та організацію з subject id_token_hint.

Події управління ресурсами​

Стандартні операції CRUD (add-*, update-*, delete-*) доступні для всіх основних ресурсів, включаючи організації, групи, користувачів, додатки, провайдерів та сертифікати. Додаткові ресурси, такі як ролі, права доступу, моделі, адаптери, ефорсери, сесії, токени, продукти, платежі та прайсинг, також підтримують ці операції. Webhooks можуть відстежувати зміни в syncers, формах, запрошеннях, конфігураціях LDAP, замовленнях, квитках та транзакціях.

Спеціалізовані операції​

Управління користувачами: add-user-keys, remove-user-from-group, upload-users, check-user-password, set-password, reset-email-or-phone, verify-identification

Масові операції: upload-groups, upload-roles, upload-permissions, upload-resource

Обробка замовлень: place-order, cancel-order, pay-order

Обробка платежів: invoice-payment, notify-payment

Запрошення: send-invitation, verify-invitation

Системи підтримки: add-ticket-message

Синхронізація: run-syncer, test-syncer-db, sync-ldap-users

Access Control: enforce, batch-enforce, add-policy, update-policy, remove-policy, add-record

Multi-Factor Authentication: delete-mfa, set-preferred-mfa, mfa/setup/initiate, mfa/setup/verify, mfa/setup/enable

WebAuthn: webauthn/signup/begin, webauthn/signup/finish, webauthn/signin/begin, webauthn/signin/finish

OAuth & Token Management: login/oauth/access_token, login/oauth/refresh_token, login/oauth/introspect

Verification & Communication: send-verification-code, verify-code, verify-captcha, send-email, send-sms, send-notification

SAML: acs, saml/metadata

System Operations: health, metrics, callback, device-auth, faceid-signin-begin, user, userinfo

Кожна подія містить контекстну інформацію в корисному навантаженні вебхука, що дозволяє вам реалізовувати власну логіку на основі конкретної дії, яка ініціювала вебхук.

Налаштування вебхука​

  1. У адміністративній консолі Casdoor перейдіть до Admin > Webhooks.
  2. Натисніть Add.
  3. Виберіть Organization, якій належить вебхук.
  4. У полі URL введіть адресу, яка приймає події.
  5. У розділі Events виберіть одну або кілька подій.
  6. Необов'язково: у розділі Headers додайте спеціальні заголовки, наприклад, для автентифікації.
  7. Встановіть Single org only, див. Події інших організацій.
  8. Увімкніть Is enabled та збережіть зміни. Після цього Casdoor надсилатиме події на вказаний URL.

Адміністратор організації може додавати вебхуки лише до своєї організації. Для будь-якої іншої організації запит POST /api/add-webhook поверне помилку "Unauthorized operation".

Події інших організацій​

Опція Single org only (singleOrgOnly) визначає, які записи активують вебхук:

  • On: Вебхук активують лише записи організації, якій він належить.
  • Off: Вебхук активують записи всіх організацій.

Лише глобальний адміністратор, тобто користувач організації built-in, може вимкнути опцію Single org only. Якщо будь-хто інший додає або оновлює вебхук, Casdoor зберігає його з увімкненою опцією Single org only.

Адреси, доступні для вебхуків​

Вебхуки всіх організацій, крім built-in, можуть надсилати запити лише на інтернет-адреси. Casdoor відмовляється підключатися до приватних, петльових (loopback), link-local адрес, неспецифікованих адрес та спільного адресного простору 100.64.0.0/10. Діапазон link-local включає адресу метаданих хмарного середовища 169.254.169.254. Casdoor перевіряє IP-адресу кожного з'єднання після її розв'язання, тому відмовляють також хости, імена яких розв'язуються в адреси внутрішньої мережі, DNS rebinding та перенаправлення на адреси внутрішньої мережі. Ці вебхуки не використовують проксі-сервер, налаштований у Casdoor.

Помилка відхиленої доставки містить повідомлення the address: <address> is not allowed, only Internet addresses can be requested.

Лише вебхуки організації built-in, якою керують тільки глобальні адміністратори, можуть отримувати доступ до хостів у внутрішній мережі. Щоб надсилати події іншої організації до служби у вашій локальній мережі, глобальний адміністратор створює вебхук в організації built-in та вимикає опцію Single org only.

Фільтрація корисних навантажень вебхуків​

Під час роботи з вебхуками вам не завжди потрібні повні дані про запис. Casdoor дозволяє фільтрувати корисне навантаження, налаштовуючи ObjectFields для кожного вебхука. Ця функція особливо цінна, коли у вас є проблеми конфіденційності, обмеження пропускної здатності або коли ваш кінцевий пункт обробляє лише певні поля.

Конфігурація ObjectFields приймає значення "All" для отримання повного запису або список назв конкретних полів, які ви хочете включити. Коли ви вказуєте назви полів, Casdoor надсилатиме у корисному навантаженні вебхука лише ці поля, зменшуючи розмір навантаження та експортуючи лише ті дані, які потрібні вашому додатку.

Якщо ви налаштуєте кілька вебхуків із різними параметрами ObjectFields, кожен вебхук працюватиме незалежно. Наприклад, один вебхук може отримувати лише ID користувачів та часові мітки, а інший — повні профілі користувачів. Casdoor гарантує, що фільтрація, застосована до одного вебхука, не впливає на дані, що надсилаються до інших, навіть якщо вони активуються однією й тією ж подією.

Приклад корисного навантаження​

Приклад JSON, який надсилається до вашого вебхука під час входу:

{
  "event": "login",
  "timestamp": 1709452800,
  "user": {
    "id": "12345",
    "username": "johndoe",
    "email": "johndoe@example.com"
  }
}

Ваш додаток повинен розібрати це корисне навантаження та виконати необхідні дії, такі як логування події або сповіщення іншої служби.

Класифікація невдалих входів​

Кожна спроба входу зберігається як запис (видимий у розділі Records в адміністративній консолі та доставлений разом із корисним навантаженням вебхука). Коли вхід не вдається, Casdoor заповнює поле detail запису стабільною, машиночитабельною причиною, щоб ви могли класифікувати невдалі спроби без аналізу локалізованих повідомлень про помилки.

Можливі причини:

деталіMeaning
user-not-foundNo matching user for the supplied identifier.
account-disabledThe user account is disabled (forbidden).
account-frozenThe user account is frozen/locked.
wrong-passwordThe password did not match.
password-expiredThe password has expired and must be reset.
mfa-failedMulti-factor authentication verification failed.

Успішні входи залишають поле detail порожнім. Використовуйте ці значення для побудови панелей аудиту, системи оповіщення (наприклад, про різке збільшення кількості випадків wrong-password) або логіки блокування, прив'язаної до конкретної причини невдачі.

Тестування вебхуків​

Перед використанням у продакшені протестуйте за допомогою:

  • Beeceptor – Дозволяє створити власну URL-адресу вебхука та перевіряти вхідні запити.
  • Webhook.site – Надає миттєву кінцеву точку вебхука для тестування.

Приклад із Beeceptor​

  1. Створіть кінцеву точку на Beeceptor.
  2. Скопіюйте URL-адресу та встановіть її як URL-адресу вебхука в Casdoor.
  3. Ініціюйте подію (наприклад, увійдіть до Casdoor).
  4. Перевірте запит на панелі керування Beeceptor.

Обробка вебхуків у вашому додатку​

Ваш сервер повинен бути здатним обробляти вхідні запити вебхуків. Нижче наведено простий приклад на Node.js:

const express = require('express');
const app = express();

app.use(express.json());

app.post('/webhook', (req, res) => {
  console.log('Received webhook:', req.body);
  res.status(200).send('Webhook received');
});

app.listen(3000, () => console.log('Server running on port 3000'));

Перевіряйте вхідні запити вебхуків (наприклад, підписи або спільні секрети) та тестуйте їх за допомогою Beeceptor або Webhook.site перед використанням вебхуків у виробничому середовищі.

Відстеження доставки та повторні спроби​

Casdoor зберігає кожну спробу доставки вебхука як запис Webhook Event. Перейдіть до Webhook Events у бічному меню, щоб переглянути історію доставок для всіх вебхуків у вашій організації.

Кожен запис події включає:

ПолеОпис
Статусpending, success, failed, or retrying
Кількість спробHow many delivery attempts have been made
Last status codeHTTP response code from the most recent attempt
Остання відповідь / помилкаТіло відповіді або повідомлення про помилку від останньої спроби
Наступний час повторуWhen the next automatic retry will occur (if applicable)

Автоматичне повторення​

Невдалі доставки автоматично повторюються фоновим процесом, який запускається кожні 30 секунд. За замовчуванням максимальна кількість повторень для однієї події становить 3. Після вичерпання всіх спроб статус події встановлюється як failed, і подальші автоматичні спроби не виконуються.

Ручне відтворення​

Щоб повторно надіслати подію, відкрийте її в списку Webhook Events і натисніть Replay. Це створює нову спробу доставки незалежно від поточної кількості повторень або статусу. Використовуйте цей метод для відновлення після тимчасових збоїв кінцевої точки або для повторної обробки події після виправлення помилки у вашому обробнику.
