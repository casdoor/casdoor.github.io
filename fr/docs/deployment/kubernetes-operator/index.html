Exécuter Casdoor avec l'Opérateur Kubernetes

Ce guide explique comment exécuter Casdoor sur Kubernetes avec l'opérateur Casdoor, et comment déclarer des organisations et des applications comme ressources Kubernetes.

Objectifs d'apprentissage​

  • Installer l'opérateur.
  • Exécuter une instance Casdoor à partir d'une ressource Casdoor, avec SQLite pour un essai et avec PostgreSQL, Redis et un Ingress pour la production.
  • Créer des organisations et des applications avec CasdoorOrganization et CasdoorApplication, et monter les identifiants client d'une application à partir d'un Secret.
  • Mettre à niveau et supprimer des instances.

Prérequis​

  • Un cluster Kubernetes, version 1.29 ou ultérieure
  • kubectl
  • Pour la production : une base de données MySQL ou PostgreSQL et un serveur Redis accessibles par le cluster
Vous ne souhaitez pas l'auto-héberger ?

Casdoor Cloud vous fournit une instance Casdoor dédiée que nous hébergeons et maintenons à jour pour vous, à partir de 29 $/mois sans frais par utilisateur. Les nouveaux comptes reçoivent 20 $ de crédit gratuit pour essayer.

Opérateur ou chart Helm ?​

Les deux exécutent la même image Casdoor.

  • Le chart Helm installe une seule release Casdoor configurée via un fichier values. Choisissez-le si vous exécutez une seule instance et la gérez avec Helm.
  • L'opérateur ajoute trois types de ressources au cluster. Casdoor exécute une instance ; CasdoorOrganization et CasdoorApplication gèrent ce qui se trouve dans une instance, et chaque application reçoit un Secret contenant son client ID, son client secret et son certificat. Choisissez-le si vous exécutez plusieurs instances, si les applications qui s'authentifient via Casdoor sont déployées sur le même cluster, ou si vous gérez le cluster avec des outils GitOps tels qu'Argo CD ou Flux.

Installer l'opérateur​

kubectl apply --server-side -k https://github.com/casdoor/casdoor-operator/config/default

La commande installe les trois définitions de ressources personnalisées (CRD) et un rôle de cluster, et exécute l'opérateur dans l'espace de noms casdoor-operator-system :

kubectl -n casdoor-operator-system get pods

L'opérateur surveille tous les espaces de noms. Pour le limiter à un seul espace de noms, ajoutez --watch-namespace=<namespace> aux arguments du déploiement casdoor-operator-controller-manager.

Pour épingler une release, ajoutez ?ref=<tag> à l'URL et définissez le tag d'image dans votre propre kustomization :

kustomization.yaml
resources:
- https://github.com/casdoor/casdoor-operator/config/default?ref=v2.2.0
images:
- name: casbin/casdoor-operator
  newTag: "2.2.0"

Les releases sont listées sur GitHub, et les images sont disponibles sur Docker Hub.

Créer une instance Casdoor​

  1. Créez un Secret contenant le mot de passe du compte built-in/admin :

    kubectl create secret generic casdoor-admin --from-literal=password='<password>'

  2. Créez une ressource Casdoor. Celle-ci exécute un seul réplica qui conserve ses données dans un fichier SQLite sur un volume de 1 Gi :

    casdoor.yaml
    apiVersion: operator.casdoor.org/v1alpha1
    kind: Casdoor
    metadata:
      name: casdoor
    spec:
      database:
        driver: sqlite
        storage:
          size: 1Gi
      initAdminPasswordSecretRef:
        name: casdoor-admin
        key: password
    kubectl apply -f casdoor.yaml
    kubectl get casdoor
    NAME      READY   REPLICAS   IMAGE                   URL                               AGE
    casdoor   True    1          casbin/casdoor:4.19.0   http://casdoor.default.svc:8000   2m

  3. Ouvrir Casdoor :

    kubectl port-forward svc/casdoor 8000:8000

    Accédez à http://localhost:8000 et connectez-vous en tant qu'admin avec le mot de passe provenant du Secret.

L'opérateur crée un Deployment, un Service et le volume. Le mot de passe est appliqué lorsque Casdoor initialise une base de données vide, et nécessite Casdoor 4.19.0 ou ultérieur. Sans initAdminPasswordSecretRef, Casdoor demande le mot de passe de built-in/admin lors de la première visite.

Exécuter Casdoor en production​

L'instance suivante exécute trois réplicas avec PostgreSQL pour les données, Redis pour les sessions et un Ingress avec TLS :

apiVersion: v1
kind: Secret
metadata:
  name: casdoor-credentials
stringData:
  db-password: <database password>
  admin-password: <admin password>
---
apiVersion: operator.casdoor.org/v1alpha1
kind: Casdoor
metadata:
  name: casdoor
spec:
  replicas: 3
  database:
    driver: postgres
    host: postgres.default.svc
    user: casdoor
    name: casdoor
    passwordSecretRef:
      name: casdoor-credentials
      key: db-password
  redis:
    endpoint: redis.default.svc:6379
  initAdminPasswordSecretRef:
    name: casdoor-credentials
    key: admin-password
  ingress:
    className: nginx
    host: door.example.com
    tlsSecretName: door-example-com-tls
  resources:
    requests:
      cpu: 100m
      memory: 256Mi

Ce que fait l'opérateur avec cette configuration :

  • Origin : origin prend par défaut le host de l'Ingress, donc l'émetteur OIDC est https://door.example.com. Définissez spec.origin si Casdoor est exposé autrement.
  • Replicas : Plus d'un réplica nécessite redis, car Casdoor y conserve les sessions ; sans cela, un utilisateur est déconnecté dès qu'une requête atteint un autre pod. SQLite ne supporte qu'un seul réplica. Le serveur API rejette une ressource Casdoor qui viole l'une de ces règles.
  • Database : Casdoor crée la base de données MySQL ou PostgreSQL si elle n'existe pas. Définissez database.create: false si l'utilisateur de la base de données ne peut pas créer de bases de données.
  • Secrets : Les mots de passe sont lus depuis des Secrets et ne sont jamais écrits dans un ConfigMap. Modifier le mot de passe de la base de données ou de Redis dans son Secret redémarre les pods avec la nouvelle valeur.
  • Availability : Avec deux réplicas ou plus, l'opérateur ajoute un PodDisruptionBudget. La ressource Casdoor possède un sous-ressource scale, donc kubectl scale casdoor casdoor --replicas=5 et un HorizontalPodAutoscaler fonctionnent dessus.
  • Health : Les sondes utilisent /api/health. La condition Ready passe à True lorsque tous les réplicas de la version actuelle sont disponibles.

Configurer l'instance​

FieldDescription
imageCasdoor image. Defaults to the version the operator was released with.
replicasNumber of pods, 1 by default.
originPublic URL, used as the OIDC issuer.
database.drivermysql, postgres or sqlite.
database.host, port, name, user, sslModeConnection settings. name defaults to casdoor.
database.passwordSecretRefSecret key holding the database password.
database.dataSourceNameSecretRefSecret key holding a complete dataSourceName, which replaces the fields above.
database.createCreate the MySQL or PostgreSQL database if it is missing. true by default.
database.storageVolume for the SQLite file. Without it, the file lives in an emptyDir and is lost with the pod. The volume is kept when the Casdoor resource is deleted.
redis.endpoint, passwordSecretRef, dbSession store. Several addresses separated by ; use Redis Cluster.
initAdminPasswordSecretRefPassword of built-in/admin for a new database.
apiCredentialsSecretRefCredentials the operator uses to call the Casdoor API. See API credentials.
initData.secretRef, newOnlySecret key holding an init data file. With newOnly, the default, objects that already exist are left alone.
configOther configuration items, such as defaultLanguage: zh. Items covered by the fields above are ignored.
envExtra environment variables for the Casdoor container, applied last.
service.type, port, annotationsService settings. Port 8000 by default.
ingress.host, className, tlsSecretName, annotationsCreates an Ingress when set.
resources, nodeSelector, tolerations, affinity, topologySpreadConstraints, priorityClassName, serviceAccountName, imagePullSecrets, podLabels, podAnnotationsPassed to the pod.

Exécutez kubectl explain casdoor.spec pour obtenir le schéma complet.

Gérer les organisations et les applications​

Identifiants API​

Pour créer des objets dans une instance, l'opérateur appelle l'API Casdoor avec le client ID et le client secret de app-built-in, l'application de l'organisation built-in, qui peut gérer toutes les organisations.

  • Avec initAdminPasswordSecretRef, l'opérateur se connecte en tant qu'built-in/admin une fois après le premier démarrage, lit les identifiants de app-built-in et les conserve dans le Secret <name>-api-credentials. Il n'utilise plus le mot de passe ensuite.
  • Si le mot de passe a été changé avant que l'opérateur ne se connecte, ou si vous ne souhaitez pas lui donner accès, copiez le client ID et le client secret de app-built-in depuis la console d'administration dans un Secret avec les clés clientId et clientSecret, et pointez spec.apiCredentialsSecretRef vers celui-ci.

La condition APIReady de la ressource Casdoor indique si les identifiants sont disponibles :

kubectl get casdoor casdoor -o jsonpath='{.status.conditions[?(@.type=="APIReady")].message}'

Si le mot de passe est incorrect, l'opérateur réessaie toutes les 5 minutes, ce qui reste inférieur au nombre de tentatives échouées qui verrouille le compte.

Créer une organisation et une application​

apiVersion: operator.casdoor.org/v1alpha1
kind: CasdoorOrganization
metadata:
  name: acme
spec:
  casdoorRef:
    name: casdoor
  displayName: ACME Corp
  websiteUrl: https://acme.example.com
  passwordType: bcrypt
  languages: [en, zh]
---
apiVersion: operator.casdoor.org/v1alpha1
kind: CasdoorApplication
metadata:
  name: acme-portal
spec:
  casdoorRef:
    name: casdoor
  organization: acme
  displayName: ACME Portal
  redirectUris:
  - https://portal.acme.example.com/callback
  grantTypes: [authorization_code, refresh_token]
  tokenFormat: JWT-Standard
  expireInHours: 24
  cert: cert-built-in
kubectl get casdoororg,casdoorapp
NAME                                            CASDOOR   READY   AGE
casdoororganization.operator.casdoor.org/acme   casdoor   True    10s

NAME                                                  CASDOOR   ORGANIZATION   CLIENT ID              READY   AGE
casdoorapplication.operator.casdoor.org/acme-portal   casdoor   acme           44f1aa1fbe1afc436140   True    10s

casdoorRef.name est le nom d'une ressource Casdoor dans le même espace de noms. name définit le nom de l'objet dans Casdoor lorsqu'il diffère du nom de la ressource Kubernetes.

Utiliser les identifiants d'une application​

Pour chaque application, l'opérateur écrit un Secret nommé <name>-casdoor, ou le nom spécifié dans credentialsSecretName, avec les clés endpoint, clientId, clientSecret, organizationName, applicationName et certificate. Les clés correspondent aux paramètres des SDK Casdoor, afin qu'une application dans le cluster puisse les lire depuis des variables d'environnement :

containers:
- name: portal
  image: example/portal
  envFrom:
  - secretRef:
      name: acme-portal-casdoor
    prefix: CASDOOR_

Casdoor génère l'ID client et le secret client sauf si vous définissez clientId ou clientSecretSecretRef. L'endpoint est l'origine de l'instance, ou son adresse Service lorsqu'elle n'a pas d'origine.

Comprendre quels champs sont écrits par l'opérateur​

  • Champs dans le spec : Ils conservent les noms de l'API Casdoor. L'opérateur les écrit dans Casdoor et les rétablit dans un délai de 10 minutes s'ils sont modifiés dans la console d'administration.

  • Champs non définis par le spec : Ils conservent les valeurs qu'ils ont dans Casdoor, ce qui permet de les modifier dans la console d'administration. Définissez tout champ n'ayant pas de champ dédié dans le spec, comme signinMethods, providers ou mfaItems, dans extraFields :

    spec:
      extraFields:
        enableSigninSession: true
        signinMethods:
        - name: Password
          displayName: Password
          rule: All

  • Objets existants : Une ressource portant le nom d'un objet existant prend le contrôle de cet objet et écrit uniquement les champs présents dans son spec.

  • Suppression : La suppression d'une ressource CasdoorApplication supprime l'application dans Casdoor. La suppression d'une ressource CasdoorOrganization conserve l'organisation et ses utilisateurs dans Casdoor, sauf si la ressource a deletionPolicy: Delete.

Utiliser un serveur Casdoor que l'opérateur ne gère pas​

CasdoorOrganization et CasdoorApplication fonctionnent également avec un serveur Casdoor extérieur au cluster, tel qu'une instance Casdoor Cloud. Placez l'ID client et le secret client d'une application de son organisation built-in dans un Secret et utilisez casdoorRef.external :

apiVersion: v1
kind: Secret
metadata:
  name: door-api
stringData:
  clientId: <client ID of app-built-in>
  clientSecret: <client secret of app-built-in>
---
apiVersion: operator.casdoor.org/v1alpha1
kind: CasdoorApplication
metadata:
  name: grafana
spec:
  casdoorRef:
    external:
      endpoint: https://door.example.com
      credentialsSecretRef:
        name: door-api
  organization: acme
  redirectUris:
  - https://grafana.example.com/login/generic_oauth

LDAP​

Le Service expose le serveur LDAP de Casdoor sur le port 389. À l'intérieur du pod, Casdoor écoute sur le port 10389, car le pod s'exécute en tant qu'utilisateur 1000 et certains environnements d'exécution de conteneurs ne permettent pas de lier des ports inférieurs à 1024. Pour utiliser un autre port à l'intérieur du pod, définissez ldapServerPort dans config.

Mettre à niveau Casdoor​

Modifiez spec.image, ou mettez à niveau l'opérateur pour obtenir une image par défaut plus récente. L'opérateur effectue le déploiement progressif des pods un par un ; avec SQLite, il arrête l'ancien pod avant de démarrer le nouveau, car deux processus ne peuvent pas ouvrir le même fichier de base de données. Casdoor met à jour le schéma de la base de données au démarrage. Avant de passer de la version 3 à la version 4, consultez Mise à niveau de v3 à v4.

Désinstallation​

  1. Supprimez les ressources CasdoorApplication et CasdoorOrganization pendant que l'opérateur est encore en cours d'exécution, afin qu'il puisse supprimer leurs finalizers :

    kubectl delete casdoorapplications,casdoororganizations --all -A

  2. Supprimez les instances, ainsi que le volume SQLite si vous n'avez plus besoin des données :

    kubectl delete casdoor casdoor
    kubectl delete pvc casdoor-data

  3. Supprimez l'opérateur :

    kubectl delete -k https://github.com/casdoor/casdoor-operator/config/default
