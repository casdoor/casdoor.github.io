二次验证

升级式 MFA（Step-up MFA）允许应用在用户执行敏感操作（如批准付款、批准请求或以其他用户身份行动）之前，要求已登录用户提供其在 Casdoor 中启用的 MFA 因子的新代码。

  • 用户无需再次输入密码，也无需再次经过登录页面。
  • 用户在 Casdoor 中只需注册一次第二因子，该因子即可同时用于登录和升级式验证。
  • 应用程序永远不会看到或存储 TOTP 密钥、电子邮件地址、电话号码或恢复代码。
  • 通过的检查会返回由 Casdoor 签名的短期有效的一次性证明令牌。应用程序服务器在执行操作前兑换该令牌。

启用它​

打开 Applications，编辑应用程序并转到 Step-up MFA 选项卡。

字段描述
Enable step-up MFA允许应用程序使用升级式 API。未启用此功能的应用程序的请求将被拒绝。
Allowed methods应用程序接受的方法：TOTP（身份验证器应用）、Email、Phone（短信）、RADIUS 和 Recovery code。留空表示用户使用的所有已启用方法。
Proof token lifetime (seconds)证明令牌的有效期时长。默认为 300，最大值为 3600。

保存应用程序，然后点击 Try step-up verification 以使用您的账户运行检查。对话框仅显示您已启用的方法。代码正确后，页面将显示证明令牌及其声明。

该选项卡还显示了包含应用程序客户端 ID 的 curl 示例，以及最近的通过检查及其状态：Valid、Expired 或 Redeemed。

谁被验证​

调用者用户应用程序
携带访问令牌的用户浏览器 (Authorization: Bearer <access_token>)令牌所属用户令牌所属应用程序。不同的 clientId 将被拒绝。
携带 Casdoor 会话 Cookie 的用户浏览器已登录用户clientId 参数。用户必须属于应用程序的组织。
使用其客户端 ID 和密钥的应用程序服务器由 owner 和 name（或 userId）指定的用户。该用户必须属于应用程序的组织。调用应用程序

用户不得被禁止或删除。

API​

所有端点接收表单数据（multipart/form-data 或 application/x-www-form-urlencoded），并以标准的 {"status": "ok", "data": ...} 格式响应。

列出方法​

GET /api/mfa/step-up/methods 返回用户已启用且应用程序允许的方法，首选方法排在第一位。电子邮件地址和电话号码会被掩码处理。

{"status": "ok", "data": [{"mfaType": "app", "isPreferred": true}, {"mfaType": "email", "dest": "jo***@example.com"}]}

发送电子邮件或短信验证码​

POST /api/mfa/step-up/send-code，其中 mfaType 设置为 email 或 sms。验证码发送至用户为 MFA 启用的电子邮件地址或电话号码，绝不会发送至请求中的地址。它使用应用程序的 Email 或 SMS 提供商，与登录时的 MFA 步骤相同。

验证代码​

POST /api/mfa/step-up/verify

Parameter描述
mfaTypeapp、email、sms、radius 或 recovery
passcode验证码。对于 recovery，恢复代码也可以作为 recoveryCode 发送。
action可选，最多 500 个字符。一个用于命名检查所批准事项的值，例如 approve-payment-1024。该值会被复制到证明令牌中。
clientId当调用者使用 Casdoor 会话 Cookie 时指定应用程序
owner, name当应用程序使用自己的凭据调用时指定用户
curl -X POST https://door.casdoor.com/api/mfa/step-up/verify \
  -H "Authorization: Bearer <access_token>" \
  -F mfaType=app -F passcode=123456 -F action=approve-payment-1024
{"status": "ok", "data": {"token": "<proof token>", "tokenType": "step-up", "expiresIn": 300, "mfaType": "app"}}

此检查比登录时的 MFA 步骤更严格：

  • 仅检查用户已启用的因子。没有用于密钥或目标的参数，也不会回退到其他方法。
  • 组织的 Master verification code 不被接受。
  • MFA 步骤中的 Remember this account 不会跳过此步骤。每次调用都需要新的验证码。
  • TOTP 代码仅被接受一次。Casdoor 保留每个用户最后接受的时间步，因此相同的代码或较旧的代码将被拒绝。这也适用于登录时的 MFA 步骤和 RADIUS server。
  • 恢复代码在使用后会被移除。电子邮件和短信验证码是一次性的。

错误代码的计数与登录过程中 MFA 步骤的限制相同：Failed signin limit 和 Failed signin frozen time，默认分别为 5 次尝试和 15 分钟。来自浏览器的调用还会受到每个 IP 地址的限制。来自应用服务器的调用仅受用户限制，因此一个为多个用户验证代码的服务器不会被锁定。

兑换证明令牌​

应用的服务器使用其自身的客户端 ID 和密钥调用 POST /api/mfa/step-up/redeem，然后再执行该操作：

curl -X POST https://door.casdoor.com/api/mfa/step-up/redeem \
  -u <client_id>:<client_secret> \
  -F token=<proof token> -F action=approve-payment-1024
{"status": "ok", "data": {"tokenType": "step-up", "owner": "built-in", "name": "alice", "amr": ["mfa", "otp"], "auth_time": 1795099922, "mfa_type": "app", "action": "approve-payment-1024", "sub": "...", "aud": ["<client_id>"], "exp": 1795100222, "jti": "..."}}

Casdoor 会检查签名、受众（调用方应用）、过期时间，以及在提供 action 时检查令牌是否为该 action 签发。每个令牌只能兑换一次。第二次兑换将失败并返回 The step-up token has already been used。

证明令牌​

证明令牌是一个 JWT，使用应用的 Token cert 进行签名，头部包含 typ: step-up+jwt。

ClaimValue
tokenTypestep-up
sub用户的 ID，与 ID 令牌中的相同
owner, name用户的组织和名称
aud应用的客户端 ID
amrTOTP 和 RADIUS 为 ["mfa", "otp"]，短信为 ["mfa", "sms", "otp"]，邮件为 ["mfa", "email", "otp"]，或恢复码为 ["mfa", "recovery"]
auth_time本次验证的时间
mfa_type使用的方法
action请求的 action（如果有）
iat, exp, jti签发时间、过期时间和唯一 ID

你也可以使用 Casdoor 的 JWKS https://<your-casdoor-host>/.well-known/jwks 自行验证令牌（参见 OIDC client）。然后检查 tokenType、aud、exp 和 action，并记住每个 jti 直到其过期，以确保令牌仅被使用一次。

典型流程​

  1. 用户在应用中点击 Approve payment。
  2. 你的前端显示一个对话框，通过 /api/mfa/step-up/methods 列出可用方法，并在需要时通过 /api/mfa/step-up/send-code 发送邮件或短信验证码。
  3. 用户输入验证码。你的前端使用用户的访问令牌和 action=approve-payment-1024 调用 /api/mfa/step-up/verify，并将证明令牌传递给服务器。
  4. 你的服务器使用相同的 action 调用 /api/mfa/step-up/redeem。只有当调用成功时，服务器才会批准付款。

如果你希望在自己的后端构建对话框，你的服务器可以使用其客户端凭证以及用户的 owner 和 name 直接调用 /api/mfa/step-up/verify，并根据响应采取行动。

审计​

每次调用都会写入 Records，归属于已验证的用户，无论成功还是失败。记录中的验证码会被掩码处理。Step-up MFA 选项卡列出了应用的最新成功验证记录。
