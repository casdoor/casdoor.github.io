MCP トラブルシューティング

このページでは、Casdoor の組み込み MCP サーバーおよび OAuth 2.0 プロバイダーとして Casdoor を使用する独自の MCP サーバーに関する問題を扱います。

よくある問題​

MCP サーバーが HTTP 401 で応答する​

原因

  • アクセストークンの有効期限が切れています。
  • トークンの aud (audience) クレームが MCP サーバーのリソース URI と一致していません。
  • リクエストに Authorization: Bearer ヘッダーがありません。

解決策

  1. jwt.io などを使用してトークンをデコードし、exp クレームを確認してください。
  2. aud クレームが MCP サーバーの URI（スキーム、ホスト、ポートを含む）と完全に一致していることを確認してください。
  3. リクエストにヘッダー Authorization: Bearer <access-token> が含まれていることを確認してください。
  4. クライアントが OAuth 2.0 フローで resource パラメータを送信する場合、それが MCP サーバーの URI であることを確認してください。
# Example: Check token claims
curl -X GET https://your-mcp-server.com/api/mcp \
  -H "Authorization: Bearer YOUR_TOKEN"

# If 401, inspect token at jwt.io:
# - exp: 1735689600 (must be in future)
# - aud: "https://your-mcp-server.com" (must match server URI)
# - scope: "read:application" (must include required scopes)

ブラウザが CORS エラーを報告する​

原因

MCP クライアントのオリジンが Casdoor に信頼されているオリジンではありません。Casdoor は、アプリケーションの Redirect URLs のオリジンからのクロスオリジンリクエストを許可しています。

解決策

  1. Casdoor 管理コンソールで、アプリケーションの編集ページを開きます。
  2. MCP クライアントのオリジン（スキームと非標準ポートを含む）を持つ URL を Redirect URLs に追加します。ローカル開発の場合は、http://localhost:<port> を追加してください。

ブラウザから API を呼び出すを参照してください。

リダイレクト URL が一致しない​

原因

  • 認可リクエストの redirect_uri が、アプリケーションの Redirect URLs に含まれていません。
  • スキーム（http または https）、ポート、または末尾のスラッシュが異なります。

解決策

  1. 認可リクエストから正確な redirect_uri をコピーします。
  2. それをアプリケーションの Redirect URLs に追加します。

以下の URL はすべて異なります：

# These are all different redirect URIs:
http://localhost:3000/callback
https://localhost:3000/callback  # Different scheme
http://localhost:3000/callback/  # Trailing slash
http://localhost:3001/callback   # Different port

ディスカバリエンドポイントが HTTP 404 を返す​

原因

クライアントが、その役割に合わないディスカバリパスを要求しています。

解決策

ユースケースに応じたエンドポイントを要求してください：

  1. OAuth 2.0 Authorization Server Metadata (RFC 8414):

    curl https://your-casdoor.com/.well-known/oauth-authorization-server

  2. OpenID Connect Discovery:

    curl https://your-casdoor.com/.well-known/openid-configuration

  3. OAuth 2.0 Protected Resource Metadata (RFC 9728):

    curl https://your-casdoor.com/.well-known/oauth-protected-resource

リソースサーバーである MCP サーバーは、認可サーバーを通知するために oauth-protected-resource ドキュメントを発行します。

動的クライアント登録が拒否される​

原因

  • 組織に対して動的クライアント登録（DCR）が無効になっています。
  • 登録リクエストに必要なフィールドが含まれていません。

解決策

  1. Casdoor 管理コンソールで、組織の編集ページを開き、Enable dynamic client registration をオンにします。登録 URL に organization パラメータがない場合、クライアントは built-in 組織に登録されます。

  2. 登録リクエストですべて必要なメタデータを送信します：

    {
      "client_name": "My MCP Client",
      "redirect_uris": ["https://client.example.com/callback"],
      "grant_types": ["authorization_code"],
      "token_endpoint_auth_method": "client_secret_basic"
    }

動的クライアント登録を参照してください。

同意画面が表示されない​

原因

  • アプリケーションにカスタムスコープがありません。Casdoor はカスタムスコープに対してのみ同意を求めます。
  • クライアントがカスタムスコープを要求していません。
  • ユーザーが既にこのアプリケーションに対して要求されたスコープを許可または拒否しています。Casdoor は再度確認せず、トークンには許可されたスコープのみが含まれます。

解決策

  1. アプリケーションでスコープが定義されており、クライアントがそれらを要求していることを確認してください。カスタムスコープを参照してください。
  2. 同意画面を再度テストするには、Consents ページで以前の許可を取り消します。

ツール呼び出しが insufficient_scope で失敗する​

原因

アクセストークンに、ツールが必要とするスコープが含まれていません。

解決策

  1. エラーから required_scope と granted_scopes を読み取ります：

    {
      "error": {
        "code": -32001,
        "message": "insufficient_scope",
        "data": {
          "tool": "add_application",
          "granted_scopes": ["read:application"],
          "required_scope": "write:application"
        }
      }
    }

  2. 必要なスコープを含めて新しいトークンを要求します：

    curl -X POST https://your-casdoor.com/api/login/oauth/access_token \
      -d "grant_type=client_credentials" \
      -d "client_id=YOUR_CLIENT_ID" \
      -d "client_secret=YOUR_CLIENT_SECRET" \
      -d "scope=read:application write:application"

スコープレファレンスを参照してください。

認可リクエストが invalid_target で失敗する​

原因

  • resource パラメータは、RFC 8707 で要求されているように絶対 URI ではありません。
  • リソース URI にスキームがありません。

解決策

  1. 完全な URL を resource として送信します:

    # Correct:
    resource=https://your-server.com
    resource=https://api.example.com:8080

    # Incorrect:
    resource=your-server.com        # Missing scheme
    resource=localhost:3000         # Missing scheme

  2. resource の値がアクセストークンの aud クレームになることを覚えておいてください。これは MCP サーバーが期待するオーディエンスと正確に一致している必要があります。

Claude Desktop または Cursor が独自の MCP サーバーに接続できない​

原因

  • MCP サーバーが有効な Protected Resource Metadata を返していません。
  • WWW-Authenticate ヘッダーが存在しないか、形式が不正です。
  • クライアントがディスカバリーエンドポイントに到達できません。
  • MCP サーバーでのトークン検証が失敗しています。

解決策

  1. メタデータエンドポイントが有効な JSON を返すか確認します:

    curl https://your-mcp-server.com/.well-known/oauth-protected-resource

    期待されるレスポンス:

    {
      "resource": "https://your-mcp-server.com",
      "authorization_servers": [
        "https://your-casdoor.com"
      ]
    }

  2. 未認証のリクエストに対する WWW-Authenticate ヘッダーを確認します:

    curl -v https://your-mcp-server.com/api/mcp

    期待されるヘッダー:

    WWW-Authenticate: Bearer realm="mcp-server",
      authorization_uri="https://your-casdoor.com/login/oauth/authorize",
      scope="read:application write:application"

  3. OAuth 2.0 フローを手動で実行します:

    # 1. Get authorization code (requires browser)
    # 2. Exchange for token
    curl -X POST https://your-casdoor.com/api/login/oauth/access_token \
      -d "grant_type=authorization_code" \
      -d "code=AUTH_CODE" \
      -d "redirect_uri=YOUR_REDIRECT_URI" \
      -d "client_id=YOUR_CLIENT_ID" \
      -d "client_secret=YOUR_CLIENT_SECRET"

    # 3. Test MCP endpoint with token
    curl https://your-mcp-server.com/api/mcp \
      -H "Authorization: Bearer ACCESS_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

デバッグツール​

MCP Inspector​

公式の MCP Inspector は、MCP 接続をインタラクティブにテストします。ツールの参照や呼び出し、JSON-RPC リクエストとレスポンスの表示、OAuth 2.0 フローの実行が可能です。

npx @modelcontextprotocol/inspector

ディスカバリーエンドポイント​

各ディスカバリーエンドポイントが有効な JSON を返すか確認します:

# OAuth Authorization Server
curl -s https://your-casdoor.com/.well-known/oauth-authorization-server | jq

# OIDC Configuration
curl -s https://your-casdoor.com/.well-known/openid-configuration | jq

# Protected Resource (for MCP resource servers)
curl -s https://your-mcp-server.com/.well-known/oauth-protected-resource | jq

トークンクレーム​

jwt.io またはコマンドラインでアクセストークンをデコードします:

# Alternative: Decode token with jq
echo "YOUR_JWT_TOKEN" | cut -d. -f2 | base64 -d | jq
ClaimCheck
audMatches the URI of the MCP server
scopeContains the scopes that the tools require
expIs in the future. The value is a Unix timestamp
issIs the URL of Casdoor
subIs the ID of the user
client_idIs the application that received the token

トークンイントロスペクション​

Casdoor にトークンが有効かどうか、またその内容を確認します (RFC 7662):

curl -X POST https://your-casdoor.com/api/login/oauth/introspect \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -u "CLIENT_ID:CLIENT_SECRET" \
  -d "token=ACCESS_TOKEN"

レスポンス:

{
  "active": true,
  "scope": "read:application write:application",
  "client_id": "your-client-id",
  "username": "admin",
  "exp": 1735689600,
  "iat": 1735603200,
  "aud": "https://your-mcp-server.com"
}

curl を使用した OAuth 2.0 フロー​

# 1. Test authorization endpoint (requires browser)
# Open in browser:
https://your-casdoor.com/login/oauth/authorize?
  client_id=YOUR_CLIENT_ID&
  redirect_uri=http://localhost:8080/callback&
  response_type=code&
  scope=read:application&
  state=random-state

# 2. Exchange authorization code for token
curl -X POST https://your-casdoor.com/api/login/oauth/access_token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=authorization_code" \
  -d "code=AUTHORIZATION_CODE" \
  -d "redirect_uri=http://localhost:8080/callback" \
  -d "client_id=YOUR_CLIENT_ID" \
  -d "client_secret=YOUR_CLIENT_SECRET"

# 3. Use access token with MCP server
curl https://your-mcp-server.com/api/mcp \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

ログとネットワークトレース​

  • MCP クライアント: デバッグモードまたは詳細モードを有効にし、リダイレクト、トークン交換、ツール呼び出しに関するログを確認します。

  • MCP サーバー: 受信した各リクエスト、トークン検証の結果（失敗の場合は理由も含む）、およびスコープチェックをログに記録します。

  • ブラウザ: 開発者ツールを開きます。ネットワークタブではリダイレクトと API 呼び出しが表示され、コンソールでは JavaScript エラーが表示されます。

  • CLI クライアント: mitmproxy を経由してクライアントをルーティングし、リクエストを確認します:

    mitmproxy -p 8080
    # Configure client to use proxy: http://localhost:8080
